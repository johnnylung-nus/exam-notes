C098

Anomaly detection

Anomaly detection identifies observations that differ from expected behaviour. It may return a normal/anomaly label or a score needing a threshold.

What this tells us: Do not compare thresholds without stating score direction and comparison rule. A normal-class probability may run in the opposite direction from an anomaly-distance score.

Threshold decisions

Read the relationships and follow the choices

  • Anomaly scores measure deviation from an assumed normal reference, not a verified cause. A high score indicates investigation need unless a separate diagnostic model is validated.
  • Geometric methods use distance from normal clusters; statistical methods use low-probability regions; supervised methods require normal and abnormal labels.
  • A threshold converts scores into operational alerts and changes false alarms versus missed events. It should reflect scenario costs and available validation.
  • Context and sequences matter: an individually ordinary reading may be abnormal for the operating mode or as part of an unusual pattern.
Implementation steps and their purpose
  1. Define normal behaviour and relevant context.
  2. Prepare representative normal and available abnormal examples.
  3. Choose cluster-distance, distribution-based or supervised classification approach according to available data.
  4. Produce a score or label.
  5. Select a threshold according to false-alarm/missed-event consequences.
  6. Investigate flagged cases and monitor drift.

Choose the method from the problem

Use for unusual sensor behaviour when the exact fault type may be unknown or rare.

  • An anomaly is not automatically a diagnosed fault.

Implement it and test the outcome

Data, components and application

  • Rare faults → evaluate missed events as well as false alarms → overall accuracy can be misleading.
  • Normal operation changes → include context/update baseline → drift can trigger spurious alarms.
  • Single reading normal but sequence unusual → analyze windows → collective anomalies need temporal context.

How to evaluate it

Check false alarms, missed anomalies, detection delay and usefulness of alerts on unseen operation periods.

Build the answer in this order

  1. What is normal?
  2. Point/contextual/collective deviation.
  3. Score and threshold.
  4. Consequences and evaluation.

An answer you could write

  • I define normal behaviour for the relevant operating mode and produce an anomaly score.
  • I choose a threshold using missed-event and false-alert consequences on held-out operation.
  • A flagged anomaly is not automatically a diagnosed Mistracking or Carryback cause.

ISY5002 Q2(c) — Critique anomaly classification with only two anomalies

What the question requires

  1. Read the imbalance and representation constraints.
  2. Identify two distinct challenges in the proposed classifier.
  3. Propose a remedy for each and tie it to the supplied features/data.
  4. Explain how anomaly detection would be assessed.

Proposed answer points

  • Challenge 1:3,000 normal sequences versus two anomalies cannot support reliable supervised anomaly generalization; an all-normal model already scores 3000/3002≈99.93% accuracy. Consider learning normal behaviour with a one-class or reconstruction-based detector and collect more diverse verified anomalies.
  • Challenge 2:30 concatenated features can be redundant/on different scales; the plotted histogram may be less discriminative than frequency features. Inspect the supplied figure, compare representations on held-out data, scale training-derived features and reduce redundant dimensions if justified.
  • Each sequence has 4×50=200 samples; this is separate from the engineered 10+20=30 feature dimensions. Evaluate false alarms and anomaly recall; two anomalies make estimates highly uncertain.

Avoid: Do not manufacture many reliable abnormal examples by copying two rows. A temporal histogram also discards order. The missing QA answer is newly analysed study guidance, not a past reviewed answer.

C099

Single-modality sensing

Single-modality sensing uses one type of evidence, such as inertial measurements, audio or vision. Choose the modality according to what must be recognized.

What can one audio stream answer?

Speech recognitionSpoken “move forward”Word transcriptLinguistic content

Environment classificationMachine/room recordingEnvironment/activity labelOverall sound pattern

What this tells us: One strong result does not transfer automatically across tasks. A model identifying the speaker has not thereby recognized the command or checked whether it is safe to execute.

What information this representation preserves

  • A single modality can have multiple axes or channels. Three accelerometer axes remain inertial evidence, not three different modalities.
  • The useful unit often is a time window: one isolated acceleration reading can occur during several activities, while a changing pattern is more distinctive.
  • Task definitions matter within a modality. Audio classification, speaker recognition and speech recognition have different outputs despite using microphone data.
  • Start with the simplest evidence sufficient for the goal; add a modality when it resolves a specific observable weakness rather than for sophistication.
Implementation steps and their purpose
  1. Define the target event and operating conditions.
  2. Choose a modality that observes the needed evidence.
  3. Capture and buffer an appropriate window.
  4. Extract features or learn a representation.
  5. Recognize the activity/object/event.
  6. Connect the result to the specified action.

Prepare the data and validate the representation

Data, components and application

  • Chosen modality cannot observe required fact → add/change evidence → no algorithm can reliably infer every hidden detail.
  • Environment noise or occlusion → improve capture or consider complementary input → modality has specific weaknesses.
  • Single reading too weak → use a sequence/window → motion and speech depend on change.

How to evaluate it

Check target recognition, robustness in intended conditions, latency and whether the sensor is sufficient for the required output.

Build the answer in this order

  1. Required fact.
  2. Why this modality?
  3. Window/features/model.
  4. Failures and action quality.

Choose the representation from the task

Use when a simple sufficient sensor solution is preferable to combining multiple data types.

An answer you could write

  • I choose one modality because it directly observes the required motion/sound/appearance evidence.
  • I define one window and its target output before selecting the recognizer.
  • I add another modality only if it supplies a clearly missing piece of evidence.

Data augmentation for sensors

Sensor augmentation creates plausible variations of training windows while preserving the target meaning. The lecture covers scaling, magnitude filtering, jittering and time-warping.

CalculationDiagramHow it worksWorked exampleChoose & designProblems & fixes

Choose from the scenario

Use when training data lacks realistic variation or the model overfits to exact recorded conditions.

Scenario cueSuitable choiceWhy it fits
Device gain differs slightlyMild scaling after label checkCan reduce sensitivity to nuisance amplitude variation.
Need preserve exact event timingAvoid aggressive time-warpingThe augmentation must not teach timing invariance incorrectly.

Choose transformations according to what defines the label

Worked study example: Illustrative activity/fault examples based on the lecture’s augmentation types.

All steps shown
TransformationBefore→afterUseful assumptionWhen invalid
Scaling[1,2,1]→[1.1,2.2,1.1]Small gain variation is nuisanceAbsolute magnitude defines severity
Jitter[1,2,1]→[1.02,1.97,1.01]Small sensor noise expectedNoise erases weak event
Time-warpingSame shape over varied intervalsExecution speed varies harmlesslyTiming itself defines fault
Train-only generationOriginal first assigned to splitRelated copies stay togetherCopy leaks into test set

What this tells us: An activity may tolerate small speed differences while a fault detector using exact periodic timing may not. “More augmented data” is therefore not a sufficient justification.

The distinction that changes the answer

  • Augmentation changes training examples to mimic nuisance variation while preserving their target labels. It does not create new independent people or machines.
  • Scaling changes overall magnitude; jitter adds noise; time-warping changes local timing. Each can destroy label meaning in the wrong task.
  • Split by independent originals/subjects before augmentation. If related copies enter both training and test sets, evaluation can reward recognition of near-duplicates.
  • Transformation strength should be validated: the benefit is robustness on real unseen recordings, not success at recognizing synthetic copies.

What would make the choice wrong?

What you observeWhy it happensWhat to changeWhy that helps
Validation unusually excellentAugmented relatives crossed splitsSplit independent originals firstPrevents near-duplicate leakage.

Common wrong answers and the exact correction
  • Augmentation does not create independent real participants/machines.
  • A technique useful for one sensor task may destroy another task’s label.

Apply the distinction

Data, components and application

  • Transformation changes event meaning → restrict range/type → prevents wrong training labels.
  • Augmented copies across splits → split originals first → prevents leakage.
  • Only augmented test performance improves → use realistic independent recordings → synthetic robustness is not enough.

How to evaluate it

Compare unseen real-data errors and resistance to relevant noise, while checking that important magnitude/timing cues remain usable.

Build the answer in this order

  1. Missing variation.
  2. Label-preserving transform.
  3. Training-only use.
  4. Real-data comparison.

An answer you could write

  • I augment only training windows using transformations that preserve the target event.
  • I retain independent real validation/test recordings and inspect each class.
  • I reject scaling or time-warping when magnitude or timing defines the required label.

Multimodal representation and fusion

Fusion combines evidence from sensor streams. The lecture distinguishes tightly coupled early/intermediate fusion, loosely coupled restricted fusion and uncoupled late fusion.

Choose from the scenario

Use when sensors provide complementary information or one stream can guide interpretation of another.

Scenario cueSuitable choiceWhy it fits
Existing validated recognizersLate fusionKeeps separate pipelines and reduces redesign.
Need fine cross-sensor interactionsAligned feature fusionThe shared model can use relationships before decisions discard detail.

Compare three fusion designs on the same sensing task

Worked study example: Illustrative machine observations; no measured improvement is asserted.

All steps shown
DesignWhat passes between streamsExampleTrade-off
Early/intermediateRaw values or learned featuresAligned sound+vibration feed shared classifierCan learn detailed interactions
RestrictedRecognition/context from first streamDetected machine mode restricts sound classesCan reduce search but propagate wrong context
LateSeparate class scores/labelsSound and vibration recognizers feed decision combinerReuses pipelines, loses internal detail
Single-stream baselineOne stream onlySound recognizer aloneNeeded to establish fusion benefit

What this tells us: The diagram should identify the actual exchanged item. A final label used as context is different from concatenating feature vectors or averaging score outputs.

The distinction that changes the answer

  • The fusion point determines what information the combined model can use. Raw/feature fusion preserves more cross-stream detail but requires stronger alignment and compatible representation.
  • Restricted fusion uses one recognizer to narrow the other’s search space. It is not merely averaging two final class scores.
  • Late fusion combines existing recognizer outputs; it can reuse pipelines but cannot recover details already discarded by those recognizers.
  • An additional sensor helps only if it contributes usable complementary evidence. Correlated errors or a poor stream can worsen the result.

What would make the choice wrong?

What you observeWhy it happensWhat to changeWhy that helps
More sensors, worse resultPoor stream dominates or errors correlateMeasure stream quality and compare baselinesInput count is not evidence quality.
Wrong second-stage classFirst-stage context incorrectly restricts searchTest restricted-fusion failure pathAn early mistake can exclude the true answer.
Common wrong answers and the exact correction
  • Fusion is not automatically more accurate.
  • Label the fusion point; “combine data” alone is vague.

Apply the distinction

Data, components and application

  • Mismatched times/entities → align streams → prevents combining unrelated events.
  • Noisy modality dominates → account for input quality → more inputs can worsen results.
  • Existing pipelines costly to rebuild → consider late fusion → reuses separate recognizers.

How to evaluate it

Compare task errors, missing/noisy-stream robustness, latency and added implementation cost.

Build the answer in this order

  1. Why multiple streams?
  2. Choose fusion point.
  3. Handle alignment/quality.
  4. Compare actual benefit.

An answer you could write

  • I choose the fusion point explicitly: features, recognition-guided restriction or final decisions.
  • I align the streams and compare with each single-modality baseline.
  • I test noisy/missing inputs because fusion gains are conditional, not guaranteed.

ISY5002 Q2(b) — Deep-RL sorting architecture, reward and safe learning

What the question requires

  1. Define observations/state, actions and task success.
  2. Choose reward terms for correct sorting, safety and time.
  3. Draw hardware, perception, decision and control loops.
  4. Explain simulation-first training and controlled transfer.

Proposed answer points

  • RGB-D + robot sensors → identification/tracking → state → deep-RL policy → safety/motion checks → arm/gripper action → new observations and reward. Include target objects, obstacles, other robots and people in the environment.
  • Reward correct placement; penalize collisions and unnecessary time. Enforce joint/gripper constraints in control rather than hoping a learned reward guarantees safety.
  • Train in a physics-based simulator, then validate in controlled low-risk real tests with safety constraints active.

Avoid: A reward penalty is not a hard safety guarantee. Classification of the object and control of the robot are separate responsibilities.

C102

Spatial / temporal / feature alignment

Alignment makes streams refer to comparable positions, times or features. Fusion is unreliable if the inputs describe different events.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Why same index may pair the wrong event phase

Worked study example: Illustrative two recordings of the same gesture at different speeds; phase names explain the correspondence.

All steps shown
IndexFast sequence phaseSlow sequence phaseSame-index problem
1StartStartAligned initially
2RaiseEarly raiseDifferent phase progress
3PeakRaisePeak paired with motion
4LowerPeakOpposite phase
Shape-based matchingPeak at fast3Peak at slow4Time warping can match similar phase

What this tells us: The goal is a sensible correspondence path, not changing the true physical timestamps. If timing delay is itself the target signal, warping it away may remove the evidence.

What information this representation preserves

  • Spatial alignment makes positions comparable across viewpoints or coordinate systems. Temporal alignment makes observations refer to the same event time.
  • Matching the same array index assumes equivalent timing. Dynamic time warping can align similar sequence shapes performed at different speeds.
  • Feature alignment learns a shared representation for corresponding content, such as image–text pairs; it does not synchronize physical sensor clocks.
  • Correspondence must be meaningful before alignment. Forcing unrelated recordings into a numerical match creates false evidence rather than useful fusion.
Implementation steps and their purpose
  1. Spatial: transform locations into a common coordinate frame.
  2. Temporal: place observations on a common time axis.
  3. When similar sequences run at different speeds, consider dynamic time warping.
  4. Feature alignment: map matching modalities to comparable learned representations.
  5. Verify correspondence before using combined evidence.

Prepare the data and validate the representation

Data, components and application

  • Clock offset → synchronize timestamps → avoids false cross-sensor relationships.
  • Different coordinate frames → calibrate transformations → same position otherwise has different values.
  • Unrelated sequences forced together → validate event identity → numerical alignment does not prove semantic correspondence.

How to evaluate it

Check known corresponding points/events, alignment error and downstream task improvement.

Build the answer in this order

  1. What differs between streams?
  2. Spatial/time/feature correction.
  3. Validate correspondence.
  4. Evaluate fused task.

Choose the representation from the task

Use before combining sensors with different clocks, viewpoints, sampling rates or representation spaces.

Scenario cueSuitable choiceWhy it fits
Different camera coordinate framesSpatial calibration/transformationSame object position must share a common reference.
Same gesture at different speedCompare DTW alignmentMatches similar shapes beyond identical indices.

Information loss, noise and failure cases

What you observeWhy it happensWhat to changeWhy that helps
False cross-sensor relationshipClock offset or wrong case pairedValidate timestamps/event identifiersDifferent events must not be combined.
Useful delay disappearsAlignment removes target timing differencePreserve original timing and choose task-aware methodNot every time difference is nuisance.
Common wrong answers and the exact correction
  • Temporal alignment and spatial alignment solve different mismatches.
  • CLIP-style feature alignment is not a clock-synchronization method.

An answer you could write

  • I first establish that both streams describe the same event, then align time or coordinates as needed.
  • DTW is appropriate when similar patterns differ in speed, provided timing difference is not the target.
  • I verify corresponding landmarks and downstream benefit rather than assuming numerical alignment is correct.

C103

End-to-end sense-making design

End-to-end sense making connects raw sensor data to recognized entities, relationships, context, knowledge and an action.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

What must the system deliver?

Use for scenario questions asking for a complete architecture rather than only a model name.

Scenario cueSuitable choiceWhy it fits
Question asks full architectureShow responsibilities and labelled arrowsDemonstrates the complete problem-solving chain.
Question asks subsystem relationship onlyUse clear black boxes and intermediate outputsAvoids unnecessary internal detail.

What each component receives and produces

  • An end-to-end architecture must explain how raw readings become recognized entities, relations, context and a useful action. Naming a neural network does not fill missing functions.
  • A feedback loop uses new sensor observations after an action to update the current state; it is not necessarily online model training.
  • The knowledge component stores reusable relationships or constraints, while the current state stores the presently observed scene and system condition.
  • Evaluation should trace errors through the chain: incorrect sensing can look like a reasoning failure, while correct recognition can still feed an unsuitable action policy.
Implementation steps and their purpose
  1. Define the user goal and required decision.
  2. Specify sensors, signals and data preparation.
  3. Choose features/representation and recognition task.
  4. Combine entity relationships with context/domain knowledge.
  5. Show planning and the action/output.
  6. Return observations/feedback where the task is a continuing loop.

What this tells us: A lane label alone does not state whether the car is drifting. The required relation and change over time must exist before the warning decision is justified.

Data, implementation and validation

Data, components and application

  • Model output unrelated to user need → connect each stage to the required action → exposes missing functions.
  • Sensors disagree → align and assess quality → avoids unsupported combined conclusions.
  • Good classifier but unusable system → evaluate timing and error consequences → complete-system usefulness matters.

How to evaluate it

Check sensing, recognition and decision errors separately, then task success, latency, robustness and action consequences.

Build the answer in this order

  1. Scenario goal.
  2. Inputs → processing → knowledge.
  3. Decision → action/feedback.
  4. Evaluate complete loop.

  • An architecture needs responsibilities and labelled arrows, not just input → AI → output.
  • Learning/training need not happen in every runtime loop.

An answer you could write

  • The sensors capture camera/motion data, recognition estimates lane position and drift, and decision logic selects a warning.
  • The audible warning is the action; later observations update the state.
  • I evaluate each stage and end-to-end warning usefulness, delay and false/missed alerts.
