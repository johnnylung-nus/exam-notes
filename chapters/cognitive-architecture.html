C059

Cognitive-system architecture

A cognitive system turns observations into useful actions using perception, memory and reasoning. Learning is a separate function; applying a fixed rule is not learning.

How it worksWorked exampleChoose & designProblems & fixesExam answer

1. What problem does it solve?

Use this to design a complete scenario solution and explain what each component contributes.

Scenario cueSuitable choiceWhy it fits
Question requests subsystem relationshipShow App → Web with labelled signInternal algorithms are unnecessary unless requested.
Question requests internal designAdd case record, knowledge base and reasoning componentThe examiner needs responsibilities and actual structures.

2. How it works — what happens and why

  • Perception transforms measurements into usable facts; reasoning needs those facts plus stored knowledge, rather than guessing directly from a raw image.
  • A runtime case record holds the present observations. A knowledge base holds reusable definitions, relationships and rules applied to many cases.
  • Reasoning selects a conclusion; planning identifies what to do; action delivers or executes it. The boxes should not all be labelled “AI”.
  • Learning changes a model or knowledge from experience. Applying an unchanged formula to another image changes the case result, not the formula.
Implementation steps and their purpose
  1. State the user problem and required output.
  2. Name the inputs and perception process.
  3. Show what information enters memory or the knowledge base.
  4. Connect reasoning to a decision and action.
  5. Show feedback or learning only where the case supports it.

4. Design the solution and check the result

Data, components and application

  • Vague AI box → label inputs, outputs and responsibility → makes the design assessable.
  • Invented training → distinguish building a model from using a fixed rule → preserves case evidence.

How to evaluate it

Check each required output, component errors, response time and the consequences of a wrong action.

Build the answer in this order

  1. User need → required functions.
  2. Data → perception output.
  3. Knowledge → reasoning/action.
  4. Test the whole flow.

5. Diagnose the proposed model — change and justify

Common wrong answers and the exact correction
  • A function is a verb/process; raw data and information are outputs.
  • Not every deployed cognitive system learns during operation.

6. Turn understanding into an exam answer

  • The App recognizes pupil/iris regions, counts their pixels and calculates relative pupil sizes before applying the supplied rule.
  • The current case record holds measurements; the knowledge base holds reusable definitions and comparison rules.
  • Applying a fixed rule is reasoning/inference, not learning a new rule during the consultation.

7. Where this is tested in the sample papers

ISY5001 Q2(a) — Stakeholder pain points

What the question requires

  1. Name the stakeholder.
  2. State a difficulty supported by the case.
  3. Connect it to the system’s intended benefit.

Proposed answer points

  • Primary doctors may lack specialist eye knowledge when choosing diagnosis/referral urgency.
  • Patients may face extra referral steps or delayed specialist assessment.

Avoid: Avoid invented numerical shortages or generic “AI is faster” claims.

ISY5001 Q2(i) — Patient self-service: benefits, risks and role boundaries

What the question requires

  1. State a position on removing the primary doctor.
  2. Acknowledge the convenience benefit.
  3. Explain a case-specific risk and a safer scope.

Proposed answer points

  • A patient-facing information/capture function could improve convenience, but removing the doctor is not justified by the presented diagnostic/triage support case.
  • Capture errors, incomplete context and delayed escalation are possible risks; retain clinician assessment for the clinical decision.

Avoid: Do not claim all cognitive systems always require a doctor; argue from this system’s intended users and risks.

C078

Multimodal cognition

Multimodal cognition combines different input types and knowledge to interpret a situation more completely than one modality alone.

How it worksWorked exampleChoose & designProblems & fixes

1. What problem does it solve?

Use when images, speech, sensor measurements or case details provide complementary evidence.

Scenario cueSuitable choiceWhy it fits
Existing App produces interpreted signCombine at the sign/case levelReuses the subsystem without inventing shared raw representations.
Raw multimodal learning explicitly requestedDesign aligned feature representationsRequires suitable paired data and a clear task objective.

2. How it works — what happens and why

  • Different modalities can provide complementary evidence, but combination must preserve who/what/time each observation refers to.
  • A visual sign and a patient detail are not interchangeable raw inputs: each needs its own acquisition, validation and representation.
  • Combining evidence can happen through intermediate features or through interpreted outputs. The architecture should say which rather than simply draw many arrows into AI.
  • A missing modality should create a defined incomplete-evidence condition, not a fabricated substitute measurement.
Implementation steps and their purpose
  1. State what each input contributes.
  2. Process each modality into useful information.
  3. Align observations belonging to the same event.
  4. Combine representations or decisions.
  5. Apply knowledge to the combined evidence.
  6. Return a decision with uncertainty and a defined action.

3. Trace multimodal evidence without merging unrelated records

What this tells us: The App’s output becomes one Web input; it does not replace the other case details. This is a reason to label intermediate outputs precisely.

4. Design the solution and check the result

Data, components and application

  • Inputs refer to different times/people → align records → prevents invalid combinations.
  • One input unreliable → represent quality or seek another reading → extra modalities are not automatically helpful.
  • Black-box fusion → label what passes between components → makes the design explainable.

How to evaluate it

Compare with single-input baselines, test missing/noisy inputs and check full task correctness.

Build the answer in this order

  1. Need for multiple evidence types.
  2. Per-input processing.
  3. Alignment and combination.
  4. Decision and evaluation.

5. Diagnose the proposed model — change and justify

What you observeWhy it happensWhat to changeWhy that helps
Correct components, wrong patient resultInputs joined without case identityUse explicit case/session linkageUnrelated observations must not be fused.
All inputs assumed reliableNo quality handlingTrack uncertainty or request recaptureOne poor stream can corrupt the combined judgement.
Common wrong answers and the exact correction
  • Multiple sensors of one type are not necessarily different modalities.
  • Fusion does not guarantee improvement.

6. Turn understanding into an exam answer

  • The App’s visual sign becomes one Web input alongside doctor-entered patient details and other signs.
  • Associate all observations with the same case/session before applying reusable knowledge.
  • Keep diagnostic possibilities, urgency and recommended action as distinct output fields, and represent missing or uncertain evidence explicitly.
