C029

Reasoning-system architecture

A reasoning-system architecture connects inputs, structured knowledge, an inference procedure, outputs and validation. Naming “AI” alone does not explain how a decision is made.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

What must the system deliver?

Use when asked to design a complete system and show component responsibilities, interfaces or knowledge structures.

Scenario cueSuitable choiceWhy it fits
Question asks subsystem relationshipBlack-box App→Web flowDo not invent internals absent from the prompt
Question asks detailed knowledge designFrame/rule records plus procedureShow how stored knowledge actually produces outputs

What each component receives and produces

  • Architecture explains responsibilities and information movement. A box labelled inference engine must name a procedure, such as forward chaining or case adaptation, while its KB must show what knowledge is stored. Input→AI→answer cannot answer a question explicitly asking for processes and data structures.
  • The requested granularity matters. Sample Q2(c) asks about the relationship between App and Web, so show the App’s RAPD output feeding the Web alongside doctor-entered findings. Q2(d) asks internal design, so now patient facts, knowledge structures, rule matching and result explanations belong in the diagram.
  • A coherent design should handle insufficient and contradictory evidence. Use present/absent/unknown for findings, request relevant missing information and avoid forcing one diagnosis when only a differential is supported. Diagnosis, urgency and recommended action are separate outputs but can be derived by one engine with different rule types.
Implementation steps and their purpose
  1. Extract user need, inputs and required outputs from the case.
  2. Choose a representation matched to available knowledge.
  3. Name the actual inference procedure.
  4. Draw component boxes with labelled data arrows.
  5. Add missing/conflict handling, explanations and validation.

Data, implementation and validation

Data, components and application

  • Overcomplicated design → one coherent procedure first → separate outputs do not require separate models.
  • Unclear arrows → label information passed → architecture must show how components cooperate.

How to evaluate it

Check requirement coverage, representative cases, data structures, explanations and failure handling. State assumptions instead of inventing case facts.

Build the answer in this order

  1. Read required scope.
  2. Specify components and data.
  3. Explain processing.
  4. Validate outputs and limitations.

  • Knowledge base is storage/representation; inference engine is the procedure.

An answer you could write

  • “Doctor findings and RAPD enter validated patient facts; a forward-chaining engine uses disease frames and typed rules to produce supported diagnoses, urgency and action.”
  • “Unknown findings trigger relevant follow-up; conflicting rules are resolved by declared priority or flagged for review.”

ISY5001 Q2(d) — Knowledge-based internal architecture and data structures

What the question requires

  1. Validate inputs; distinguish present, absent and unknown.
  2. Store patient facts in working memory.
  3. Represent specialist knowledge as disease frames and diagnostic/triage/action rules.
  4. Match/fire rules; display conclusions and explanations.

Proposed answer points

  • Patient facts → inference engine ← knowledge base → diagnosis candidates + urgency + action.
  • Show structures: patient fact fields; disease frame IDs; rules with conditions, conclusions, priority and explanation. One engine can apply several rule types.
  • If evidence is missing/conflicting, request information or flag for doctor review. Clinical contents require specialist validation.

Avoid: A box labelled “AI” is insufficient. A KB stores knowledge; an inference engine names the procedure using it. Softmax scores do not automatically encode urgency.

Avoid: Do not claim every lookup table can return only one diagnosis or cannot represent combinations. If criticizing unweighted tick counts, explicitly state that assumption.

C030

Rules + ML integration

Rules plus ML separates prediction from policy. ML estimates an outcome; rules use that estimate and other facts to choose permitted actions.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

What must the system deliver?

Use when learned patterns help prediction but business, safety or operational constraints must determine decisions.

Scenario cueSuitable choiceWhy it fits
Noisy patterns plus strict operational constraintsML predictor followed by rulesEach component addresses a distinct requirement
Only a simple exact eligibility ruleRule-only system may sufficeA trained model adds no justified information

What each component receives and produces

  • Prediction estimates an unknown outcome; policy decides an action under constraints. A fraud score can inform a review decision but does not itself encode daily limits, exceptions or the cost of blocking a legitimate transaction. Separating these roles makes both model errors and policy errors diagnosable.
  • The rules may consume raw case facts as well as the model score. For example, a hard transaction limit does not need to be inferred from a probability, and an account-compromise flag can trigger action even when a model score is modest. The interface should carry the needed facts explicitly.
  • Evaluation must cover both layers. A well-ranked risk model can still produce excessive review workload under a poor threshold; a correctly implemented threshold can still fail if the scores drift. Record score/model version, relevant facts, fired policy and final action so a changed decision can be explained.
Implementation steps and their purpose
  1. Define the ML prediction target and input data.
  2. Train/evaluate the predictor.
  3. Pass prediction and relevant facts to the rule engine.
  4. Apply thresholds, exceptions and constraints.
  5. Return action with prediction evidence and fired-rule explanation.

Illustrative score-plus-policy decision table

Worked study example: Policy is invented to demonstrate the lecture fraud pattern: over-limit transactions are blocked; otherwise score≥0.8 goes to review, and lower scores pass ordinary checks.

All steps shown
TransactionScoreHard limit exceeded?Policy action
A0.91NoReview; do not equate score with certainty
B0.20YesBlock by hard-limit rule
C0.50NoPass ordinary checks under this policy
D0.85No, but verified exceptionApply documented exception/review rule

What this tells us: B demonstrates why raw constraints cannot be replaced by the learned score. D shows that exception handling must be part of policy, not a hidden adjustment to the model output.

Data, implementation and validation

Data, components and application

  • Score treated as action → define policy mapping → probability alone does not encode allowed behaviour.
  • Stale rules/model → monitor both → either part can fail independently.

How to evaluate it

Evaluate prediction quality separately from decision outcomes, constraint violations and review workload. Test threshold boundaries and conflicts.

Build the answer in this order

  1. Separate prediction from decision.
  2. Draw labelled flow.
  3. State rule inputs and policy.
  4. Validate model and final action.

Component failure → system consequence → remedy

What you observeWhy it happensWhat to changeWhy that helps
Great prediction metric, too many reviewsThreshold/action policy misaligned with capacityTune decision policy using costs and workloadPrediction quality and operational utility differ
Low score overrides a mandatory constraintRules depend only on model outputPass raw constraint facts directlyHard requirements should remain enforceable
Common wrong answers and the exact correction
  • High confidence is not automatically high urgency.
  • Hybrid design needs a reason for each component, not a catalogue of algorithms.

An answer you could write

  • “The model predicts fraud risk; the rule engine combines that score with transaction limits and account facts to choose approve/review/reject.”
  • “I evaluate model discrimination separately from false blocks, missed fraud and review volume, and log the policy supporting each action.”

C031

Knowledge graph + LLM integration

A KG–LLM workflow uses structured graph facts to support natural-language answers. The language model can interpret a question and explain retrieved relationships.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

What must the system deliver?

Useful when users ask questions requiring connected entity knowledge, but need readable answers.

Scenario cueSuitable choiceWhy it fits
Answer requires entity relationships plus readable explanationKG lookup then LLM synthesisStructured conditions remain checkable
Answer is an exact stored approved FAQ responseDirect retrieval may sufficeGeneration can add unsupported material unnecessarily

What each component receives and produces

  • KG–LLM integration assigns structured lookup and language generation different jobs. The graph query identifies connected entities under explicit conditions; the LLM interprets the user’s wording and explains retrieved results. It should not fill a missing approved-drug fact from a plausible association in its language memory.
  • Entity linking and query construction are failure points before generation. A synonym, gene variant or relation direction can change the intended query. A controlled query template or validation of generated queries helps ensure the system asks the graph the same question the user asked.
  • Provenance must survive the interface. Retrieved facts should include source and freshness where available; extracted or predicted links need an evidence status. Otherwise a fluent explanation can make a tentative graph-completion suggestion look like a verified database assertion. An empty graph answer should trigger a qualified response rather than fabricated completeness.
Implementation steps and their purpose
  1. Identify entities and relations in the question.
  2. Construct a controlled graph query.
  3. Retrieve relevant facts/paths.
  4. Give retrieved evidence to the language model.
  5. Generate a concise answer with supporting facts and check it against evidence.

Illustrative structured query versus fluent assumption

Worked study example: Question: “Which approved drugs target gene G?” Candidate records are invented to explain conjunction and evidence handling.

What this tells us: The language answer should name A with supporting relations. It can state that other evidence is incomplete, but should not turn B’s trial participation or C’s predicted link into an approved verified answer.

Data, implementation and validation

Data, components and application

  • Wrong entity/query → validate query and entity mapping → fluent language can hide retrieval errors.
  • Incomplete KG → state missing evidence → graph grounding cannot create missing verified facts.

How to evaluate it

Evaluate query correctness, retrieved evidence coverage and whether every answer claim is supported. Check source freshness.

Build the answer in this order

  1. State required relationships.
  2. Show query/retrieval step.
  3. Explain LLM role.
  4. Validate evidence and final answer.

Component failure → system consequence → remedy

What you observeWhy it happensWhat to changeWhy that helps
Correct graph but wrong entity selectedAmbiguous user term/entity linkingResolve identifier or ask clarificationPrecise lookup cannot repair the wrong starting entity
Answer invents approvalGeneration exceeds retrieved evidenceRestrict claims and retain sources/statusFluent wording is not verification
Common wrong answers and the exact correction
  • A language model does not automatically make graph facts trustworthy.
  • Predicted/extracted links need provenance and validation.

An answer you could write

  • “I resolve gene G, query drugs with both a verified targets edge and the required approval status, then generate a sourced explanation from those records.”
  • “Predicted links and trial-only candidates remain labelled and are not presented as verified approved matches.”

C032

Retrieval-augmented generation

Retrieval-augmented generation retrieves relevant external material and supplies it to an LLM before it generates an answer. It can improve grounding and freshness.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Illustrative policy retrieval failure analysis

Worked study example: Question asks whether overseas remote work is allowed. Policy fragments are invented to show why evidence selection and synthesis must be checked separately.

All steps shown
Retrieved materialGenerator behaviourResultRepair
Only “remote work permitted”Faithfully says yesMissing overseas conditionRetrieve surrounding exception
Overseas clause requires approvalStates approval requirementGrounded answerCite clause and scope
Correct clauseAdds “automatic approval after 7 days”Unsupported generationRemove invented claim
No relevant clauseConfident yes/noNo evidenceClarify or report unavailable answer

What this tells us: A useful system can explain whether failure came from retrieval coverage or generation faithfulness. Retrieval reduces hallucination risk but does not guarantee correctness.

What information this representation preserves

  • RAG has two accuracy problems: finding the right evidence and generating an answer that stays faithful to it. A generator can be perfectly faithful to an irrelevant passage and still answer the user incorrectly. Evaluating only fluent final wording hides the retrieval failure.
  • The document index should preserve source identity and enough context to interpret exceptions. A chunk containing “remote work permitted” may be misleading if the adjacent condition requires country approval. Chunking and retrieval must retain the rule and its applicable scope, rather than merely maximise keyword matches.
  • In sample Q1(b), returning the approved answer linked to the closest stored question is semantic FAQ retrieval. It becomes retrieval-augmented generation only if an LLM synthesises a response from retrieved evidence. Do not add that generation step merely to sound sophisticated when exact approved answers already meet the task.
Implementation steps and their purpose
  1. Prepare approved documents with source identifiers.
  2. Split/index searchable content using suitable text or embeddings.
  3. Retrieve relevant passages for the user query.
  4. Provide passages and the question to the LLM.
  5. Return an evidence-grounded answer or clarify when retrieval is insufficient.

Prepare the data and validate the representation

Data, components and application

  • Wrong passage → improve retrieval/chunking → generation cannot compensate for absent evidence.
  • Unsupported additions → constrain answer to evidence and verify → RAG reduces but does not eliminate hallucination.

How to evaluate it

Check retrieval relevance/coverage and answer faithfulness separately. Test unanswered questions and stale/conflicting policies.

Build the answer in this order

  1. Identify knowledge source.
  2. Describe retrieval.
  3. Describe grounded generation.
  4. Add verification/fallback.

Choose the representation from the task

Choose when a language interface must answer from an approved or changing document collection.

Scenario cueSuitable choiceWhy it fits
Changing organisational documents and natural-language questionsRAGEvidence can be retrieved at runtime without retraining the language model
Approved FAQ pairs with exact response requiredSemantic retrieval and linked answerThis simpler design matches sample Q1(b)

Information loss, noise and failure cases

What you observeWhy it happensWhat to changeWhy that helps
Answer omits exceptionChunks/retrieval lose policy contextRetrieve linked context and validate scopeExceptions determine applicability
Answer cites a source but adds unsupported detailCitation presence mistaken for faithfulnessCheck each claim against evidenceA source link does not support every sentence
Common wrong answers and the exact correction
  • Semantic FAQ retrieval returning a stored answer is not automatically RAG.
  • Retrieval does not retrain the LLM.

An answer you could write

  • “I index approved policy passages with source IDs, retrieve the relevant rule plus exceptions, and generate only claims supported by those passages.”
  • “When retrieval is insufficient, I clarify or report the gap; the FAQ task may instead return its stored approved answer directly.”

C033

Agentic orchestration

Agentic orchestration coordinates planning, tools, memory and feedback over multiple steps. An agent chooses actions, observes their results and adjusts its plan.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

What must the system deliver?

Useful when a task needs several operations or external tools, rather than one prediction or answer.

Scenario cueSuitable choiceWhy it fits
Next step depends on tool resultsAgentic orchestrationA controller can revise sequence and tool choice
Stable known steps with no branchingFixed workflowSimpler orchestration is easier to test and explain

What each component receives and produces

  • An agentic system chooses the next operation from the current task state. The important loop is action→observation→revised plan, not an ornate list of tools. A fixed workflow is often enough if the same steps always apply; agentic choice helps when later steps depend on uncertain earlier results.
  • Tool outputs are observations to inspect, not guaranteed completion. A flight search may return an option outside dates; a calculation may use incompatible currencies. The controller must validate results against the goal and constraints before using them as premises for the next step.
  • Memory should record useful state such as confirmed constraints, completed actions and evidence, preventing repeated work. Limits on retries, cost and action scope prevent an unsuccessful tool loop. Consequential external actions should be separated from planning: a proposed itinerary does not by itself mean a ticket has been booked.
Implementation steps and their purpose
  1. Define goal, constraints and available tools.
  2. Break the task into useful substeps.
  3. Select a tool with explicit inputs.
  4. Inspect returned observations and update task state.
  5. Validate completion or revise the plan; enforce a stopping limit.

Illustrative adaptive travel-assistant trace

Worked study example: Goal: propose a three-day visit within a stated budget and dates. This follows the lecture travel-agent pattern with invented observations.

All steps shown
StepObservationNext justified action
Search flightsOnly late arrival fits budgetCheck whether first meeting time remains feasible
Check meeting scheduleMorning meeting conflictsSearch earlier arrival or revise proposal
Calculate combined costHotel pushes total over budgetTry lower-cost eligible hotel
Recheck constraintsDates, arrival and total now fitReturn evidenced proposal
Search still failsNo feasible option foundReport constraint conflict, not fictitious booking

What this tells us: The plan changes because of checked observations. The system should retain the failed budget calculation so it does not repeatedly propose the same infeasible combination.

Data, implementation and validation

Data, components and application

  • Tool error/loop → check results and limit retries → repeated actions are not progress.
  • Unsupported plan → validate dates, resources and constraints → plausible text is not an executable solution.

How to evaluate it

Evaluate task completion, constraint satisfaction, tool errors, cost and traceable evidence. Compare with a simpler fixed workflow.

Build the answer in this order

  1. Explain why multiple steps are needed.
  2. Draw plan–tool–observation loop.
  3. State memory/constraints.
  4. Show validation and stopping.

Component failure → system consequence → remedy

What you observeWhy it happensWhat to changeWhy that helps
Repeated identical searchesTask state not retainedRecord completed attempts and limitsThe controller must recognise non-progress
Plan looks plausible but violates budgetOutputs accepted without validationRecalculate totals and enforce constraintsLanguage fluency cannot certify feasibility
Common wrong answers and the exact correction
  • More agents are not automatically better.
  • Tool outputs are observations to check, not guaranteed truth.

An answer you could write

  • “The controller searches options, validates the observation against dates/budget, and revises the next tool action when a constraint fails.”
  • “It records attempts, stops after bounded non-progress, and returns a proposal with evidence rather than claiming an unperformed booking.”

C058

Symbolic / connectionist / hybrid AI

Symbolic AI uses explicit representations/rules; connectionist AI learns distributed representations in neural networks. Hybrid systems combine complementary capabilities.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

Choose from the scenario

Use when a question asks which AI approach fits structured expertise, noisy high-volume data or a system needing both.

Scenario cueSuitable choiceWhy it fits
Explicit validated policies, limited training labelsSymbolic designRules can encode available expertise directly
Noisy visual recognition plus strict decisionsJustified learned perception plus symbolic constraintsDifferent components address different evidence types

Sample-aligned supported facts versus proposed design

Worked study example: Reasoned study distinctions. The scenario establishes App measurement and Web support; proposed frame/rule internals belong to Q2(d) design, not factual description of deployed internals.

All steps shown
StatementEvidence statusExam treatment
App measures eye responses and yields RAPD signCase-described functionUse in subsystem diagram
RAPD sign becomes Web inputSupported information flowShow labelled App→Web arrow
Every stage is a trained neural networkNot establishedDo not assert
Web uses patient frames plus rulesCoherent proposed Q2(d) designLabel proposal and justify
Exact lecturer hybrid taxonomy labelUnconfirmed in discussionDescribe serial relationship without false certainty

What this tells us: The tutor should not add an exotic model merely to satisfy a fashionable label. Use the smallest coherent architecture that addresses the requested inputs, knowledge, inference and outputs.

The distinction that changes the answer

  • The useful distinction is where knowledge comes from and how it is used. Symbolic systems apply explicit facts, rules and structured relationships; connectionist systems learn distributed representations from data. Neither label alone establishes reliability or suitability for the scenario.
  • A hybrid should connect complementary responsibilities. Perception from images may benefit from a learned model; explicit domain constraints can govern allowed decisions; frames can organise facts and rules can explain consequences. However, a hypothetical useful architecture must not be presented as what the sample case actually implements. The App’s described measurement/formula processing is not evidence of a trained classifier.
  • Exact taxonomy labels and dataflow descriptions should also be separated. Sample Q2(c) supports App output feeding Web input, which can be described as sequential/serial flow; the lecturer’s exact hybrid-type label remains unconfirmed. An honest design answer can show the supported flow while identifying that naming uncertainty.

What would make the choice wrong?

What you observeWhy it happensWhat to changeWhy that helps
Hybrid diagram becomes a catalogue of AI namesNo assigned responsibilitiesRemove unsupported components and label dataflowMore techniques do not make a coherent system
Proposed model described as case factDesign assumption not separatedMark proposal and source-supported behaviour distinctlyExam answers must respect scenario evidence
Common wrong answers and the exact correction
  • Not every reasoning system requires every AI technique.
  • Separate subsystem responsibilities do not prove multiple neural networks.

Apply the distinction

Data, components and application

  • Rule maintenance → expert updates/tests → hand-built knowledge can become stale.
  • Neural opacity/bias → validation, explanations and constraints → learnt patterns need system-level checks.

How to evaluate it

Compare task success, explanation quality, knowledge/data requirements and maintenance. The simplest justified design may be sufficient.

Build the answer in this order

  1. Identify task/evidence.
  2. Choose paradigm with reason.
  3. Show hybrid interface if needed.
  4. Explain limits and validation.

An answer you could write

  • “The supported relationship is serial: the App’s RAPD output becomes one Web input alongside doctor-entered findings.”
  • “For Q2(d), I propose patient frames plus specialist rules and forward chaining; I do not claim the case already contains a neural classifier or a confirmed taxonomy label.”
