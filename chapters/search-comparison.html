Exam wording: Search = Reasoning Engine

In this lecture, search is the reasoning engine that explores possible states and actions to reach a goal, guided by an evaluation function.

State space + Actions + Goal + Evaluation → Search / Reasoning Engine. Recognise this wording when a scenario asks how the system chooses its next action or finds a solution.

Day 1: PDF p.71 / slide 76. This is the framing in the search chapter; reasoning can also use other methods.

State space + Actions + Goal + Evaluation

PartMeaningQuestion to identify it
State / state spaceA state describes one situation. State space is the set of possible situations the search can consider.What is the current situation, and what other situations are possible?
ActionsAllowed moves that change one state into another.What can the system do next?
GoalThe required outcome; the goal test checks whether it has been reached.What counts as success?

Search = Reasoning Engine: use allowed actions to explore possible states, evaluate the alternatives, and seek a state satisfying the goal.

Goal versus evaluation: reaching the goal answers “Have we succeeded?” Evaluation answers “How good or promising is this option?” Reaching a goal does not automatically mean finding the best solution.

For the search methods discussed: Dijkstra evaluates with g; Hill Climbing with h; A* with g+h. These guide selection; the actual completed route cost is g at the goal.

C001

Search problem formulation

Search means exploring possible states and actions to reach a goal. The representation determines what solutions the algorithm can find.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Illustrative route state: location is not enough

Worked study example: A courier starts at A, must visit B and C, and return to A. We compare two partial routes arriving at B. These are invented values used to explain state design.

All steps shown
Partial routeCorrect state informationCan go straight home?
A→BAt B; visited A,B; C unservedNo: C remains required
A→C→BAt B; visited A,B,CYes, if return edge allowed
A→B→ABack at A; C unservedNot a goal despite returning
A→C→B→ABack at A; all servedFeasible; compare total cost

What this tells us: A visited-set is necessary because the same current location does not imply the same remaining task. After feasibility is established, compare complete-route costs. A heuristic cannot repair a representation that forgot a required customer.

What information this representation preserves

  • A search state must retain everything that changes future legal actions. For a visit-each-city route, “current city” alone is insufficient: two arrivals at the same city can have different unvisited destinations. They are different planning states even though they share a location.
  • The goal test answers whether a candidate is acceptable; the objective compares acceptable candidates. “Every customer served” is a goal/constraint, while minimum distance ranks feasible routes. Mixing them lets an apparently cheap solution win by skipping required work.
  • An action changes the state and has a cost. Costs must represent the exam objective: distance, time and fare are different quantities. State updates must also update resources, visited locations or deadlines, because later action feasibility depends on these values.
Implementation steps and their purpose
  1. Define what one state contains.
  2. Specify the initial state and valid actions.
  3. State the goal test and hard constraints.
  4. Assign action costs and the objective.
  5. Choose a search method that matches costs, memory and heuristic availability.

Prepare the data and validate the representation

Data, components and application

  • Missing state information → include visited cities/resources → legality depends on history.
  • Conflicting objectives → state priority or weights → cheapest and fastest need not coincide.

How to evaluate it

Check that the final path reaches the goal, obeys constraints and has correctly summed cost. Compare search effort and solution quality.

Build the answer in this order

  1. Identify state and goal.
  2. Define actions, constraints and costs.
  3. Justify algorithm.
  4. Trace and check result.

Choose the representation from the task

Use when the question asks for a route, arrangement or sequence satisfying requirements.

C002

Breadth-first search

Breadth-first search explores all states at one depth before going deeper. It uses a queue: add new children at the end.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Illustrative BFS queue trace

Worked study example: A has children B,C; B has D,E; C has goal G. Expand children left to right. Every edge costs one unit.

All steps shown
RemovedQueue after adding childrenReason
AB,CFirst level waits
BC,D,EC was discovered before D,E
CD,E,GAll children append to end
D then EGEarlier depth-two nodes go first
GEmptyParent chain gives A→C→G

What this tells us: The solution costs two steps even though the expansion trace inspected five other nodes. With unequal fares, this guarantee applies only to edge count; a two-edge route could cost more than a three-edge route.

Read the relationships and follow the choices

  • BFS keeps earlier discoveries ahead of later discoveries. Appending children to the queue means every depth-one node is removed before depth-two nodes. This is why it finds a minimum-number-of-actions route when all action costs are equal, rather than because it estimates distance to the goal.
  • The frontier is the waiting list, not the route already travelled. Parent pointers reconstruct the actual solution after a goal is found; the expansion order may include nodes belonging to several different branches and is usually not itself a valid route.
  • In a graph, repeated-state handling prevents cycles from recreating the same work. With a proper state definition and unit-cost edges, recording a discovered state prevents later longer routes to that same state from entering the queue. Memory can still grow rapidly because an entire wide level waits together.
Implementation steps and their purpose
  1. Put the start in the frontier queue.
  2. Remove the oldest queued node and check the goal.
  3. Append its valid unvisited children.
  4. Record parents to reconstruct the path.
  5. Repeat until success or the queue is empty.

Choose the method from the problem

Useful for fewest-step solutions when each action has the same cost, or finding all nodes within a limited number of hops.

Scenario cueSuitable choiceWhy it fits
Unweighted minimum hopsBFSDepth corresponds to path cost
Fare differs by edgeUniform-cost searchQueue order does not compare accumulated fare

Implement it and test the outcome

Data, components and application

  • Cycles → keep visited states → prevent repeated expansion.
  • Large branching → frontier grows rapidly → consider cost/heuristic search when suitable.

How to evaluate it

Verify the queue and expansion order. On equal-cost edges, the first reached goal has minimum steps; weighted edges require another criterion.

Build the answer in this order

  1. Check equal step costs.
  2. Write frontier after each expansion.
  3. Apply stated child order.
  4. Return path, not just visiting order.

An answer you could write

  • All edges in this example cost one, so BFS finds a minimum-step route by removing the oldest frontier node and appending new children.
  • The expansion order is A,B,C,D,E,G, but the returned parent path is A→C→G, costing two steps.

C003

Depth-first search

Depth-first search follows one branch deeply before returning to alternatives. New children go at the front of the frontier, giving stack-like behaviour.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Illustrative DFS with a failed branch

Worked study example: A has B,C; B has D,E; C has goal G. Visit the left child first. D and E are dead ends.

All steps shown
ActionActive routeUnexplored alternative
Descend A→B→DA,B,DE and C
D fails; backtrackA,BE and C
Try E; E failsA,B,EC
Return to A; try CA,CG below C
Reach GA,C,GSolution found

What this tells us: The route A→C→G has two edges, but DFS explored a complete wrong branch first. A different tree could give DFS a much longer first solution; reaching a goal provides no shortest-path proof.

Read the relationships and follow the choices

  • DFS places the current branch’s children ahead of older alternatives, so it follows one branch before visiting siblings. Backtracking means returning to the most recent decision with an unexplored alternative; it does not mean randomly restarting from the root.
  • DFS can keep a relatively narrow active path, but a deep wrong branch delays an easy shallow goal. In an infinite tree it may never return. Graph cycle checks avoid repeated states, while a depth limit addresses unbounded depth; these solve different failure causes.
  • The stack order must match the question’s stated neighbour order. Pushing B then C onto an ordinary stack causes C to pop first, so implementations often push children in reverse order to obtain a left-to-right trace. An exam trace should state its convention rather than claim one universal sequence.
Implementation steps and their purpose
  1. Start with the initial node.
  2. Take the most recently added node.
  3. Check goal and generate children in the stated order.
  4. Explore deeper before siblings.
  5. Backtrack when a branch ends; track visited states or path cycles.

Choose the method from the problem

Useful for exploring a branch, enumerating paths or situations where keeping a broad frontier is expensive.

  • Deepest-first does not mean choosing the most promising heuristic.

Implement it and test the outcome

Data, components and application

  • Infinite branch → depth limit or suitable cycle control → ensure other branches can be considered.
  • Poor first branch → excessive search → use information or another strategy.

How to evaluate it

Check expansion/backtracking order and memory. DFS does not generally guarantee the shortest or cheapest solution.

Build the answer in this order

  1. Identify branching and goal.
  2. Apply stack order consistently.
  3. Show backtracking.
  4. Discuss completeness and cost limitations for this space.

An answer you could write

  • With left-first DFS, I explore A→B→D, backtrack to try E, then return to A and explore C→G.
  • The solution is A→C→G; the earlier visited D and E belong to failed branches, and DFS provides no general shortest-path guarantee.

Uniform-cost search / Dijkstra

Uniform-cost search, called Dijkstra in the route example, expands the frontier path with the lowest accumulated cost from the start. It uses no goal-distance estimate.

What this tells us: Accepting the first generated G would return cost 11. Updating B and G yields cost 3. Selection from the frontier, not mere appearance in it, is the decisive event.

Read the relationships and follow the choices

  • Uniform-cost search orders waiting paths by the entire cost already paid. A newly generated goal is only a candidate: a cheaper unfinished path may still lead to a better goal. The guarantee comes when the least-cost frontier path is removed, under nonnegative edge costs.
  • If a state is reached by a cheaper route, its best cost and predecessor must be updated. Otherwise the system can remember an expensive first discovery and incorrectly reject a later improvement. Frontier entries made obsolete by an update must be replaced or ignored when removed.
  • Dijkstra and BFS coincide when every edge has the same cost because accumulated cost then grows directly with depth. When costs differ, Dijkstra may deliberately choose more edges to obtain a lower total. It has no estimate of the destination’s remaining distance, so it may explore cheap but irrelevant directions.
Implementation steps and their purpose
  1. Set start cost to zero.
  2. Keep frontier entries ordered by total cost so far.
  3. Remove the lowest-cost entry.
  4. Relax each outgoing edge: update a state if this path is cheaper.
  5. Stop when the goal is selected from the frontier.

Choose the method from the problem

Choose when edge costs differ and the aim is the cheapest path with nonnegative edge costs.

How to evaluate it

Sum the returned path cost and compare alternatives. With equal edge costs it behaves like BFS; without a heuristic it may explore many nodes.

Build the answer in this order

  1. Identify weighted objective.
  2. Calculate cumulative costs.
  3. Update best paths.
  4. Select goal only when cheapest frontier entry.

An answer you could write

Why the calculation works

  • A* estimates the complete route through a waiting node: g is everything already paid from the start, h estimates the remaining journey, and f=g+h. The comparison is across all retained frontier entries. Moving into one branch does not erase promising alternatives from previous expansions.
  • An admissible h is a lower bound on the true remaining cost. A frontier f therefore bounds how cheaply a solution through that node could turn out. If a generated goal costs 450 but another waiting node has f=417, the unfinished route could still beat the goal and must be considered.
  • Graph duplicate handling matters as well as admissibility. If a cheaper route reaches an already expanded state, reopen it unless the implementation can rely on a consistent heuristic. A* is not simply “choose the child nearest the destination”; that would ignore g and potentially ignore the global frontier.
Implementation steps and their purpose
  1. Set cost so far g(start)=0; h is estimated remaining cost.
  2. Calculate f=g+h for every frontier entry.
  3. Expand the globally lowest f; keep unexpanded alternatives.
  4. For each child, add the edge to the parent g and update cheaper paths.
  5. Stop when the goal is selected as the lowest-f frontier entry.

Use the result and check it

Data, components and application

  • Stopping on goal generation → continue frontier comparison → another route may be cheaper.
  • Inconsistent heuristic → reopen improved states or require consistency → closed-state shortcuts can lose optimality.

How to evaluate it

Check cumulative g, correct h and all frontier f values. Optimality needs admissibility plus correct repeated-state handling.

Build the answer in this order

  1. Define g, h and f in words.
  2. Maintain frontier across branches.
  3. Update cheaper duplicate paths.
  4. Explain stopping and optimality conditions.

What this tells us: A single overestimate is enough to refute admissibility. Straight-line kilometres are a defensible road-distance bound, but cannot automatically estimate fares: a long subsidised trip can cost less than a short expensive one.

Why the calculation works

  • A heuristic is not a promise that the next move is good. It supplies an estimate of the best remaining cost from a state. To justify admissibility, show why the estimate can never exceed a real feasible route under the chosen cost definition; a few accurate examples are not a proof.
  • More informative lower bounds can prune exploration by giving larger estimates that remain safe. Zero is always a safe bound for nonnegative remaining costs, but contributes no directional information. Two bounds cannot be compared only by their numeric size if they estimate different units or use incompatible assumptions.
  • Consistency is a relationship between neighbouring estimates: the estimate before a move should not exceed that move’s cost plus the estimate afterwards. It supports settled-state graph-search behaviour. Admissibility alone concerns the cost to a goal; correct reopening can be needed when consistency is absent.
Implementation steps and their purpose
  1. Identify the actual objective and its units.
  2. Explain how the estimate relates to that objective.
  3. Check that the goal estimate is zero.
  4. Justify a lower bound, rather than checking only convenient examples.
  5. Use consistency or reopen improved states in graph search.

Use the result and check it

Data, components and application

  • Wrong units → align estimate with cost → kilometres cannot directly estimate fare.
  • Overestimation → revise lower bound → A* may otherwise choose a suboptimal goal.

How to evaluate it

Check estimates against known remaining costs; compare nodes expanded. Zero is admissible but gives no directional guidance and reduces A* to uniform-cost search.

Build the answer in this order

  1. State what cost is being estimated.
  2. Check lower-bound argument.
  3. Discuss informativeness.
  4. Connect conditions to algorithm guarantee.

The distinction that changes the answer

  • The deck calls its route procedure “Hill Climbing (Greedy Best First Search)” and describes selecting by h alone while discarding earlier alternatives, with backtracking at dead ends. Preserve the specific rule when tracing the lecture; do not silently replace it with a textbook global-frontier procedure.
  • The common weakness is that looking only at the remaining estimate ignores the price already paid. A destination can look close from a node reached through a costly detour. Therefore a low h justifies “looks near”, not “this whole route is cheapest”.
  • Conventional local hill climbing compares neighbouring candidates against the current solution and can stop at a local optimum or plateau. Global greedy best-first instead keeps waiting alternatives ordered by h. These retention/stopping rules produce different traces, so an exam answer must identify which variant is intended before discussing guarantees or repairs.

C008

Simulated annealing

Simulated annealing is an optimisation search that sometimes accepts a worse move, helping escape a local minimum. The chance of accepting worse moves decreases as temperature cools.

What this tells us: B was worse than A but enabled C. Greedy local improvement would reject B and remain at 10 in this neighbourhood. Annealing makes escape possible, not certain, and the final returned best must still satisfy hard constraints.

Read the relationships and follow the choices

  • Annealing changes the local-search acceptance rule. An improving neighbour is accepted, but a worse neighbour may also be accepted with probability governed by how much worse it is and the current temperature. Early exploration can therefore leave a basin that traps always-improve search.
  • As temperature decreases, worse moves become less likely, shifting effort from exploration toward refinement. Cooling too quickly removes that opportunity before the search has explored useful alternatives. Never cooling enough keeps discarding useful improvements in favour of random wandering.
  • The best solution encountered should be tracked separately from the current solution: accepting a worse current candidate need not erase a better earlier result. The supplied lecture briefly lists annealing as a local-minimum escape technique; this procedural explanation is study elaboration rather than a detailed taught numerical schedule.
Implementation steps and their purpose
  1. Define candidate solutions, allowed neighbours and objective.
  2. Start from a solution and a temperature schedule.
  3. Propose a random neighbour.
  4. Accept improvements; sometimes accept a worse move according to temperature and deterioration.
  5. Cool gradually, repeat and retain the best solution found.

Choose the method from the problem

Useful when the search/error landscape has local traps and always-improve local search can get stuck.
