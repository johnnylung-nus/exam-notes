C071

Audio sampling and coding

Sampling records audio amplitude at time intervals; quantization maps amplitude to discrete levels. They control different parts of the digital representation.

How it worksWorked exampleChoose & designProblems & fixes

1. What problem does it solve?

Use when choosing or diagnosing audio input formats for speech processing.

Scenario cueSuitable choiceWhy it fits
Model requires 16 kHz inputCorrectly resample valid audioMatches the time scale expected during training.
Quiet-sound quantization mattersConsider encoding/precision choicesThe lecture contrasts linear PCM and logarithmic coding.

2. How it works — what happens and why

  • Sampling rate controls how often amplitude is measured; bit depth controls how finely each measured amplitude is represented. Increasing one does not directly increase the other.
  • A speech model expects particular input properties. A recording labelled with the wrong rate can alter its apparent time/frequency scale.
  • Uncompressed PCM size depends on samples per second, bits per sample, channel count and duration. Compression changes storage representation, not the original captured evidence.
  • Upsampling can create intermediate values but cannot uniquely recover high-frequency information already lost through undersampling.
Implementation steps and their purpose
  1. Check the signal frequencies that need preservation.
  2. Choose an adequate sampling rate.
  3. Choose sample precision and encoding.
  4. Use the sample rate/format expected by the recognition model.
  5. Check the captured file before recognition.

3. What changes when the audio settings change?

4. Design the solution and check the result

Data, components and application

  • Undersampling → choose sufficient rate before capture → lost frequency detail cannot be restored merely by changing a file header.
  • Wrong input rate → correctly resample → matches model assumptions.
  • Low-amplitude distortion → consider suitable quantization/encoding → lecture contrasts PCM with logarithmic coding.

How to evaluate it

Listen/check for clipping and format errors, then compare speech-recognition quality on representative recordings.

Build the answer in this order

  1. Signal needs.
  2. Sampling rate versus amplitude precision.
  3. Model-compatible conversion.
  4. Test input and recognition.

6. Turn understanding into an exam answer

  • Sampling rate determines the number of time samples per second; bit depth determines amplitude precision.
  • A 16 kHz,16-bit,mono PCM recording needs 256,000 bits per second before overhead.
  • Match audio rate/format to the model and verify capture quality; resampling cannot restore information lost during original undersampling.

C072

Spectrogram and audio features

A spectrogram shows which frequencies are present over time. It is built by applying Fourier analysis to short signal windows.

How it worksWorked exampleChoose & designProblems & fixes

1. What problem does it solve?

Use when sound changes during an event; a whole-recording frequency summary would hide when changes happen.

Scenario cueSuitable choiceWhy it fits
Need repeated frequency content onlyWhole-window spectrumA simpler representation may suffice.
Need onset or changing componentsSpectrogram/windowed transformRetains where in time the pattern occurs.

2. How it works — what happens and why

  • A whole-recording Fourier transform tells which frequencies occur but can hide when they occur. A spectrogram repeats frequency analysis over short windows.
  • The horizontal direction follows time windows; the vertical direction follows frequency; strength indicates the contribution within each window.
  • Windowing creates a trade-off: short windows localize rapid changes but give less precise frequency separation; longer windows give more frequency detail but smear timing.
  • The spectrogram is a feature representation. A classifier or other task process must still interpret the pattern and produce the requested output.
Implementation steps and their purpose
  1. Capture audio with a suitable rate.
  2. Split it into short time windows.
  3. Apply short-time Fourier transformation.
  4. Represent frequency strength across the windows.
  5. Use this representation for visual inspection or a learned audio task.

4. Design the solution and check the result

Data, components and application

  • Time order lost in one spectrum → use windowed analysis → preserves changing frequency patterns.
  • Noise dominates features → improve recording/preprocessing → cleaner task evidence.
  • Input format mismatch → match model requirements → avoids treating the wrong sampling scale as meaningful.

How to evaluate it

Check whether features distinguish the target events on unseen recordings, rather than only producing a visually clear plot.

Build the answer in this order

  1. What sound event matters?
  2. Need time and frequency information?
  3. Extract windowed representation.
  4. Evaluate the downstream task.

6. Turn understanding into an exam answer

  • Use a spectrogram when frequency content changes over time and the event timing matters.
  • Apply local Fourier analysis to short windows and pass the resulting time-frequency representation to the task model.
  • Compare window choices using event recognition rather than visual appearance alone.

C073

Speech recognition

Automatic speech recognition converts recorded speech to text. NLU then determines what that text means for the task.

How it worksWorked exampleChoose & designProblems & fixes

1. What problem does it solve?

Use for voice interfaces; recognition and understanding are separate stages with separate errors.

Scenario cueSuitable choiceWhy it fits
Low-risk free dictationReturn editable transcriptThe user can repair wording directly.
Action depends on a critical numberCheck/confirm that field when uncertainOne word changes the operation materially.

2. How it works — what happens and why

  • ASR predicts words from audio; NLU predicts intent and details from those words. A transcription error can therefore become an incorrect action downstream.
  • Errors affecting an important slot may matter more than errors in ordinary wording. “Fifteen” versus “fifty” changes a timer even if the rest is correct.
  • Real input includes noise, accents, spontaneous phrasing, reverberation and overlapping speakers. Testing only read speech omits these failure conditions.
  • A correction/retry path can improve task completion even when model-level word error is unchanged. The interface design matters alongside the recognizer.
Implementation steps and their purpose
  1. Capture speech using the expected audio format.
  2. Preprocess the recording where necessary.
  3. Run the speech-recognition model.
  4. Pass the transcript to NLU/dialogue processing.
  5. Allow correction or retry when the task-critical words are uncertain.

3. One recognition error changes the requested action

4. Design the solution and check the result

Data, components and application

  • Noise/reverberation → improve recording and representative tests → reduces recognition errors.
  • Overlapping speakers → manage input conditions → one transcript may mix sources.
  • Spontaneous speech or accents → test realistic user speech → read-speech performance is insufficient.

How to evaluate it

Use word error rate for transcript quality, then task completion, corrections and retries for the complete interface.

Build the answer in this order

  1. Voice task.
  2. Audio → transcript → intent/action.
  3. Likely recognition failures.
  4. Measure transcript and task success.

5. Diagnose the proposed model — change and justify

Strong laboratory result, poor deploymentTest speech differs from workplace recordingsInclude real noise/accent conditionsGeneralization must match users.

Common wrong answers and the exact correction
  • Speech recognition identifies words; speaker recognition identifies who spoke.
  • Low overall word error can still hide an important slot error.

6. Turn understanding into an exam answer

  • ASR converts speech into a transcript; NLU then extracts the intent and action-critical fields.
  • A fifteen/fifty recognition error changes the reminder interval, so uncertain critical values need correction or confirmation.
  • Evaluate word error rate and complete-task success, retries and response time separately.

C075

Whisper

The lecture presents Whisper as a multilingual, multitask speech model for recognition, speech translation and language recognition.

How it worksWorked exampleChoose & designProblems & fixes

1. What problem does it solve?

Use when choosing a pretrained model for converting varied-language speech into a task-usable output.

Scenario cueSuitable choiceWhy it fits
Cloud resources and difficult recordingsTest larger candidate if justifiedExtra capacity may help but must show measurable benefit.
Tight memory/response budgetCompare smaller candidatesA practical solution needs adequate quality within constraints.

2. How it works — what happens and why

  • Whisper’s lecture role is pretrained multilingual/multitask speech processing. The required output must be chosen: transcription, speech translation or language recognition.
  • Pretraining gives an initial model, not proof that it handles a particular workplace accent, microphone or specialist term well.
  • Model size affects resource use and latency; the appropriate choice is the smallest option that meets measured task needs, not automatically the largest.
  • The recognizer remains only the speech front end. It does not by itself execute a reminder or retrieve the right specialist FAQ answer.
Implementation steps and their purpose
  1. Identify whether the required output is transcript, translation or language.
  2. Prepare audio in the format expected by the chosen implementation.
  3. Select a model size suited to device and time constraints.
  4. Test real accents, noise and vocabulary.
  5. Connect the output to the downstream task and recovery flow.

3. Choose the right speech output before integration

6. Turn understanding into an exam answer

  • Choose Whisper’s required output task explicitly: transcription, speech translation or language recognition.
  • Compare suitable model sizes on representative language, accent, noise and vocabulary cases under deployment constraints.
  • Pass the resulting transcript to NLU or retrieval; the speech model alone does not execute the user’s requested action.

C076

Wav2Vec self-supervised learning

Wav2Vec2.0 is presented as self-supervised speech representation learning: learn useful audio features from speech before using task labels.

How it worksWorked exampleChoose & designProblems & fixes

1. What problem does it solve?

Use when unlabelled audio is available but transcribed or otherwise labelled target data is limited.

Scenario cueSuitable choiceWhy it fits
Few target labelsReuse frozen pretrained features firstLimits the amount that must be learned from scarce labels.
Target audio differs substantiallyTest fine-tuningAdapts representations, but needs held-out evaluation.

2. How it works — what happens and why

  • The lecture divides Wav2Vec2.0 use into self-supervised pretraining and supervised downstream adaptation. These phases use different sources of training targets.
  • A CNN creates latent speech features; selected feature time steps are masked so the contextual model must use surrounding information.
  • Quantization creates discrete target representations from the audio itself. Training aligns contextual representations with the corresponding targets rather than requiring a transcript for every pretraining clip.
  • For the target task, keep the pretrained encoder frozen or fine-tune it using labelled examples. The learned representation can support speech recognition or speaker identification.
Implementation steps and their purpose
  1. Collect representative unlabelled speech.
  2. Encode audio with a CNN; mask selected time-step features.
  3. Learn contextual representations matching quantized audio targets: discrete targets created from the audio itself.
  4. Freeze or fine-tune the pretrained model with labelled target data.
  5. Evaluate on separate speakers/recordings.

3. Follow one speech segment through the two training stages

Worked study example: Illustrative feature sequence; symbols A/B/C are code labels, not words or taught numeric outputs.

What this tells us: A code is not a recognized word. The pretext task first learns useful audio structure; downstream labels connect that representation to the real output.

4. Design the solution and check the result

Data, components and application

  • Little labelled data → reuse pretrained features → reduces learning from scratch.
  • Pretraining audio differs from deployment → adapt and test locally → representations may not transfer perfectly.
  • Train/test speakers overlap → separate them → avoids optimistic generalization claims.

How to evaluate it

Assess the downstream speech task and complete interaction, not just the pretraining objective.

Build the answer in this order

  1. Unlabelled versus labelled data available.
  2. Self-supervised pretraining.
  3. Target-task adaptation.
  4. Unseen-speaker/task evaluation.

5. Diagnose the proposed model — change and justify

What you observeWhy it happensWhat to changeWhy that helps
Good pretraining objective, weak recognitionPretext features not sufficient for targetEvaluate and adapt downstream taskPretraining loss is not task success.
Optimistic resultsSame speakers leak across splitsHold out speakers/recordingsTests transfer to genuinely unseen speech.
Common wrong answers and the exact correction
  • Self-supervised does not mean no learning target.
  • Do not describe it as ordinary supervised training on transcripts.

6. Turn understanding into an exam answer

  • Wav2Vec2.0 pretrains on unlabelled audio using masked feature positions and audio-derived quantized targets.
  • The contextual model learns speech structure from surrounding features, then a downstream head uses labelled task data.
  • Compare frozen and fine-tuned representations on separate speakers/recordings rather than relying only on pretraining loss.
