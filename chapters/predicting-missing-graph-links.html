C023

TransE embeddings

TransE learns vectors so that moving from a head entity by a relation vector lands near the tail entity. Nearer means a more plausible triple.

  1. Add the relation vector to the head.
  2. Measure distance from that position to each candidate tail.
  3. Lower mismatch means a better model fit; a negative-distance score reverses the numeric direction.

Interpret the result: Rank plausible tails, then validate proposed links.

Read the relationships and follow the choices

  • TransE tries to make a head vector plus a relation vector land near a tail vector. The remaining distance is a mismatch measure: smaller distance means the triple fits the learned geometry better. Some implementations report the negative distance, in which case larger scores mean better; state the direction rather than confusing score with distance.
  • Training compares observed triples against corrupted alternatives, such as replacing the tail. This creates pressure to preserve known relationships while separating unlikely ones. Because KG data are incomplete, a corrupted triple can accidentally be true; the negative labels are not equivalent to verified false facts.
  • The geometric simplification provides compact scoring but limits relation patterns. If one head with one relation has many distinct tails, forcing all of them near the same translated location can collapse distinctions. A more expressive model is justified by the relation structure and held-out results, not simply by having a longer name.
Implementation steps and their purpose
  1. Collect known head–relation–tail triples.
  2. Learn entity and relation vectors.
  3. Train known triples to score better than corrupted alternatives.
  4. For a query, apply the relation to the head vector.
  5. Rank candidate tails by closeness and validate predicted links.

Choose the method from the problem

Use for compact KG representations and candidate missing-link prediction when a simple translation model suits the relations.

Implement it and test the outcome

Data, components and application

  • One-to-many relations → consider relation-specific models → one translation struggles to represent many distinct tails.
  • False negatives in corrupted triples → sample/check carefully → missing links may actually be true.

How to evaluate it

Hide known links and check candidate ranking; inspect relation types where performance is poor. Compare cost and quality with alternatives.

C024

TransR embeddings

TransR keeps entities in an entity space and projects them into a separate space for each relation before applying translation. Different relations can focus on different aspects.

Read the relationships and follow the choices

  • TransR gives each relation its own projection of the entity vectors. It can therefore emphasise work-related features for worksFor and a different combination for a family relation. Head and tail are projected using the chosen relation’s matrix before translation is scored.
  • The projection is the key change from TransE; simply adding more dimensions without relation-specific handling does not explain TransR. Entities retain a shared base representation, but their relation-specific views can differ. The relation vector acts inside that projected space, not directly in the original space.
  • This flexibility costs parameters and computation. A sparsely observed relation may not provide enough evidence to learn a reliable projection, so a model with greater apparent expressiveness can perform worse on new links. Model choice must compare the representational need against data per relation, regularisation and serving budget.
Implementation steps and their purpose
  1. Start with entity vectors and relation-specific projection matrices.
  2. For a candidate triple, project head and tail into that relation’s space.
  3. Apply the relation translation there.
  4. Train true triples to score above negative alternatives.
  5. Rank candidates and check held-out links.

Choose the method from the problem

Consider when one shared TransE space poorly handles diverse relation types or one-to-many/many-to-one relationships.

C025

Bilinear / DistMult embeddings

Bilinear KG models score interactions between a head, a relation and a tail. RESCAL uses a full relation matrix; DistMult restricts it to a diagonal for efficiency.

CalculationDiagramHow it worksWorked exampleChoose & designProblems & fixes

Choose from the scenario

Choose by the relation pattern: efficient symmetric scoring may be suitable for some links but fails to distinguish directed roles.

Scenario cueSuitable choiceWhy it fits
Symmetric relation and efficiency priorityDistMult baselineDiagonal interactions are compact and naturally symmetric
Important asymmetric relationsUse a suitable asymmetric model such as ComplExThe score must be capable of representing direction

If relation is friendOfSymmetric direction may be acceptableSame score can fit semanticsPotentially appropriate

What this tells us: No amount of training can make this unchanged scoring expression distinguish those two directions for the same relation. This is an expressiveness issue, not merely insufficient optimisation.

The distinction that changes the answer

  • RESCAL and DistMult score how head and tail features interact under a relation. RESCAL’s full relation matrix can mix different feature dimensions. DistMult keeps only diagonal interactions, so each head component interacts with the corresponding tail component through a relation weight; this reduces parameter cost.
  • The same simplification creates a structural limitation. Multiplying corresponding head and tail values is unchanged when their order swaps, so DistMult gives identical scores to a triple and its reversal under the same relation. This is a problem for fatherOf, greaterThan or any relation where direction should matter.
  • A richer full-matrix or complex-valued model can represent patterns DistMult cannot, but its cost must be justified. The lecture’s RESCAL memory warning is valid in spirit, but relation matrices scale with embedding dimension squared per relation, not simply the number of entities squared. Entity storage is a separate component.

  • KG factorisation is a different task from user–item recommendation MF.

Apply the distinction

Data, components and application

  • Asymmetric relation → consider ComplEx or a suitable asymmetric model → DistMult swaps head/tail without changing score.
  • Full relation matrices → assess memory/overfitting → RESCAL has greater parameter cost.

How to evaluate it

Test directional reversals, held-out link ranks and memory. RESCAL relation-matrix storage depends quadratically on embedding dimension, not simply entity count.

C026

Neural knowledge graph embeddings

Neural KG models learn richer interactions between entities and relations. Graph neural approaches also aggregate information from neighbours. The architecture determines what new entities it can handle.

New isolated featureless nodeNo useful 2 or neighbour valuesInductive architecture still lacks evidence

What this tells us: The transfer comes from reusing a learned aggregation function, not from every neural network automatically understanding new nodes. The lecture’s broad claim needs this qualification.

Read the relationships and follow the choices

  • A neural KG model must specify where information comes from. ConvE processes learned head/relation embeddings through convolution and nonlinear features before matching candidate tails. Graph neural models instead use graph neighbourhoods, sometimes with relation-specific aggregation; these mechanisms are not interchangeable descriptions of “deep learning”.
  • Neighbour aggregation lets information from connected nodes influence a representation. Repeating layers reaches progressively farther neighbours, but only through the allowed training graph. If held-out target edges are left in that graph, the supposed prediction can leak its own answer through message passing.
  • Unseen-node handling is architecture-dependent. An ID-only embedding table has no learned entry for a new identifier. An inductive feature aggregator such as GraphSAGE can compute a new representation from available features and neighbours using shared parameters. It still needs useful inputs; a completely isolated featureless new node remains difficult.
Implementation steps and their purpose
  1. Define link prediction or node/graph classification target.
  2. Choose inputs: IDs, relation types, node features or text.
  3. Use the appropriate architecture, such as ConvE or relation-aware aggregation.
  4. Train on permitted graph information.
  5. Validate on the required setting, including genuinely unseen nodes if relevant.

Choose the method from the problem

Useful when simple translation/bilinear scores miss relevant graph structure or external features.
