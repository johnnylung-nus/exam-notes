C062

TF-IDF and cosine similarity

TF-IDF gives more weight to distinctive words. Cosine similarity compares vector directions to rank related texts.

How it worksWorked exampleChoose & designProblems & fixesExam answer

1. What problem does it solve?

Use for a simple text-classification or FAQ-retrieval baseline; embeddings are more suitable when different words express similar meaning.

Scenario cueSuitable choiceWhy it fits
Similar wording and simple baseline neededTF-IDF plus cosineEasy to inspect term contributions and evaluate retrieval.
Different wording with same meaningSentence embeddings plus cosineCan match semantic paraphrases with little shared vocabulary.

2. How it works — what happens and why

  • TF-IDF is a representation step: distinctive terms receive greater weight than words common across the collection. It does not itself retrieve an answer.
  • Cosine similarity compares vector directions. Ranking chooses the closest stored question, then its identifier retrieves the linked approved answer.
  • Stored questions and new queries must use the same fitted vocabulary/weights or embedding model. Vectors from incompatible spaces cannot be meaningfully compared.
  • A threshold checks match adequacy; it is an application-tuned decision, not a universal number or probability of medical correctness.
  • Tiny cosine calculation, using supplied weights in the same two word dimensions: query [1,1] and stored question A [1,1] have matching-position products 1×1 + 1×1 = 2. Each vector has length √2, so similarity is 2/(√2×√2) = 1.
  • For stored question B [1,0], the matching-position products sum to 1 and its length is 1, giving 1/(√2×1) ≈ 0.707. Dividing by both lengths compares direction rather than rewarding a question simply for having larger weights. These supplied vectors illustrate the calculation, not the FAQ scores below.
Implementation steps and their purpose
  1. Prepare stored questions using consistent tokenization.
  2. Fit the vocabulary and word weights on the stored/training collection.
  3. Transform stored questions and new query in the same vector space.
  4. Compare query against candidate vectors using cosine similarity.
  5. Return the linked answer only when the match is adequate.

4. Design the solution and check the result

Data, components and application

  • Synonyms share few words → use semantic embeddings → better captures paraphrases.
  • Weak nearest match → clarify/fallback → the closest available answer can still be wrong.

How to evaluate it

Test known paraphrases and unrelated questions; measure whether the retrieved approved answer is relevant.

6. Turn understanding into an exam answer

  • Store the specialist’s FAQ question–answer pairs with stable IDs and represent stored questions and the new query using the same embedding model.
  • Rank stored question vectors by cosine similarity; when the best match is adequate, return its linked approved answer.
  • If no adequate match exists, ask for clarification or report that no approved match is available; a generative model or knowledge graph is unnecessary for this direct lookup.

7. Where this is tested in the sample papers

ISY5001 Q1(b) — FAQ retrieval without unnecessary architecture

What the question requires

  1. Store approved question–answer pairs.
  2. Represent stored questions and the new query consistently.
  3. Retrieve the closest question and its linked approved answer.
  4. Clarify or fall back when no reliable match exists.

Proposed answer points

  • New query → embedding/similarity search → matched FAQ ID → linked answer.
  • A generative LLM or knowledge graph is not required. Retrieval plus generation would be a different, justified extension.

Avoid: Similarity is not proof the retrieved answer is correct; keep a fallback.

C082

RAG and knowledge-graph cognition

RAG retrieves relevant source material before an LLM writes an answer. A knowledge graph represents explicit entities and relationships for linked knowledge use.

How it worksWorked exampleChoose & designProblems & fixes

1. What problem does it solve?

Use when answers need domain documents or relationships that should remain traceable to stored knowledge.

Scenario cueSuitable choiceWhy it fits
Approved answer should remain unchangedRetrieval-only FAQMinimizes unnecessary generation and validation.
Answer requires combining relevant passagesRAGGeneration can synthesize evidence that is not one existing answer.

2. How it works — what happens and why

  • FAQ retrieval returns an existing answer linked to a matched question. RAG adds generation from retrieved evidence; these are different architectures and different sources of risk.
  • RAG needs loading, splitting, indexing and retrieval before an LLM can use source chunks. The retrieved text must actually contain evidence for the requested answer.
  • A knowledge graph explicitly represents entities and relationships; a vector index ranks similar text. Choosing one depends on the needed query, not a preference for complexity.
  • Grounding reduces unsupported output but does not guarantee it disappears. Check retrieval relevance and generated claims as separate stages.
Implementation steps and their purpose
  1. Load and split approved documents.
  2. Embed/index chunks for retrieval.
  3. Retrieve material relevant to the query.
  4. Provide that material with the question to generation.
  5. Check that the answer stays within the evidence.
  6. Use graph relationships when the task actually needs them.

4. Design the solution and check the result

Data, components and application

  • Wrong chunk retrieved → improve retrieval and inspect relevance → generation cannot fix missing evidence reliably.
  • Unsupported answer → require citations/fallback → limits overreach.
  • Unnecessary graph complexity → use a simple linked FAQ store → matches the actual task.

How to evaluate it

Check retrieval relevance, answer faithfulness, coverage, uncertainty and end-to-end task success.

Build the answer in this order

  1. Knowledge needed.
  2. Choose retrieval/store representation.
  3. Retrieved evidence → answer.
  4. Check faithfulness and missing evidence.

Common wrong answers and the exact correction

6. Turn understanding into an exam answer

  • For the supplied FAQ collection, semantic retrieval plus approved-answer lookup directly addresses Q1(b).
  • RAG is appropriate when retrieved passages must be synthesized; it adds a generation step that must be checked for evidence faithfulness.
  • A knowledge graph is justified by explicit relationship queries, not merely by the existence of a knowledge base.
