Text-to-speech

Text-to-speech converts text into spoken audio. It provides the spoken-response side of a voice interface.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

What must the system deliver?

Use when users need to hear responses or cannot easily read a display.

Scenario cueSuitable choiceWhy it fits
Simple repetitive confirmationTemplate plus TTSPredictable wording reduces ambiguity.
Longer spoken guidanceStructured approved content with suitable pausesThe user needs understandable sequencing, not only natural voice quality.

What each component receives and produces

  • TTS generates spoken output from text. It does not determine whether the information is correct or whether the underlying operation succeeded.
  • The response text should be grounded before synthesis; otherwise an expressive voice merely makes an incorrect answer easier to believe.
  • Numbers, abbreviations, names and domain vocabulary need pronunciation checks because mishearing a critical value can undo correct earlier processing.
  • The lecture’s progression moves from early and concatenative systems through HMM/deep-learning approaches to end-to-end models; model choice should serve intelligibility and runtime constraints.
Implementation steps and their purpose
  1. Obtain the final grounded response text.
  2. Prepare numbers, dates and domain terms for clear speech.
  3. Generate spoken audio.
  4. Deliver it through the chosen output device.
  5. Check that users understand the important content.

A correct action still needs understandable spoken confirmation

Data, implementation and validation

Data, components and application

  • Fluent but wrong content → verify text before synthesis → speech generation cannot repair a factual error.
  • Mispronounced names/numbers → test task vocabulary → important details must remain understandable.
  • Slow response → evaluate the complete pipeline → synthesis adds to interaction time.

How to evaluate it

Check intelligibility, pronunciation and whether users correctly understand the response; measure task success and response time.

Build the answer in this order

  1. Why spoken output?
  2. Grounded text → speech.
  3. Domain vocabulary and delivery issues.
  4. Evaluate comprehension and interaction.

An answer you could write

  • Generate speech only after the response text reflects approved content or the actual service result.
  • Check pronunciation and pacing of critical numbers and domain terms so users understand the intended action.
  • Assess comprehension and task completion as well as voice intelligibility and response delay.

C077

Audio/system evaluation

Evaluate the model, the intelligent task and the complete system separately. A good component score does not prove that users succeed.

CalculationDiagramHow it worksWorked exampleChoose & designProblems & fixes

Word error rate

WER = (S + D + I) / N
S
substituted words
D
deleted words
I
inserted words
N
number of reference words
  1. Reference has5 words.
  2. “fifteen”→“fifty” is1 substitution; D=0 and I=0.
  3. WER=(1+0+0)/5=.20=20%.
  4. Check downstream interval separately:15 became50.

Interpret the result: WER20%; action-critical interval is wrong.

Calculate WER, then ask whether the reminder task succeeds

What this tells us: This is why task completion, correction rate, retries and response time belong beside WER. Equal component scores can produce very different user experiences.

Why the calculation works

  • A model score assesses a particular output; a task score assesses the intelligent operation; system evaluation asks whether the complete user workflow succeeds.
  • Word error rate counts substitutions, deletions and insertions relative to the number of reference words. It does not weight business or action importance automatically.
  • A change can lower overall transcription errors yet increase critical-number errors, so end-to-end task checks are needed.
  • Comparisons require equivalent unseen cases and clearly defined outcomes. A better score on easier test recordings is not evidence that the changed model is better.
Implementation steps and their purpose
  1. Identify the output the model predicts.
  2. Choose a matching task measure.
  3. Test on unseen, representative cases.
  4. Measure complete user outcomes.
  5. Check robustness, speed and error consequences.
  6. Compare the changed system with the original under the same conditions.

Use the result and check it

Data, components and application

  • Only accuracy reported → add task and system checks → component quality may not deliver value.
  • Easy test data → use realistic noise/users → tests deployment conditions.
  • Fast but wrong response → evaluate quality and latency together → speed alone is insufficient.

How to evaluate it

Word error rate = substitutions + deletions + insertions, divided by reference words. For 10 reference words and 2 such errors, WER is 20% (illustrative).

Build the answer in this order

  1. Required outcome.
  2. Model/task measure.
  3. System/user measure.
  4. Compare baseline and failure cases.

Common wrong answers and the exact correction
  • Evaluation data must not be reused as training examples.
  • A lower error score need not improve every user task.

When would this calculation be useful?

Use whenever an exam asks whether a system works or whether a proposed change is worthwhile.

An answer you could write

  • For the five-word reference, one substitution or one insertion gives WER 20%.
  • The substitution fifteen→fifty corrupts the interval, while adding “please” may leave the action correct despite equal WER.
  • Compare transcript quality with task completion, correction burden and latency under the same held-out conditions.
