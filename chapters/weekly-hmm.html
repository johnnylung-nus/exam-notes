HMM: weekly query patterns

A hidden Markov model (HMM) explains an ordered observation sequence using hidden states that can change over time. For this classification task, a defensible design trains one HMM for each work-pattern class.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

What must the system deliver?

Recognize software-engineer pattern A versus sales-executive pattern B from a week of chatbot query records.

Scenario cueSuitable choiceWhy it fits
Goal is work-pattern classOne HMM per labelled role patternSeparates stable class from changing daily latent state.
Goal is daily mode inferenceInfer states within a chosen modelThis is a different output from classifying the whole week.

What each component receives and produces

  • An HMM distinguishes observed daily query counts from an unobserved daily mode. The hidden state is not a copy of the count vector.
  • Transitions describe how modes follow one another across days; emissions describe which observations are likely within each mode. Both contribute to sequence likelihood.
  • For stable role classification, one defensible architecture fits an HMM for pattern A and another for pattern B, then compares a new week.
  • Software engineer versus sales executive is the week’s class label in this design; changing daily modes sit inside each class model. No probabilities can be estimated reliably from the printed ellipses alone.
Implementation steps and their purpose
  1. Prepare one ordered daily-count sequence per employee-week: ergonomics, visual-habit and eye-exercise counts.
  2. Propose hidden daily work/eye-care-need modes, such as sustained screen work versus varied activity; these are modelling assumptions.
  3. Learn initial-state probabilities, transitions between daily modes and emissions: how likely each query-count observation is under a mode.
  4. Fit separate HMMs using labelled A and B training weeks.
  5. Score a new weekly sequence under each HMM; choose the better-supported class, accounting for class priors if unequal.

Data, implementation and validation

Data, components and application

  • Only a few table rows shown → obtain complete training weeks → cannot estimate reliable probabilities from ellipses.
  • Similar query counts across roles → test unseen employees → proxy behaviour may not separate work patterns.

How to evaluate it

Hold out employees/weeks; compare A/B classification errors and whether sequence order adds useful evidence.

Build the answer in this order

  1. State the class being predicted.
  2. Define hidden state versus observed daily counts.
  3. Explain transitions, emissions and one-model-per-class scoring.
  4. Validate on unseen employee-weeks.

Common wrong answers and the exact correction
  • Do not alternate software-engineer/sales-executive job labels as daily activity states without justification.
  • Query counts are observations; their temporal order matters.

An answer you could write

  • I use daily category-count vectors as observations and assume latent daily work modes as states.
  • I train separate HMMs on labelled A and B employee-weeks and classify a new week using their sequence likelihoods, with priors if required.
  • I hold out employees/weeks and state that the printed incomplete table cannot support numerical parameter estimates.

Where this is tested in the sample papers

ISY5001 Q1(d) — HMM states, observations and sequence classification

What the question requires

  1. Define hidden states and the observed daily query records.
  2. Specify initial, transition and emission probabilities conceptually.
  3. Explain how probabilities would be learned or supplied.
  4. Score the week’s sequence and choose the supported work-pattern class.

Proposed answer points

  • One defensible design trains an HMM per job/work-pattern class. Hidden states represent daily activity modes; observations are daily query categories/counts.
  • Compute each class model’s sequence likelihood, combine with class priors if used, and choose the highest supported class. Activity labels and model structure are design assumptions.

Avoid: Do not confuse an observed count with a hidden state or invent transition/emission numbers from an incomplete table. Job role and changing daily activity are not automatically the same variable.
