C018

Semantic networks

A semantic network represents entities/concepts as nodes and relationships as labelled edges. Inheritance and traversal help connect related knowledge.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

Illustrative relationship audit

Worked study example: Compare a simple animal hierarchy with the eye/face distinction emphasised in the sample discussion. These are representation examples, not medical claims.

All steps shown
Proposed linkRelation meaningValid inferenceInvalid inference
Canary is-a BirdSubclassCanary belongs to Bird categoryAll birds are canaries
Bird is-a AnimalSuperclass hierarchyCanary is an animal through BirdAnimal inherits every Canary property
Eye part-of FaceCompositionEye is a component of a faceEye is a subtype of Face
Alice instance-of PersonIndividual membershipAlice is a personEvery person has Alice’s attributes

What this tells us: The chain is only as meaningful as its relation types. A generic “related to” edge can support navigation but cannot justify precise subtype inference.

What information this representation preserves

  • A semantic network gives links their meaning through relation labels. A line between Eye and Face is insufficient: is-a and part-of imply different things. Class inheritance permits category membership to flow upward; composition describes containment and does not make a component a subtype of the whole.
  • Instances and categories also differ. Alice member-of Person says Alice is one person; Student is-a Person says every student belongs to the broader category. Mixing these levels can create incorrect inheritance, such as treating an individual’s property as universal for every person.
  • Networks are useful when the examiner wants relationships visible, but informal arrows do not automatically define an inference engine. State the traversal or inheritance procedure and any exception/default handling. If formal consistency and shared domain constraints matter, an ontology may be the stronger representation.
Implementation steps and their purpose
  1. Identify classes and instances.
  2. Choose meaningful relationship labels.
  3. Draw the directed links and hierarchy.
  4. Separate class membership, is-a inheritance and part-of composition.
  5. State what can be inferred by following the links.

Prepare the data and validate the representation

Data, components and application

  • Unlabelled links → label direction and semantics → readers cannot infer what a connection means.
  • Exceptions to inherited defaults → represent overrides → a general property may not hold for every subclass.

How to evaluate it

Check that each claimed inference follows the intended relation semantics. Informal networks need additional rules if stronger formal inference is required.

Build the answer in this order

  1. Extract entities.
  2. Label relations.
  3. Show useful paths/inheritance.
  4. Check meaning and exceptions.

Useful for showing associations or concept hierarchies when a visual relationship model is more helpful than flat records.

An answer you could write

  • Canary is-a Bird and Bird is-a Animal permit inherited category membership, while Eye part-of Face describes composition rather than subtype.
  • I label relation direction and distinguish individual membership from class hierarchy before claiming any inherited property.

C019

Frames

Frames represent structured objects or typical situations using named slots, values and relationships. Parent frames can provide inherited shared properties and defaults.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

Sample-aligned frame structures

Worked study example: This is a proposed study schema based on the sample discussion, not an official answer key. Clinical slot values/rules require specialist validation.

All steps shown
FrameSlots/linksWhy separate?
BodyPart parentname, position, time_recordedShared observation structure
Eye childinherits BodyPart; eye_positionSpecialises shared fields
Monitorbrightness, contrast, height_statusEquipment is not a body-part subtype
PatientFactssymptom_X: unknown; sign_Y: presentCurrent evidence, including missingness
DiseaseKnowledgeassociated_signs, diagnostic_rule_idsReusable knowledge, not this patient’s truth

What this tells us: The engine can use these records to ask a relevant question or test rule conditions. Naming frames alone does not explain the diagnostic process; connect them to matching/chaining and show output structures.

What information this representation preserves

  • A frame is a structured description with named slots, not just a box containing a label. Slots specify what can be known about the object and which values are permitted. Qualitative slots such as too-close/optimal/too-far can capture the interpretation required by the scenario, rather than storing only uncontextualised numbers.
  • Inheritance shares common slot definitions through parent frames. A child adds specialised slots or overrides a default; it should not duplicate every field or confuse a has-part link with a subtype. A disease frame stores domain knowledge while a patient frame stores this particular case’s observations.
  • Reasoning still needs a procedure. A frame can organise associated symptoms, rule references and result fields, but “match patient to disease frame” must explain what counts as a match. Simple match counts are support scores, not calibrated probabilities, and a typical disease property is not automatically true for every patient.
Implementation steps and their purpose
  1. Identify object/frame types.
  2. Define slots, value types and qualitative states.
  3. Create shared parent slots and specific child slots.
  4. Link frames with correctly named relationships.
  5. Specify how an inference procedure uses the stored information.

Prepare the data and validate the representation

Data, components and application

  • Only drawing objects → add slots/relations and inference use → a database alone does not establish frame-based reasoning.
  • Defaults treated as facts → allow patient-specific override → typical knowledge is not always true.

How to evaluate it

Check inheritance, qualitative values and whether the schema can represent the question’s actual inputs and conclusions.

Build the answer in this order

  1. List frames.
  2. Specify slots and links.
  3. Show inheritance/overrides.
  4. Explain matching or rule processing.

Choose the representation from the task

Choose when the scenario naturally describes objects with attributes, such as patient findings, equipment or diseases.

Objects with attributes/defaultsFrames plus explicit inferenceCase data and shared knowledge can be organised readably
Only free-form text descriptionsExtract/validate structured slots firstA frame engine cannot reliably test unspecified values

Common wrong answers and the exact correction
  • A frame stores knowledge; it does not itself choose a diagnosis.
  • Disease knowledge and current patient findings are different records.

An answer you could write

  • BodyPart stores shared name, position and observation time; Eye inherits those slots and adds eye position, while Monitor is separate equipment.
  • PatientFacts stores current present/absent/unknown findings; disease frames store reusable knowledge and rule links used by the inference engine.

ISY5001 Q2(d) — Knowledge-based internal architecture and data structures

What the question requires

  1. Validate inputs; distinguish present, absent and unknown.
  2. Store patient facts in working memory.
  3. Represent specialist knowledge as disease frames and diagnostic/triage/action rules.
  4. Match/fire rules; display conclusions and explanations.

Proposed answer points

  • Patient facts → inference engine ← knowledge base → diagnosis candidates + urgency + action.
  • Show structures: patient fact fields; disease frame IDs; rules with conditions, conclusions, priority and explanation. One engine can apply several rule types.
  • If evidence is missing/conflicting, request information or flag for doctor review. Clinical contents require specialist validation.

Avoid: A box labelled “AI” is insufficient. A KB stores knowledge; an inference engine names the procedure using it. Softmax scores do not automatically encode urgency.

What the question requires

  2. Compare it with the complete required functions.

C020

Ontologies

An ontology formally specifies a domain’s concepts, relationships, hierarchies and constraints. It provides shared meaning and supports classification/consistency checks.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Lecture university ontology reasoning

Worked study example: Classes include Person, Academic and Professor. Professor is a subclass of Academic. Relations include teaches and enrolls_in.

All steps shown
Stored statementOntology meaningDerived/check result
Alice instance-of ProfessorProfessor subclass AcademicAlice is Academic
Academic subclass PersonAcademic is a kind of PersonAlice is Person
Alice teaches AI101Teacher-to-course relationTypes can be checked
AI101 teaches AliceEndpoints reversedFlag against intended relation roles
Bob enrolls_in AI101Student/course relationshipQuery enrolled courses using shared meaning

What this tells us: The useful result is not merely a prettier graph. Shared definitions support inference, validation and integration while retaining the distinction between rules/schema and instance facts.

What information this representation preserves

  • An ontology specifies what kinds of things exist in the model and what relationships are meaningful between them. It gives different datasets a shared vocabulary, so “provider”, “doctor” and “clinician” are reconciled only when the domain definitions justify equivalence rather than because their words look similar.
  • Class hierarchy enables consequences such as Professor being an Academic. Property constraints and definitions allow consistency checking: a relation can be flagged if its endpoints do not match the intended types. The ontology defines the semantics; the KG contains particular people, courses and their asserted relations.
  • A formal model still depends on correct domain choices and source facts. An apparently inconsistent record may expose a source-data error, a mapping error or an overly restrictive ontology. The appropriate response is to investigate, not to silently delete a difficult fact merely to make the reasoner report consistency.
Implementation steps and their purpose
  1. Define important classes and instance types.
  2. Specify properties and permitted relations.
  3. Add class hierarchy and constraints.
  4. Map source terms to the shared definitions.
  5. Check consistency and state valid inferred memberships.

Prepare the data and validate the representation

Data, components and application

  • Conflicting source meanings → map and reconcile concepts → identical labels can mean different things.
  • Excessive complexity → model required distinctions only → maintenance cost can exceed value.

How to evaluate it

Check class consistency, illegal relation types and whether relevant queries can be expressed. Have domain experts review definitions.

Build the answer in this order

  1. Identify shared concepts.
  2. Define hierarchy and constraints.
  3. Map entities/facts.
  4. Demonstrate one inference and validation.

Choose the representation from the task

Useful when several data sources must describe the same domain consistently or when valid relations and class membership matter.

Scenario cueSuitable choiceWhy it fits
Several sources use inconsistent domain categoriesOntology and mappingShared definitions reduce incompatible interpretations
Simple one-off object form with few linksFrames may sufficeFull formal ontology introduces unnecessary modelling effort

Information loss, noise and failure cases

What you observeWhy it happensWhat to changeWhy that helps
Same term merged across different meaningsString equality treated as semantic equalityReview mappings with domain expertsVocabulary reconciliation requires meaning
Valid data rejectedConstraint too restrictive or source mapping wrongInvestigate model and record togetherConsistency failure is evidence to diagnose, not proof data must vanish
Common wrong answers and the exact correction
  • Ontology defines the schema/meaning; a KG stores concrete facts.
  • More formality does not make incorrect source facts true.

An answer you could write

  • Because Professor is a subclass of Academic and Academic of Person, Alice being a Professor implies Alice is Academic and Person.
  • The ontology defines classes and permitted relationships; the KG stores Alice and AI101 facts, whose mappings and constraints I validate.

C021

Knowledge graph structure and queries

A knowledge graph stores connected facts as entities and named relationships, often subject–predicate–object triples. Queries exploit those connections.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Lecture entities: follow the right identity

Worked study example: Stored triples include Alice teaches AI101, Alice advises Bob and Bob enrollsIn AI101. Consider questions about Bob and Alice.

All steps shown
QuestionGraph operationAnswer/reasoning
Who advises Bob?Reverse-match advises edge ending at BobAlice
Which course does Bob enroll in?Follow Bob→enrollsInAI101
Which course does Bob’s adviser teach?Bob←advises←Alice→teachesAI101
Does Bob teach AI101?No matching asserted teaches edgeNot established; enrollment is different
What supports the answer?Return source triples/pathIdentity and relation chain can be audited

What this tells us: Two steps through a shared entity answer a question a flat keyword match can confuse. The missing teaches edge does not establish that Bob never teaches; it establishes that this graph lacks that fact.

Read the relationships and follow the choices

  • A KG represents facts through entity identities and named directed relations. The representation is more than a collection of keywords: Alice–advises–Bob and Bob–enrollsIn–AI101 can be joined because the Bob identifier is the same entity in both facts.
  • Queries exploit these joins. To answer a relational question, identify the starting entity, the relations to follow and what answer type is required. Keeping relation direction explicit prevents a query for “courses taught by Bob’s adviser” from returning courses Bob himself teaches.
  • The absence of an edge may mean unknown, not false. Coverage and provenance therefore matter: a query can be exact over an incomplete graph yet miss a true real-world answer. Predicted links from an embedding model must remain distinguishable from validated stored facts, especially in sensitive scenario design.
Implementation steps and their purpose
  1. Identify entities and stable identifiers.
  2. Define meaningful relation types and directions.
  3. Store source-backed triples and relevant attributes.
  4. Translate the question into graph conditions.
  5. Retrieve matching facts and retain their provenance.

Choose the method from the problem

Use when questions require relationships across entities, rather than only one row’s features.

Scenario cueSuitable choiceWhy it fits
Question depends on connected entity relationshipsKG queryShared identifiers support exact joins across facts
Question only predicts a label from a feature rowPredictive model may fit betterA KG is not automatically the right tool for every task

Where the graph or reasoning can fail

What you observeWhy it happensWhat to changeWhy that helps
Wrong Bob’s records joinedNames used as unique IDsUse entity IDs/disambiguationDifferent people can share a name
Confident “no” from empty queryIncomplete graph treated as closed truthReport not established and assess coverageMissing relationships are not universal negatives
Common wrong answers and the exact correction
  • A KG is not a decision tree.
  • An absent edge does not prove a relationship is false.

Implement it and test the outcome

Data, components and application

  • Duplicate names → entity matching → separate records may refer to one person.
  • Missing/incorrect links → validate and record provenance → graph queries are only as reliable as stored facts.

How to evaluate it

Check query answers against known examples, graph coverage and relation direction. Distinguish stored facts from predicted links.

Build the answer in this order

  1. Extract entity/relation schema.
  2. Show sample triples.
  3. Translate query.
  4. Return answer with supporting path.

An answer you could write

  • To find courses taught by Bob’s adviser, I follow Bob backwards through advises to Alice, then Alice through teaches to AI101.
  • Bob’s enrollment does not establish that Bob teaches AI101; an absent teaches edge means the graph has no supporting fact, not universal falsity.

C022

KG traversal and multi-hop queries

Multi-hop queries follow several relationships. Conjunctive queries require all stated conditions, often joining or intersecting results.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Illustrative conjunctive query with trace

Worked study example: Find drugs targeting an Alzheimer-associated protein AND involved in Phase II trials. Invented candidate records illustrate the lecture query structure.

All steps shown
DrugTargets Alzheimer-linked protein?Phase II trial?Keep?
Drug AYes, via Protein PYesYes: same drug meets both
Drug BYes, via Protein QNoNo: trial condition missing
Drug CNo known pathYesNot established as answer
Drug DProtein link unknownTrial link unknownInsufficient graph evidence

What this tells us: Returning B or C because each satisfies one branch answers OR, not AND. Drug C may be relevant in reality, but a missing protein path prevents a source-backed assertion from this graph.

Read the relationships and follow the choices

  • A path query composes relationships; a conjunctive query joins several conditions on the same candidate. The difference matters: drugs reaching an Alzheimer-linked protein form one candidate set, while drugs in a trial form another; the answer to AND is their intersection, not their union.
  • The sequence and direction of edges determine what the path means. “Disease associated with Protein targeted by Drug” can require following a relation backwards from protein to drug. Natural-language word order alone is not enough to determine traversal direction; inspect the stored schema.
  • Traversal cannot use a missing link even if that relationship is real. This is why a graph-completion model may be proposed to suggest candidates, but predicted edges should not silently become established query facts. An answer can be precise over known links while having poor recall because the graph is incomplete.
Implementation steps and their purpose
  1. Identify the anchor entity and desired answer type.
  2. Write the sequence of relation directions.
  3. Traverse the relevant links.
  4. For AND conditions, retain only entities meeting every branch.
  5. Return the answer and supporting paths.

Choose the method from the problem

Useful for questions such as finding a team owner through its player, or finding entities satisfying several connected criteria.

Scenario cueSuitable choiceWhy it fits
Several relationship stepsPath traversal with explicit directionEach hop must connect through the correct intermediate entity
Two conditions on one answer entityJoin/intersect candidatesBoth conditions must hold for the same candidate

Where the graph or reasoning can fail

What you observeWhy it happensWhat to changeWhy that helps
Returned unrelated entities from each branchUsed union for ANDJoin on drug identifier and intersectConditions belong to one output object
Empty result interpreted as impossible therapyGraph coverage incompleteState missing evidence and verify sourcesTraversal does not infer absent links automatically
Common wrong answers and the exact correction
  • AND is not a union of unrelated answers.
  • Predicted edges require validation before being treated as facts.

Implement it and test the outcome

Data, components and application

  • Graph incompleteness → label incomplete coverage or propose verified link completion → traversal cannot follow missing edges.
  • Unbounded traversal → constrain relation types/depth → avoid exploring irrelevant paths.

How to evaluate it

Check each hop, direction and join. Measure correctness and coverage separately; an empty result may mean insufficient data.

Build the answer in this order

  1. Parse target and anchors.
  2. Draw required path/branches.
  3. Apply all conditions.
  4. Explain missing-data limitations.

An answer you could write

  • I first follow the Alzheimer→associated protein←targets drug path, then retain only those same drugs with a Phase II trial relation.
  • Drug B fails the trial condition and Drug C lacks a known protein path; an AND answer must satisfy both branches on one drug identifier.
