C060

Natural language understanding

Natural language understanding (NLU) converts a request into an intent plus the details needed to act.

How it worksWorked exampleChoose & designProblems & fixesExam answer

1. What problem does it solve?

Use when a scenario asks how a chatbot understands different wordings and uses conversation context.

Scenario cueSuitable choiceWhy it fits
Direct action requestIntent-and-slot pipelineA concrete operation must be completed.
General question similar to an existing FAQRetrieval routeThe goal is finding an approved answer, not setting a reminder.

2. How it works — what happens and why

  • An utterance expresses a goal and details. NLU maps it to an actionable representation; it does not simply search for any matching word.
  • The goal determines which slots matter: a reminder needs a reminder type and interval, whereas exercise guidance needs the chosen exercise.
  • References such as “that reminder” require earlier conversation state. Re-reading the latest sentence alone can lose the object being changed.
  • NLU output can be incomplete. Dialogue management must collect missing values before an action is executed or confirmed.
Implementation steps and their purpose
  1. List only functions supported by the case.
  2. Tokenize or otherwise prepare the input.
  3. Identify the requested intent.
  4. Extract the required slot values.
  5. Resolve references using previous turns.
  6. Pass a completed action template to dialogue management.

3. EyeCoach: two turns become one complete request

Worked study example: Sample functions are from the paper; utterances and state values below are illustrative.

All steps shown

Remind me to look awaySet reminder; type=look away; interval=missingPending reminder, not savedAsk the interval

What this tells us: The second sentence is not a new unrelated intent. Its interpretation depends on the pending action and the slot currently being requested.

4. Design the solution and check the result

Data, components and application

  • Ambiguous request → clarify the intent → avoids an incorrect action.
  • Missing detail → ask for that slot → completes the request.
  • “It” or “his” unresolved → use conversation context → links the right entity.

How to evaluate it

Test paraphrases, ambiguous requests and multi-turn references; check whether the final action matches the request.

Build the answer in this order

  1. List case functions.
  2. Map request → intent + slots.
  3. Explain missing-context handling.
  4. Test complete tasks.

5. Diagnose the proposed model — change and justify

Common wrong answers and the exact correction
  • User role is not automatically an intent.
  • Intent, slot name and actual value are different.

6. Turn understanding into an exam answer

  • EyeCoach supports ergonomic advice, visual-habit reminders and eye-exercise guidance as high-level user goals.
  • A reminder request needs its reminder type and interval; if the interval is missing, retain the type and ask only for that interval.
  • The follow-up “every 20 minutes” fills the pending interval rather than creating a new unrelated request.

C061

Intent classification

Intent classification predicts the user’s requested goal from their utterance. It is a classification task, not the extraction of every detail.

How it worksWorked exampleChoose & designProblems & fixesExam answer

1. What problem does it solve?

Use when many phrasings must route to the same supported function.

Scenario cueSuitable choiceWhy it fits
Labelled paraphrases availableTrain a classifier with suitable text featuresLearns distinctions between supported request classes.
Small initial collectionSimilarity against representative utterancesCreates a baseline that can be inspected and improved.

2. How it works — what happens and why

  • Training examples connect many utterance forms to a small set of supported goals. The class label describes the operation, not the employee’s occupation.
  • A classifier learns a boundary between intents from labelled text features. A similarity approach instead compares the query with representative known utterances.
  • Both methods need coverage of confusing requests; ordinary word overlap can confuse “show reminder settings” with “set a reminder”.
  • Confidence handling is part of the design. The highest-ranked supported class can still be wrong when the request is unsupported or ambiguous.
Implementation steps and their purpose
  1. Define distinct intent classes from the scenario.
  2. Collect representative utterances with intent labels.
  3. Convert text to TF-IDF features or embeddings.
  4. Train a classifier, or compare against known utterance vectors.
  5. Check confidence and request clarification for unclear input.

3. Separate goal classification from detail extraction

Worked study example: Illustrative EyeCoach training/testing examples; no measured classifier scores are asserted.

All steps shown
UtteranceIntent labelDetail handled elsewhere
How do I adjust screen brightness?Ergonomic adviceFeature=brightness
Remind me to blinkSet visual-habit reminderInterval still missing
Guide me through eye rollingExercise guidanceExercise=eye rolling
What causes night blindness?FAQ question routeSeparate Q1(b) FAQ route; not an extra required Q1(a) intent.

What this tells us: “Software engineer” is a role feature in the work-pattern problem, not a user intent. A high-level intent must describe what the bot is being asked to do.

4. Design the solution and check the result

Data, components and application

  • Similar classes confused → improve representative training examples and boundaries → makes routing clearer.
  • Unsupported request forced into a class → provide fallback → avoids pretending the system can fulfil it.
  • Few labelled examples → test a similarity baseline → reduces initial training needs.

How to evaluate it

Inspect intent mistakes by class and paraphrase; also check whether the system completes the intended task.

Build the answer in this order

  1. Identify supported goals.
  2. Choose text representation and classifier.
  3. Specify uncertain-input handling.
  4. Evaluate routing and task success.

5. Diagnose the proposed model — change and justify

What you observeWhy it happensWhat to changeWhy that helps
Reminder and exercise confusedTraining labels mix goals and topicsRelabel by requested operation and add contrastive examplesWords such as “eyes” occur in multiple goals.
Unsupported request forced into a classNo rejection route existsUse clarification/fallbackNearest class is not necessarily a supported interpretation.
Common wrong answers and the exact correction
  • Classification chooses a goal; NER extracts a detail.
  • Similar wording need not mean identical intent.

6. Turn understanding into an exam answer

  • Define intents by the requested operation: ergonomic advice, reminder setting and exercise guidance, not software engineer or sales executive.
  • Train an intent classifier on labelled paraphrases using consistent text features or compare with representative utterance embeddings.
  • Check confusion between related requests and provide clarification for unsupported or uncertain intent predictions.

C063

Slot detection and information extraction

Slots are named details required by an intent. Information extraction finds the values and links them to the correct entities.

How it worksWorked exampleChoose & designProblems & fixesExam answer

1. What problem does it solve?

Use when the system knows the requested action but still needs who, where, when or another domain-specific field.

Scenario cueSuitable choiceWhy it fits
Common entity typeUse existing NER and validate formatAvoids annotating every ordinary date/location manually.
Domain-specific reminder/exercise wordingRules or trained custom extractorThe domain vocabulary may not appear in a general entity model.

2. How it works — what happens and why

  • Slot extraction answers which details accompany the goal. The same entity value can serve different roles, so its slot name must follow the selected action.
  • Standard dates, locations and names can use NER; custom terms such as reminder type may need domain rules or annotated examples.
  • Validation checks whether a value is usable, not merely present. “Regularly” does not specify a numeric interval if the scheduling service requires one.
  • Conversation state supplies omitted details only when the reference is clear; otherwise clarification is safer than filling a field with a guess.
Implementation steps and their purpose
  1. Define required slot names for each intent.
  2. Extract standard entities such as dates or locations using NER.
  3. Use domain rules or annotated examples for custom fields.
  4. Resolve references to previous entities.
  5. Validate completeness and ask only for missing information.

3. From employee wording to a reminder record

Worked study example: Illustrative utterance trace using functions in the EyeCoach case.

All steps shown

Remind me to blink every 20 minutestype=blink; interval=20 minutesBoth required fields complete

What this tells us: The slot name is “interval”, its value is “20 minutes”, and the intent is “set reminder”. Writing all three as the same concept makes the schema unusable.

4. Design the solution and check the result

Data, components and application

  • Wrong entity type → validate against the slot schema → avoids putting a person into a location field.
  • Custom wording missed → add domain rules or labelled examples → covers case vocabulary.
  • Unclear reference → clarify → avoids filling a slot with a guess.

How to evaluate it

Check extracted values, their field names, reference resolution and downstream action correctness.

Build the answer in this order

  1. Required action → required fields.
  2. Choose entity extraction method.
  3. Handle missing/ambiguous values.
  4. Verify action template.

5. Diagnose the proposed model — change and justify

What you observeWhy it happensWhat to changeWhy that helps
Wrong value attached to wrong actionIntent context ignoredExtract into an intent-specific schemaThe same phrase can have different responsibilities.
Incomplete action executesMissing field treated as empty defaultCheck required slots before service callA default interval would invent the user’s choice.
Common wrong answers and the exact correction
  • A slot is the field; its value is the supplied detail.
  • Detecting an entity alone does not resolve its role.

6. Turn understanding into an exam answer

  • For set-reminder intent, use reminder_type and interval slots; “blink every 20 minutes” supplies their values.
  • Normalize equivalent wording such as “half an hour” to the scheduling service’s interval representation.
  • Resolve “that reminder” using dialogue state and ask for clarification if the reference or a required value is missing.

C064

Dialogue management and generation

Dialogue management decides what happens next; natural language generation (NLG) expresses the result in readable language.

How it worksWorked exampleChoose & designProblems & fixesExam answer

1. What problem does it solve?

Use when a chatbot must handle incomplete requests, remember context and respond after an action.

Scenario cueSuitable choiceWhy it fits
Predictable service confirmationTemplate-based replyKeeps wording tied to actual saved values.
Flexible document explanation requiredGrounded NLG after retrievalMore wording flexibility is useful, but evidence remains necessary.

2. How it works — what happens and why

  • Dialogue state records a pending action, filled slots and relevant prior objects. It is operational memory, not the specialist’s FAQ knowledge base.
  • Dialogue management chooses among waiting, asking for information and acting. The choice depends on whether the action template is complete.
  • Natural language generation turns an actual result into a reply. A template may be sufficient for reliable confirmations; a generative model is optional.
  • State must distinguish pending, completed and failed actions so a later “change it” modifies the intended object rather than creates a duplicate.
Implementation steps and their purpose
  1. Receive intent and slots from NLU.
  2. Check whether required details are complete.
  3. Wait for more input or actively ask for missing details.
  4. Call the relevant API or database once complete.
  5. Generate a response from the returned facts.
  6. Retain useful context for the next turn.

3. Incomplete request, successful save and follow-up change

Worked study example: Illustrative state machine; service outcomes below are assumed for demonstration.

All steps shown

IdleRemind me to blinkPending; interval missingAsk interval
Pending blinkEvery 20 minutesReady to saveCall reminder service

What this tells us: The state machine prevents both premature confirmation and repeated questioning. A general FAQ question can follow a separate retrieval path without entering a reminder-saving state.

4. Design the solution and check the result

Data, components and application

  • Fluent reply without executed action → separate action result from response generation → prevents false confirmations.
  • Lost context → retain relevant recent messages/entities → supports follow-up questions.
  • Invented facts → use templates or grounded generation → keeps responses faithful.

How to evaluate it

Check task completion, retries, correction rate, response time and whether output matches the actual execution result.

Build the answer in this order

  1. Input state → missing fields.
  2. Next dialogue action.
  3. Execute supported operation.
  4. Return grounded response and evaluate completion.

5. Diagnose the proposed model — change and justify

What you observeWhy it happensWhat to changeWhy that helps
Duplicate remindersFollow-up creates a new objectRetain the completed object IDUpdates act on the correct reminder.
Bot says done after failureReply generated before outcomeBranch on success/failure resultUser receives an honest status and can retry.
Common wrong answers and the exact correction
  • NLU understands; dialogue management chooses the next step; NLG phrases the answer.

6. Turn understanding into an exam answer

  • Dialogue management retains the pending reminder and filled slots while collecting missing information.
  • Once complete, it calls the scheduling service and generates confirmation from the returned result.
  • Store the reminder ID so “make it 30 minutes” updates the existing reminder rather than creating a duplicate.

C065

LLM tools and agents

An LLM can translate a natural-language request into a tool call. An agent adds planning, memory and repeated action–observation steps.

How it worksWorked exampleChoose & designProblems & fixes

1. What problem does it solve?

Use when answering needs live data or actions, rather than text generation alone.

Scenario cueSuitable choiceWhy it fits
Only fixed reminder operations neededSimple intent/slot service pipelineFewer moving parts and clear action outcomes.
Several dependent operations requiredAgent with explicit observations and memoryLater choices can depend on real earlier results.

2. How it works — what happens and why

  • The LLM proposes a structured tool invocation; an external tool performs the operation. These are distinct events and should have distinct outputs in the design.
  • A tool interface needs a function name and typed arguments. Missing slots must be resolved before the request is executed.
  • An agent may repeat plan → tool → observation when multiple steps are needed; a one-step API call does not require an elaborate agent framework.
  • Memory keeps useful state and results, while the tool response supplies authoritative current facts. Generated prose must not replace the observation.
Implementation steps and their purpose
  1. Identify the required external operation.
  2. Extract its arguments from the request.
  3. Choose and call the appropriate tool/API.
  4. Read the actual result and report it.
  5. For multiple steps, plan subgoals and repeat after observing each outcome.

3. A natural-language request becomes a verified tool call

What this tells us: For a reminder, replace the weather tool with a scheduling service. The same boundary applies: generating an API-shaped string is not equivalent to saving a reminder.

4. Design the solution and check the result

Data, components and application

  • Made-up result → require actual tool output → distinguishes action from guessing.
  • Wrong arguments → validate required fields → avoids querying the wrong object/date.
  • High latency or private data → consider smaller/local components where appropriate → matches scenario constraints.

How to evaluate it

Check argument correctness, tool success, end-to-end task completion, latency, cost and faithful reporting.

Build the answer in this order

  1. Task requires which tool?
  2. Request → arguments.
  3. Tool result → next action/answer.
  4. Test failure and recovery.

5. Diagnose the proposed model — change and justify

What you observeWhy it happensWhat to changeWhy that helps
Wrong date usedAmbiguous relative dateResolve date before callCorrect syntax can still query the wrong event.
Tool failure concealedLLM fills missing result from general knowledgeRequire observed tool resultPrevents a plausible but false success statement.
Common wrong answers and the exact correction
  • A tool-using chatbot is not automatically fully autonomous.
  • An LLM response does not prove an operation happened.

6. Turn understanding into an exam answer

  • The language component extracts a supported function name and validated arguments before calling the external tool.
  • The tool performs the actual operation; generated API-shaped text is not proof that it succeeded.
  • Use the returned result to answer or choose another step, and report a failure rather than inventing success.
