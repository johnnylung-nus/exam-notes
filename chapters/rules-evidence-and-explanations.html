C009

Deductive reasoning

Deduction applies a general rule to facts to obtain a conclusion. If the rule and premises are true and inference is valid, the conclusion follows logically.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Lecture deduction direction, extended with unknowns

Worked study example: The lecture uses “if raining then street wet”. The following truth-status table explains what that rule does and does not allow.

All steps shown
Known factsRule applicable?Permitted conclusion
Raining=trueYes: IF condition satisfiedStreet wet
Street wet=true onlyNo evidence of rain conditionRain is not deductively proved
Rain status unknownNot yet establishedRequest evidence or leave unresolved
Raining=falseRule condition failsCannot infer street dry

What this tells us: The second row is a hypothesis problem, while the fourth exposes another invalid reversal. A condition not triggering this rule says nothing about other possible causes or rules.

What information this representation preserves

  • Deduction preserves truth from premises to conclusion when the inference is valid. The important exam condition is not simply that the rule exists: all required conditions must be established for the current case. An unknown symptom cannot be silently counted as absent or present to complete a rule.
  • A domain rule and an inference procedure have different roles. “If these findings then this conclusion” belongs in the KB; matching facts to that rule and adding its conclusion is what the engine does. Frames can organise the facts without replacing this matching procedure.
  • An explainable answer names which observations and rules support the conclusion. It must also preserve the rule’s scope: a toy implication in a lecture is not a validated universal clinical statement. Logical correctness cannot establish the truth or completeness of the expert knowledge supplied.
Implementation steps and their purpose
  1. Write the relevant rule clearly.
  2. Match its conditions against present facts.
  3. Check every required condition, including AND/OR and thresholds.
  4. Apply the conclusion and record the rule used.
  5. Continue if the new conclusion triggers another rule.

Prepare the data and validate the representation

Data, components and application

  • Unknown condition → ask or defer → missing is not automatically false.
  • Incorrect domain rule → expert validation and versioning → valid logic cannot rescue false premises.

How to evaluate it

Test ordinary cases, boundaries, missing facts and contradictory rules. Explain which facts and rules support the result.

Build the answer in this order

  1. State facts.
  2. Select applicable rule.
  3. Show inference direction.
  4. State conclusion and assumptions.

C010

Abductive reasoning

Abduction proposes an explanation for observed evidence. The explanation is plausible, not logically guaranteed, because other causes may produce the same evidence.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Illustrative explanatory reasoning

Worked study example: A machine is unexpectedly hot. Causes below are invented to show reasoning, not factual diagnostic rules. Further observations should distinguish causes.

All steps shown
Candidate explanationExplains heat?Useful extra evidenceEffect on reasoning
Blocked airflowYesInspect vent obstructionClear vent weakens candidate
Failed fanYesCheck fan operationStopped fan supports candidate
Heavy workloadYesCheck workload and timingNormal load weakens candidate
Shared observation: hot surfaceAll candidatesRepeat temperature onlyLittle discrimination between causes

What this tells us: A plausible first explanation is not enough. Compare alternatives and request evidence that separates them. In a clinical exam, use only case-supported findings and specialist-validated knowledge; do not invent precise probabilities.

What information this representation preserves

  • Abduction moves from an observation to possible explanations. Because several causes may produce the same effect, its output should be candidates supported by evidence, not a guaranteed fact. The useful tutoring question is “what other explanation could produce this?” rather than merely naming the most familiar cause.
  • Additional observations matter when they discriminate between candidates. Repeating evidence shared by every candidate does not help much. In a system design, follow-up questions should target differences that can change the ranking or rule support, rather than collect every conceivable feature.
  • A diagnostic output and an action output need not be identical. The sample paper distinguishes possible diagnoses from urgency/referral decisions. A direct warning-sign rule can justify urgency even while the diagnosis remains uncertain; forcing every action through one confident diagnosis creates an unnecessary dependency.
Implementation steps and their purpose
  1. List the observed effects.
  2. Identify candidate causes that could explain them.
  3. Check additional evidence and competing explanations.
  4. Rank or update candidates if justified probabilities are available.
  5. Report uncertainty and request discriminating information.

Prepare the data and validate the representation

Data, components and application

  • Single-cause assumption → compare alternatives → several causes can share symptoms.
  • Invented probabilities → use justified prior/likelihood information → labels alone do not quantify uncertainty.

How to evaluate it

Check whether the proposed explanation accounts for the observations and survives contrary evidence. In labelled cases, assess diagnostic/ranking performance.

Build the answer in this order

  1. Name evidence.
  2. Generate plausible causes.
  3. Identify what distinguishes them.
  4. Conclude with stated uncertainty.

Choose the representation from the task

Use for diagnosis, fault finding or interpreting observed effects under uncertainty.

Severe warning sign despite uncertaintyApply justified urgency rule directlyAction urgency is a separate responsibility

Common wrong answers and the exact correction
  • Do not present reverse implication as deduction.
  • Most plausible does not mean certainly true.

An answer you could write

  • Heat is compatible with blocked airflow, failed fan or heavy workload, so I retain alternatives rather than declare one proven cause.
  • I check fan operation and workload because these distinguish candidates; a repeated hot-surface observation alone does not identify the cause.

C011

Inductive reasoning

Induction learns a general pattern from particular observations. Unlike deduction, a pattern supported by examples can still fail on a new case.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Illustrative generalisation from an incomplete sample

Worked study example: A toy dataset contains ten staff cars, all Japanese models. A new sample includes staff not observed in the original collection.

All steps shown
ObservationSupported statementUnsupported stronger statement
10 observed staff cars JapaneseAll observed cases have this propertyEvery staff member drives Japanese cars
Only morning arrivals sampledPattern applies to sampled arrivalsAll shifts are represented
New staff car is non-JapaneseOriginal universal claim has counterexampleThe observation was impossible
Broader representative sample collectedGeneralisation can be reassessedFuture exceptions are now impossible

What this tells us: Induction needs held-out evidence and a clear target population. The car example demonstrates uncertainty of generalisation; it does not recommend this weak variable as a meaningful prediction task.

What information this representation preserves

  • Induction compresses a collection of examples into a reusable hypothesis. It can learn a relationship that was not explicitly written as a rule, but the conclusion remains contingent on the observations: a sample may omit important exceptions or represent only a narrow population.
  • The training row must correspond to the future decision. In the sample diagnosis discussion, current patient features are inputs and the recorded doctor diagnosis is the historical label. Including that label in the input would make training deceptively easy while being unusable when the new patient arrives.
  • Learning a pattern and deploying a decision are different operations. The model predicts from its learned relationship; policy or domain review may still govern what is done with the prediction. This avoids treating a statistical association as a universal rule or assuming a model’s output automatically specifies an action.
Implementation steps and their purpose
  1. Define one training example, input features and desired output.
  2. Collect representative observations.
  3. Fit a hypothesis/model to the training examples.
  4. Tune complexity on validation data.
  5. Evaluate on untouched cases and inspect errors.

Prepare the data and validate the representation

Data, components and application

  • Biased observations → broaden sampling → observed cases may not represent the target population.
  • Memorisation → control complexity and validate → fitting the past is not the same as generalising.

How to evaluate it

Judge performance on unseen representative data, with metrics reflecting the task and costs of mistakes.

Build the answer in this order

  1. Identify examples and target.
  2. Explain learning from instances.
  3. Check sampling and leakage.
  4. Assess generalisation.

Choose the representation from the task

Use when historical labelled examples are available and the goal is to predict unseen outcomes.

No relevant outcome labelsDo not promise supervised prediction immediatelyThe desired target must first be obtained or redefined

  • Training labels must not become prediction-time inputs.

An answer you could write

  • The ten Japanese cars support a pattern only in the observed sample; a non-Japanese staff car would refute the universal claim.
  • For historical diagnosis learning, the current findings are inputs and the recorded diagnosis is the target, which is unavailable as an input for the new patient.

C012

Forward chaining

Forward chaining starts with known facts and repeatedly applies satisfied IF–THEN rules to derive more facts. It is data-driven.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

Lecture forward-chaining chain

Worked study example: Toy lecture facts: temperature 104°F, illness for two months and sore throat. These are lecture rule illustrations, not clinical advice.

All steps shown
CycleMatched ruleNew factWhy now possible
1Temperature above 100°F → feverFeverMeasured temperature known
2Long illness AND fever → suspected infectionSuspected infectionFever was derived in cycle 1
3Sore throat AND suspected infection → strep conclusionToy strep conclusionBoth conditions now available
4No further new factsStopNo productive new inference

What this tells us: The conclusion is explained by the whole dependency chain. Jumping directly from temperature to strep omits two required rules and makes the answer impossible to audit.

Read the relationships and follow the choices

  • Forward chaining grows a set of conclusions from the facts already available. Newly derived facts are not merely displayed: they become usable conditions for later rules. That intermediate working memory is why the engine can produce a multi-step conclusion instead of running unrelated one-off tests.
  • The rule matcher identifies rules whose full conditions currently hold. If more than one rule matches, a documented conflict policy determines which fires next. After firing, matching is repeated because the available facts changed. Detecting unchanged/refired conclusions prevents loops that add no information.
  • In the agreed A-EYE-Web study design, one engine can process diagnostic, triage and action rule groups. Those responsibilities can have different conclusion fields without needing three neural networks. Patient observations, disease frames, rule records and result records remain distinct data structures.
Implementation steps and their purpose
  1. Store current facts in working memory.
  2. Match rule conditions to these facts.
  3. Choose a rule if several can fire.
  4. Add its new conclusions.
  5. Repeat until no new facts arise or the required result is reached.

Choose the method from the problem

Useful when incoming observations should trigger all relevant conclusions, such as diagnosis, warning and action rules.

Data, components and application

  • Many irrelevant rules → index conditions or restrict scope → reduce unnecessary matching.

Trace derived facts and rule IDs. Test missing data, conflicts and termination; expert-supplied clinical rules require validation.

  1. List initial facts.
  2. Show rule firing order.
  3. Add intermediate facts.
  4. Return outputs and reasons.

An answer you could write

  • Temperature104°F triggers the toy fever rule; fever plus two-month illness derives suspected infection; that plus sore throat enables the toy strep conclusion.
  • The engine repeatedly matches and fires rules, storing intermediate facts; patient frames and typed diagnostic/triage/action rules do not require a separate model for each output.

C013

Backward chaining

Backward chaining starts with a goal and works backwards through rules that could establish it. Their conditions become subgoals.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Lecture backward reasoning from a hypothesis

Worked study example: Using the lecture’s toy throat rules, ask whether the strep-throat conclusion can be established. Existing facts are temperature 104°F, two-month illness and sore throat.

All steps shown
Goal/subgoalEvidence or rule requiredStatus
Strep conclusionSore throat AND suspected infectionSore throat known; investigate infection
Suspected infectionLong illness AND feverLong illness known; investigate fever
FeverTemperature above 100°F104°F satisfies condition
Return to original goalAll dependent conditions establishedToy conclusion proved within these rules

What this tells us: The engine investigates backwards but finally applies each implication in its valid forward direction. If temperature were unknown, this route would remain unresolved rather than magically producing fever.

Read the relationships and follow the choices

  • Backward chaining works from a desired conclusion to the evidence needed to establish it. A rule is useful because its THEN part matches the goal; its IF parts become subgoals. This reverses the order of investigation, not the logical direction of the rule itself.
  • A subgoal can be satisfied by an existing fact or by another rule. If several rules could establish the same goal, failure of one route does not automatically disprove the goal: another route may succeed. If facts are unknown and no supporting rule establishes them, the system should report insufficient evidence.
  • The advantage is focus: asking a few goal-relevant questions can be cheaper than deriving every implication of a large fact set. The danger is circular goals or repeatedly exploring the same unsupported chain. Active-goal tracking and a clear unknown/failure distinction are therefore part of the design.
Implementation steps and their purpose
  1. State the goal to prove.
  2. Find rules with that goal in their THEN part.
  3. Check each IF condition against known facts.
  4. Turn unknown conditions into subgoals or questions.
  5. Continue until the goal succeeds or candidate rule paths fail.

Choose the method from the problem

Useful for checking a specific hypothesis or asking only questions relevant to a target conclusion.

Scenario cueSuitable choiceWhy it fits
Specific diagnosis/policy eligibility to verifyBackward chainingLimits investigation to evidence relevant to the goal
Stream of facts needs all consequencesForward chainingA goal-first process may miss other important outputs unless separately checked

Where the graph or reasoning can fail

What you observeWhy it happensWhat to changeWhy that helps
Repeated question chain never endsRules create circular subgoalsTrack current proof stackRevisiting an active unresolved goal cannot supply evidence
System calls disease absent after failed proofKnowledge incompleteReturn unknown/insufficient evidence unless explicitly negatedFailure to prove is not proof of absence
Common wrong answers and the exact correction
  • Do not start by firing every rule from all data.
  • Goal-directed inference does not automatically mean probabilistic reasoning.

Implement it and test the outcome

Data, components and application

  • Circular subgoals → track active goals → avoid recursion loops.
  • Failure to prove → distinguish insufficient knowledge from falsity → unknown is not necessarily absent.

How to evaluate it

Check that every required subgoal has evidence and that the final explanation contains the supporting rule chain.

Build the answer in this order

  1. Identify goal.
  2. Select supporting rules.
  3. Expand conditions into subgoals.
  4. State proven, disproven or unresolved based on evidence.

An answer you could write

  • To check the toy strep goal, I require sore throat and suspected infection; infection requires long illness and fever, and fever is established by104°F.
  • If temperature is unknown, this proof route is unresolved rather than disproved; I may request that evidence or inspect another supporting rule.

C014

Conflict resolution in rule systems

Conflict resolution chooses which rule fires when several rules match in the same cycle. The choice can affect processing order and possibly outputs.

DiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

Choose from the scenario

Needed in rule-engine designs with multiple applicable rules, contradictory actions or exception policies.

Scenario cueSuitable choiceWhy it fits
Several rules matchApply documented conflict policyMatching alone does not specify firing order
Contradictory outputs with no precedenceFlag conflict/request reviewArbitrary selection conceals missing domain policy

Illustrative generic exception policy

Worked study example: A discount system has an ordinary loyalty rule and a restricted-item exclusion. Explicit priorities are invented to show how conflict resolution must be specified.

All steps shown
RuleConditions currently trueConclusionPriority
R1Loyal customerApply discount1
R2Restricted itemDo not discount10
Matcher resultBoth R1 and R2 matchTwo eligible activationsNeed policy
Priority policySelect R2; exclusion overridesNo discount with explanationDeterministic result

What this tells us: The conclusion follows the declared business exception, not a claim that higher priority is a probability. Without override semantics, firing R1 later could reintroduce the forbidden action.

The distinction that changes the answer

  • Matching rules and selecting a rule are separate steps. Several rules may be eligible because their conditions all hold. The conflict set is this collection of activations; it does not necessarily mean the rules logically contradict one another. Selection controls processing when only one is fired per cycle.
  • The lecture offers priority, specificity and recency policies. Priority expresses domain precedence, specificity prefers a rule with more particular matching conditions, and recency uses newer supporting facts. These are policies, not mathematical evidence that the selected conclusion is truer than the others.
  • When conclusions really conflict, a firing-order rule may be insufficient unless the KB defines override/retraction behaviour. An audit trail should show matching rules, the selected policy and its consequence. In a high-impact scenario, unresolved contradictions should be flagged rather than hidden by whichever record happened to be stored first.

What would make the choice wrong?

What you observeWhy it happensWhat to changeWhy that helps
Result changes after database reorderImplicit storage order controls firingRecord priority/specificity strategyBehaviour should follow domain policy, not incidental ordering
Exclusion later undoneNo conclusion override/retraction designSpecify exception precedence and final validationFiring one rule does not remove competing effects automatically
Common wrong answers and the exact correction
  • A conflict set need not imply all rules are logically inconsistent.
  • Choosing one rule does not prove the others false.

Apply the distinction

Data, components and application

  • Hidden priorities → record explicit rule priority → make behaviour reproducible.
  • Conflicting conclusions → detect and escalate or apply defined precedence → arbitrary order can produce unsafe decisions.

How to evaluate it

Create test cases where multiple rules match. Check deterministic selection, explanation and that important exceptions are not bypassed.

Build the answer in this order

  1. Identify matching rules.
  2. Show the conflict.
  3. Name and apply selection policy.
  4. Explain resulting conclusion.

An answer you could write

  • Both the loyalty rule and restricted-item rule match; the documented priority10 exclusion overrides priority1 discount.
  • I record that precedence and check the final action so later firing of the general rule cannot silently restore the prohibited discount.

C015

Case-based reasoning

Case-based reasoning solves a new problem by retrieving similar previous cases, adapting their solutions and retaining the reviewed outcome.

DiagramHow it worksWorked exampleChoose & designProblems & fixes

Illustrative adapting a support solution

Worked study example: A new laptop cannot connect to VPN. The case base contains previous incidents and their outcomes. Values are invented for reasoning practice.

All steps shown
Retrieved caseSimilarityCritical differenceDecision
Old laptop, same VPN symptomHighDifferent operating systemDo not copy configuration blindly
Same OS, expired certificateHighNew certificate still validCause not supported; seek another case
Same OS, blocked network portModerateSame network restriction observedAdapt approved network fix
After applying candidate fixNot a similarity questionConnection succeeds/failsRecord verified outcome

What this tells us: A lower overall similarity case may be more useful if it shares the decisive causal condition. Outcome review distinguishes a successful adaptation from an attractive story.

Read the relationships and follow the choices

  • Case-based reasoning keeps prior problems together with their solutions and outcomes. Retrieval finds experience worth considering, but successful reuse also requires checking differences: an old solution can be wrong for a new case even when several observed features match.
  • Adaptation is the mechanism connecting retrieval to action. It may change a parameter, remove an unsuitable step or select another case when a critical precondition differs. Merely showing the nearest historical record is a retrieval service; explaining how its solution is made applicable completes more of the reasoning task.
  • Retention should include success or failure after review, not simply save every generated answer. Otherwise the case base accumulates confident but untested proposals. Similarity features, adaptation decisions and provenance make the result inspectable and support targeted correction when an apparently similar case failed.
Implementation steps and their purpose
  1. Represent the new case using relevant features.
  2. Retrieve similar stored cases.
  3. Inspect why the retrieved cases are relevant.
  4. Adapt their solutions to the important differences.
  5. Evaluate the proposed solution and retain success/failure for future use.

Choose the method from the problem

Suitable when solved examples are available but writing complete explicit rules is difficult.

Scenario cueSuitable choiceWhy it fits
Rich prior solved cases; incomplete explicit rulesCase-based reasoningExperience can guide solutions with documented adaptation
Need universal policy complianceAdd explicit constraints/rulesA past successful case cannot authorise a forbidden action

Where the graph or reasoning can fail

Nearest case gives wrong remedySimilarity ignores decisive differenceWeight relevant features and inspect preconditionsSurface resemblance does not establish applicability

Common wrong answers and the exact correction
  • Nearest-case retrieval alone omits adaptation and review.
  • A case database is not automatically an explicit rule engine.

Implement it and test the outcome

Data, components and application

  • Superficial similarity → use task-relevant features and differences → a familiar-looking case may need another solution.
  • Bad historical solutions → quality review before retention → errors can otherwise propagate.

How to evaluate it

Measure retrieval relevance and final solution success separately. Explain the matched case, differences and adaptation.

Build the answer in this order

  1. Define case fields.
  2. Specify similarity/retrieval.
  3. Explain adaptation.
  4. Validate and retain reviewed result.

An answer you could write

  • The blocked-network case is useful only if the same restriction is observed; I retain the adapted remedy with its reviewed success or failure.

C016

Bayesian reasoning

Bayesian reasoning updates belief in a hypothesis after observing evidence. It combines the prior belief with how likely that evidence is under competing hypotheses.

CalculationDiagramHow it worksWorked exampleChoose & designProblems & fixesExam answer

Posterior from two evidence branches

P(man | long hair) = (.5×.04) / [(.5×.04)+(.5×.50)]
P(man | long hair)
share of men among long-haired people under these assumptions
  1. Male-and-long-hair mass=.5×.04=.02.
  2. Female-and-long-hair mass=.5×.50=.25.
  3. Total long-hair mass=.27.
  4. Desired posterior=.02/.27≈.074.

Interpret the result: About7.4%, shown as7% in lecture.

Lecture long-hair calculation in probability mass

Worked study example: The lecture assumes equal male/female proportions, 4% long hair among men and 50% among women. This is a toy numerical example, not demographic evidence.

All steps shown
GroupPriorLong-hair likelihoodJoint mass
Men0.50.040.020
Women0.50.500.250
All long-haired peopleBoth groupsSum masses0.270
Men given long hairDesired mass / total0.020 / 0.270About 7.4%

What this tells us: The answer is not 4%: that is long hair given male, the reverse conditional. The observed long-haired group contains much more female probability mass under these assumptions.

Why the calculation works

  • Bayesian updating compares explanations using both the prior frequency and the likelihood of the observed evidence under each explanation. An impressive-looking piece of evidence can still yield a low posterior for a rare cause if the same evidence is common under alternatives.
  • The denominator normalises all possible routes to the evidence. A simple frequency or probability-mass table is often clearer in an exam than an unexplained formula: first calculate each cause-and-evidence mass, then divide the desired mass by their total.
  • A Bayesian model needs actual conditional probabilities and defensible dependencies. Drawing arrows or naming a Bayesian network does not create those values. The sample design discussion permits uncertain diagnostic inference, but warns not to invent numerical tables or turn model confidence directly into urgency.
Implementation steps and their purpose
  1. Name the hypothesis and observed evidence.
  2. Identify prior probabilities.
  3. Identify evidence likelihoods for the competing hypotheses.
  4. Multiply each prior by its evidence likelihood.
  5. Normalise across possible hypotheses to obtain updated beliefs.

Use the result and check it

Data, components and application

  • Ignoring base rate → include prior → evidence alone can mislead.
  • Unsupported conditional probabilities → collect/validate them → a graph or label does not supply numeric values.

How to evaluate it

Check that probabilities are coherent and sum appropriately; compare predictions with observed outcomes where available.

Build the answer in this order

  1. Identify hypothesis/evidence.
  2. Separate prior and likelihood.
  3. Calculate and normalise.
  4. Interpret uncertainty in the scenario.

  3. Multiply prior and likelihoods under the stated conditional-independence assumption.
  4. Normalize the two scores and select the higher class.

Proposed answer points

  • Carryback: (5/9)×(1/5)×(3/5)=1/15. Mistracking: (4/9)×(2/4)×(2/4)=1/9.
  • Normalize: Carryback=0.375; Mistracking=0.625. Predict Mistracking under the Naive Bayes model.

Avoid: Independence is conditional on cause, not unconditional independence of sensors. No zero counts occur in these two likelihoods; smoothing is not required to reproduce this calculation.

First-order / predicate logic

Predicate logic describes objects, their properties and relationships using predicates, variables and quantifiers. It makes the scope of a rule explicit.

Illustrative quantifier and direction checks

Worked study example: Use the lecture rainy-day example. The domain is all days under discussion. Words are shown alongside logic to avoid introducing unexplained notation.

What this tells us: The first and second sentences are different despite sharing vocabulary. The correct representation must preserve both quantifier scope and implication direction.

What information this representation preserves

  • Predicate logic makes explicit which object a statement refers to. A predicate such as Rainy(day) describes a property; a relation such as Treats(doctor,patient) has ordered roles. Swapping arguments changes meaning even though the same entities remain present.
  • Quantifiers describe scope. “Every” imposes a property or implication on all objects in the declared domain; “there exists” only asserts at least one. In an exam, define the domain before formalising so that an accidental choice such as all days versus all recorded rainy days does not weaken the statement.
  • An implication only promises the consequent when the condition holds. It does not assert that the condition occurs, nor that it is the only cause. A readable answer should translate the formal sentence back into ordinary language and test a counterexample; unfamiliar symbols without this explanation add no useful reasoning.
Implementation steps and their purpose
  1. Define the domain of objects.
  2. Name predicates and what each argument means.
  3. Translate relations and conditions.
  4. Choose “for all” versus “there exists” carefully.
  5. Test the statement against a small counterexample.

Prepare the data and validate the representation

Data, components and application

  • Ambiguous scope → state quantifier and domain → everyday language can hide different meanings.
  • Reversing implication → check direction → cause-to-effect does not prove effect-to-cause.

How to evaluate it

Check whether the representation says exactly what the scenario requires. Trace a valid inference using its facts and rules.

Build the answer in this order

  1. Identify entities and relations.
  2. Define predicates.
  3. Write rule and quantifiers.
  4. Explain its meaning in plain words.
