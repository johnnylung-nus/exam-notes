C059

Cognitive-system architecture

A cognitive system turns observations into useful actions using perception, memory and reasoning. Learning is a separate function; applying a fixed rule is not learning.

Problem it solves: Use this to design a complete scenario solution and explain what each component contributes.

How to use it

  1. State the user problem and required output.
  2. Name the inputs and perception process.
  3. Show what information enters memory or the knowledge base.
  4. Connect reasoning to a decision and action.
  5. Show feedback or learning only where the case supports it.

Source check: Exact eleven-box sample-paper diagram is not claimed to be reproduced by these lecture pages.

Example · data issues · evaluation · exam flow

Worked idea

Sample-paper system: eye images → pupil/iris measurements → supplied comparison rule → sign passed to the Web subsystem. Patient details and signs support its separate diagnosis/urgency outputs.

What can go wrong → what to change → why

  • Vague AI box → label inputs, outputs and responsibility → makes the design assessable.
  • Invented training → distinguish building a model from using a fixed rule → preserves case evidence.

How to evaluate

Check each required output, component errors, response time and the consequences of a wrong action.

Answer flow

  1. User need → required functions.
  2. Data → perception output.
  3. Knowledge → reasoning/action.
  4. Test the whole flow.

Exam traps

  • A function is a verb/process; raw data and information are outputs.
  • Not every deployed cognitive system learns during operation.

C060

Natural language understanding

Natural language understanding (NLU) converts a request into an intent plus the details needed to act.

Problem it solves: Use when a scenario asks how a chatbot understands different wordings and uses conversation context.

How to use it

  1. List only functions supported by the case.
  2. Tokenize or otherwise prepare the input.
  3. Identify the requested intent.
  4. Extract the required slot values.
  5. Resolve references using previous turns.
  6. Pass a completed action template to dialogue management.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: “Remind me to look away every 20 minutes” → intent: set reminder; reminder type: look away; interval: 20 minutes.

What can go wrong → what to change → why

  • Ambiguous request → clarify the intent → avoids an incorrect action.
  • Missing detail → ask for that slot → completes the request.
  • “It” or “his” unresolved → use conversation context → links the right entity.

How to evaluate

Test paraphrases, ambiguous requests and multi-turn references; check whether the final action matches the request.

Answer flow

  1. List case functions.
  2. Map request → intent + slots.
  3. Explain missing-context handling.
  4. Test complete tasks.

Exam traps

  • User role is not automatically an intent.
  • Intent, slot name and actual value are different.

C061

Intent classification

Intent classification predicts the user’s requested goal from their utterance. It is a classification task, not the extraction of every detail.

Problem it solves: Use when many phrasings must route to the same supported function.

How to use it

  1. Define distinct intent classes from the scenario.
  2. Collect representative utterances with intent labels.
  3. Convert text to TF-IDF features or embeddings.
  4. Train a classifier, or compare against known utterance vectors.
  5. Check confidence and request clarification for unclear input.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: “Remind me later” and “Set a reminder” share a reminder intent. The interval still needs a slot value before execution.

What can go wrong → what to change → why

  • Similar classes confused → improve representative training examples and boundaries → makes routing clearer.
  • Unsupported request forced into a class → provide fallback → avoids pretending the system can fulfil it.
  • Few labelled examples → test a similarity baseline → reduces initial training needs.

How to evaluate

Inspect intent mistakes by class and paraphrase; also check whether the system completes the intended task.

Answer flow

  1. Identify supported goals.
  2. Choose text representation and classifier.
  3. Specify uncertain-input handling.
  4. Evaluate routing and task success.

Exam traps

  • Classification chooses a goal; NER extracts a detail.
  • Similar wording need not mean identical intent.

C062

TF-IDF and cosine similarity

TF-IDF gives more weight to distinctive words. Cosine similarity compares vector directions to rank related texts.

Problem it solves: Use for a simple text-classification or FAQ-retrieval baseline; embeddings are more suitable when different words express similar meaning.

How to use it

  1. Prepare stored questions using consistent tokenization.
  2. Fit the vocabulary and word weights on the stored/training collection.
  3. Transform stored questions and new query in the same vector space.
  4. Compare query against candidate vectors using cosine similarity.
  5. Return the linked answer only when the match is adequate.
Example · data issues · evaluation · exam flow

Worked idea

Lecture calculation: similarity of D1 with D3 is 0.8246, versus 0.0801 with D2; D3 is the closer candidate. This ranks similarity, not answer truth.

What can go wrong → what to change → why

  • Synonyms share few words → use semantic embeddings → better captures paraphrases.
  • Weak nearest match → clarify/fallback → the closest available answer can still be wrong.

How to evaluate

Test known paraphrases and unrelated questions; measure whether the retrieved approved answer is relevant.

Answer flow

  1. Existing FAQ → stored question-answer links.
  2. Same representation for query and collection.
  3. Similarity rank → answer lookup.
  4. Check relevance and fallback.

Exam traps

  • A vector store is not automatically a knowledge graph.
  • Cosine similarity is not a calibrated probability.

C063

Slot detection and information extraction

Slots are named details required by an intent. Information extraction finds the values and links them to the correct entities.

Problem it solves: Use when the system knows the requested action but still needs who, where, when or another domain-specific field.

How to use it

  1. Define required slot names for each intent.
  2. Extract standard entities such as dates or locations using NER.
  3. Use domain rules or annotated examples for custom fields.
  4. Resolve references to previous entities.
  5. Validate completeness and ask only for missing information.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: “Weather in Seattle today” → intent: weather forecast; location slot: Seattle; start-date slot: today. “There tomorrow” needs the previous location.

What can go wrong → what to change → why

  • Wrong entity type → validate against the slot schema → avoids putting a person into a location field.
  • Custom wording missed → add domain rules or labelled examples → covers case vocabulary.
  • Unclear reference → clarify → avoids filling a slot with a guess.

How to evaluate

Check extracted values, their field names, reference resolution and downstream action correctness.

Answer flow

  1. Required action → required fields.
  2. Choose entity extraction method.
  3. Handle missing/ambiguous values.
  4. Verify action template.

Exam traps

  • A slot is the field; its value is the supplied detail.
  • Detecting an entity alone does not resolve its role.

C064

Dialogue management and generation

Dialogue management decides what happens next; natural language generation (NLG) expresses the result in readable language.

Problem it solves: Use when a chatbot must handle incomplete requests, remember context and respond after an action.

How to use it

  1. Receive intent and slots from NLU.
  2. Check whether required details are complete.
  3. Wait for more input or actively ask for missing details.
  4. Call the relevant API or database once complete.
  5. Generate a response from the returned facts.
  6. Retain useful context for the next turn.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: reminder intent with no interval → ask “How often?” → user supplies 20 minutes → save reminder → confirm the actual saved settings.

What can go wrong → what to change → why

  • Fluent reply without executed action → separate action result from response generation → prevents false confirmations.
  • Lost context → retain relevant recent messages/entities → supports follow-up questions.
  • Invented facts → use templates or grounded generation → keeps responses faithful.

How to evaluate

Check task completion, retries, correction rate, response time and whether output matches the actual execution result.

Answer flow

  1. Input state → missing fields.
  2. Next dialogue action.
  3. Execute supported operation.
  4. Return grounded response and evaluate completion.

Exam traps

  • NLU understands; dialogue management chooses the next step; NLG phrases the answer.

C065

LLM tools and agents

An LLM can translate a natural-language request into a tool call. An agent adds planning, memory and repeated action–observation steps.

Problem it solves: Use when answering needs live data or actions, rather than text generation alone.

How to use it

  1. Identify the required external operation.
  2. Extract its arguments from the request.
  3. Choose and call the appropriate tool/API.
  4. Read the actual result and report it.
  5. For multiple steps, plan subgoals and repeat after observing each outcome.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example: ask for Singapore weather on a date → extract location/date → call weather API → use returned temperature and conditions in the response.

What can go wrong → what to change → why

  • Made-up result → require actual tool output → distinguishes action from guessing.
  • Wrong arguments → validate required fields → avoids querying the wrong object/date.
  • High latency or private data → consider smaller/local components where appropriate → matches scenario constraints.

How to evaluate

Check argument correctness, tool success, end-to-end task completion, latency, cost and faithful reporting.

Answer flow

  1. Task requires which tool?
  2. Request → arguments.
  3. Tool result → next action/answer.
  4. Test failure and recovery.

Exam traps

  • A tool-using chatbot is not automatically fully autonomous.
  • An LLM response does not prove an operation happened.

C066

Vision cognition pipeline

Vision cognition goes beyond naming objects: pixels become features, objects, relations, context and a useful decision.

Problem it solves: Use when a scenario needs a judgement or action from images, not just an object label.

How to use it

  1. Define what decision the user needs.
  2. Capture suitable images.
  3. Extract relevant objects, regions or measurements.
  4. Represent relations and apply domain knowledge.
  5. Produce a judgement with uncertainty.
  6. Trigger the specified action or review.
Example · data issues · evaluation · exam flow

Worked idea

Lecture PPE case: camera → detect worker and PPE → segmentation checks coverage → rule engine checks the PPE list → flag missing/incorrect items → reviewer confirms.

What can go wrong → what to change → why

  • Poor lighting/occlusion → improve capture or request another view → missing evidence cannot support a confident judgement.
  • Object detected but placement wrong → inspect regions/relations → presence alone does not prove compliance.
  • Unsupported inference → separate visible evidence from interpretation → exposes uncertainty.

How to evaluate

Check perception, interpretation, judgement, usability and consequences of errors separately.

Answer flow

  1. Required decision.
  2. Perception output needed.
  3. Rules/context → decision.
  4. Check failure and response.

Exam traps

  • “Mask detected” does not prove “mask worn correctly”.
  • Do not invent hidden details from one image.

C067

Marr’s three levels

Marr’s analysis separates what problem is solved, which representations/processes solve it, and how the solution is physically implemented.

Problem it solves: Use to explain a vision-system design at the right level rather than mixing the goal, algorithm and hardware.

How to use it

  1. Computational level: state the goal and why it matters.
  2. Algorithmic level: choose representations and operations.
  3. Implementation level: identify camera, device and software deployment.
  4. Check that the selected operations actually support the goal.
Example · data issues · evaluation · exam flow

Worked idea

Lecture PPE example: goal = check correct wearing; algorithm = detection, segmentation, pose and rule checking; implementation = camera, model, edge device and dashboard.

What can go wrong → what to change → why

  • Hardware listed as goal → separate levels → makes the answer address the question.
  • Algorithm without decision criteria → define required compliance knowledge → connects processing to the goal.
  • Over-detailed implementation → match requested abstraction → avoids wasting exam time.

How to evaluate

Trace one required output through all three levels; check feasibility and whether the algorithm answers the stated problem.

Answer flow

  1. What and why?
  2. Representations and processing?
  3. Physical realization?
  4. Does the design meet the goal?

Exam traps

  • Do not confuse these three analysis levels with early vision → recognition → cognition.
  • Primal sketch, 2.5D sketch and 3D model are another lecture distinction.

C068

Detection vs segmentation

Classification labels the whole image; detection returns object boxes and labels; segmentation assigns labels to pixels.

Problem it solves: Choose the output detail the task needs. Measurement of exact areas usually needs segmentation rather than only detection.

How to use it

  1. Identify the requested output: class, location or boundary.
  2. Choose classification, detection or segmentation accordingly.
  3. Prepare matching labels for training/evaluation.
  4. Convert model outputs into the required measurements or decisions.
  5. Inspect difficult capture conditions.
Example · data issues · evaluation · exam flow

Worked idea

Sample-paper mapping: locate an eye region, identify pupil/iris pixels, count them and calculate their size ratio. A whole-image eye label alone cannot supply pixel counts.

What can go wrong → what to change → why

  • Boxes include background → segment the region → improves area measurements.
  • Tiny/occluded objects → improve capture and representative examples → reduces missed regions.
  • Good object score but wrong decision → evaluate the derived measurement too → downstream errors matter.

How to evaluate

Check the relevant labels/boxes/masks, boundary errors and final measurement or task correctness.

Answer flow

  1. Required information.
  2. Choose output granularity.
  3. Model output → measurement.
  4. Evaluate downstream consequence.

Exam traps

  • A bounding box is not an exact object boundary.
  • Detection success does not establish the correctness of a later rule.

C069

Visual attention and context

Visual attention selects relevant regions. Bottom-up attention follows striking image features; top-down attention follows the task and context.

Problem it solves: Use when a full scene contains distractions or recognition depends on surrounding relationships.

How to use it

  1. State the target and task.
  2. Identify useful visual cues such as contrast or edges.
  3. Use likely location and scene context to focus processing.
  4. Inspect the selected regions and related objects.
  5. Retain uncertainty when context conflicts with evidence.
Example · data issues · evaluation · exam flow

Worked idea

Lecture distinction: a bright/high-contrast region attracts bottom-up attention; checking whether a worker’s mask covers the nose is guided by the PPE task.

What can go wrong → what to change → why

  • Bright distractor selected → use task/context guidance → saliency alone may miss the relevant object.
  • Expected object imagined → verify visible evidence → context is guidance, not proof.
  • Relevant region hidden → request another view → attention cannot recover absent pixels.

How to evaluate

Check whether relevant objects/relations are found under distraction, unusual context and changed camera angles.

Answer flow

  1. Task and target.
  2. Bottom-up cues versus top-down guidance.
  3. Context-supported interpretation.
  4. Test distractors and uncertainty.

Exam traps

  • Self-attention is learned relationships between patches; it is not identical to visual saliency.
  • Expected does not mean observed.

C070

Vision-language models

A vision-language model (VLM) processes image/video and text together. It can link questions to visual regions and generate descriptions or judgements.

Problem it solves: Use for image questions or visual reasoning where language and scene information must interact.

How to use it

  1. Provide the image and a precise task prompt.
  2. Ask what is visibly present.
  3. Ground referenced objects in relevant regions.
  4. Apply the required relationships or domain rules.
  5. Separate evidence, inference and uncertainty in the output.
Example · data issues · evaluation · exam flow

Worked idea

Lecture PPE exercise asks “Is PPE correctly worn?” with three sections: observable evidence, inference and uncertainty. Missing views should be stated rather than filled with guesses.

What can go wrong → what to change → why

  • Hallucinated details → require evidence-grounded output → fluent language can exceed visual evidence.
  • Wrong relation → check object locations/coverage → detected objects alone do not resolve the question.
  • Unseen setting → test representative cases → broad pretraining does not prove domain reliability.

How to evaluate

Evaluate objects, grounding, relation/judgement accuracy and usefulness of uncertainty to the user.

Answer flow

  1. Question → required visual evidence.
  2. Ground entities/relations.
  3. Apply case knowledge.
  4. Evaluate judgement and missing information.

Exam traps

  • A plausible caption does not prove correct reasoning.
  • Use a VLM only if it serves the case requirements.

C071

Audio sampling and coding

Sampling records audio amplitude at time intervals; quantization maps amplitude to discrete levels. They control different parts of the digital representation.

Problem it solves: Use when choosing or diagnosing audio input formats for speech processing.

How to use it

  1. Check the signal frequencies that need preservation.
  2. Choose an adequate sampling rate.
  3. Choose sample precision and encoding.
  4. Use the sample rate/format expected by the recognition model.
  5. Check the captured file before recognition.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative calculation: 16,000 samples/second × 16 bits/sample = 256,000 bits/second for one uncompressed mono channel, before file overhead.

What can go wrong → what to change → why

  • Undersampling → choose sufficient rate before capture → lost frequency detail cannot be restored merely by changing a file header.
  • Wrong input rate → correctly resample → matches model assumptions.
  • Low-amplitude distortion → consider suitable quantization/encoding → lecture contrasts PCM with logarithmic coding.

How to evaluate

Listen/check for clipping and format errors, then compare speech-recognition quality on representative recordings.

Answer flow

  1. Signal needs.
  2. Sampling rate versus amplitude precision.
  3. Model-compatible conversion.
  4. Test input and recognition.

Exam traps

  • Sample rate is not bit depth.
  • Upsampling does not invent lost original detail.

C072

Spectrogram and audio features

A spectrogram shows which frequencies are present over time. It is built by applying Fourier analysis to short signal windows.

Problem it solves: Use when sound changes during an event; a whole-recording frequency summary would hide when changes happen.

How to use it

  1. Capture audio with a suitable rate.
  2. Split it into short time windows.
  3. Apply short-time Fourier transformation.
  4. Represent frequency strength across the windows.
  5. Use this representation for visual inspection or a learned audio task.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: a machine sound changes halfway through a recording. A spectrogram can show when the new frequency pattern appears, helping localize a possible abnormal segment.

What can go wrong → what to change → why

  • Time order lost in one spectrum → use windowed analysis → preserves changing frequency patterns.
  • Noise dominates features → improve recording/preprocessing → cleaner task evidence.
  • Input format mismatch → match model requirements → avoids treating the wrong sampling scale as meaningful.

How to evaluate

Check whether features distinguish the target events on unseen recordings, rather than only producing a visually clear plot.

Answer flow

  1. What sound event matters?
  2. Need time and frequency information?
  3. Extract windowed representation.
  4. Evaluate the downstream task.

Exam traps

  • Frequency strength is not a word transcript.
  • A spectrogram is a representation, not the final classifier.

C073

Speech recognition

Automatic speech recognition converts recorded speech to text. NLU then determines what that text means for the task.

Problem it solves: Use for voice interfaces; recognition and understanding are separate stages with separate errors.

How to use it

  1. Capture speech using the expected audio format.
  2. Preprocess the recording where necessary.
  3. Run the speech-recognition model.
  4. Pass the transcript to NLU/dialogue processing.
  5. Allow correction or retry when the task-critical words are uncertain.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: recognition hears “set timer for fifty” instead of “fifteen”; even a largely correct transcript can trigger the wrong duration unless the interface checks the critical value.

What can go wrong → what to change → why

  • Noise/reverberation → improve recording and representative tests → reduces recognition errors.
  • Overlapping speakers → manage input conditions → one transcript may mix sources.
  • Spontaneous speech or accents → test realistic user speech → read-speech performance is insufficient.

How to evaluate

Use word error rate for transcript quality, then task completion, corrections and retries for the complete interface.

Answer flow

  1. Voice task.
  2. Audio → transcript → intent/action.
  3. Likely recognition failures.
  4. Measure transcript and task success.

Exam traps

  • Speech recognition identifies words; speaker recognition identifies who spoke.
  • Low overall word error can still hide an important slot error.

C074

Text-to-speech

Text-to-speech converts text into spoken audio. It provides the spoken-response side of a voice interface.

Problem it solves: Use when users need to hear responses or cannot easily read a display.

How to use it

  1. Obtain the final grounded response text.
  2. Prepare numbers, dates and domain terms for clear speech.
  3. Generate spoken audio.
  4. Deliver it through the chosen output device.
  5. Check that users understand the important content.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: after a reminder is actually saved, the system speaks its type and interval. The speech should express the stored result, not invent a successful action.

What can go wrong → what to change → why

  • Fluent but wrong content → verify text before synthesis → speech generation cannot repair a factual error.
  • Mispronounced names/numbers → test task vocabulary → important details must remain understandable.
  • Slow response → evaluate the complete pipeline → synthesis adds to interaction time.

How to evaluate

Check intelligibility, pronunciation and whether users correctly understand the response; measure task success and response time.

Answer flow

  1. Why spoken output?
  2. Grounded text → speech.
  3. Domain vocabulary and delivery issues.
  4. Evaluate comprehension and interaction.

Exam traps

  • Text-to-speech is not speech recognition.
  • Good voice quality does not establish content correctness.

C075

Whisper

The lecture presents Whisper as a multilingual, multitask speech model for recognition, speech translation and language recognition.

Problem it solves: Use when choosing a pretrained model for converting varied-language speech into a task-usable output.

How to use it

  1. Identify whether the required output is transcript, translation or language.
  2. Prepare audio in the format expected by the chosen implementation.
  3. Select a model size suited to device and time constraints.
  4. Test real accents, noise and vocabulary.
  5. Connect the output to the downstream task and recovery flow.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: for an employee voice request, use transcription first and then intent/slot extraction. Translating speech is a different chosen output task.

What can go wrong → what to change → why

  • Large model too slow → compare suitable sizes → trades resource use against measured quality.
  • Domain terms wrong → evaluate those terms explicitly → average performance may hide critical errors.
  • Multilingual claim overtrusted → test actual languages/conditions → pretraining is not a local guarantee.

How to evaluate

Compare transcript errors and task completion alongside latency and resource use on the intended deployment.

Answer flow

  1. Required speech task.
  2. Pretrained model and size.
  3. Deployment/data mismatch.
  4. Model and system evaluation.

Exam traps

  • Speech translation is not identical to same-language transcription.
  • Do not assume a pretrained model needs no testing.

C076

Wav2Vec self-supervised learning

Wav2Vec2.0 is presented as self-supervised speech representation learning: learn useful audio features from speech before using task labels.

Problem it solves: Use when unlabelled audio is available but transcribed or otherwise labelled target data is limited.

How to use it

  1. Collect representative unlabelled speech.
  2. Encode audio with a CNN; mask selected time-step features.
  3. Learn contextual representations matching quantized audio targets: discrete targets created from the audio itself.
  4. Freeze or fine-tune the pretrained model with labelled target data.
  5. Evaluate on separate speakers/recordings.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: learn from untranscribed workplace audio, then adapt with a smaller set of labelled utterances for recognition. The task still needs appropriate labelled evaluation data.

What can go wrong → what to change → why

  • Little labelled data → reuse pretrained features → reduces learning from scratch.
  • Pretraining audio differs from deployment → adapt and test locally → representations may not transfer perfectly.
  • Train/test speakers overlap → separate them → avoids optimistic generalization claims.

How to evaluate

Assess the downstream speech task and complete interaction, not just the pretraining objective.

Answer flow

  1. Unlabelled versus labelled data available.
  2. Self-supervised pretraining.
  3. Target-task adaptation.
  4. Unseen-speaker/task evaluation.

Exam traps

  • Self-supervised does not mean no learning target.
  • Do not describe it as ordinary supervised training on transcripts.

C077

Audio/system evaluation

Evaluate the model, the intelligent task and the complete system separately. A good component score does not prove that users succeed.

Problem it solves: Use whenever an exam asks whether a system works or whether a proposed change is worthwhile.

How to use it

  1. Identify the output the model predicts.
  2. Choose a matching task measure.
  3. Test on unseen, representative cases.
  4. Measure complete user outcomes.
  5. Check robustness, speed and error consequences.
  6. Compare the changed system with the original under the same conditions.
Example · data issues · evaluation · exam flow

Worked idea

Lecture speech example: microphone → preprocessing → ASR transcript → dialogue system → response. Word error rate tests transcription; task completion, retries and abandonment test the interaction.

What can go wrong → what to change → why

  • Only accuracy reported → add task and system checks → component quality may not deliver value.
  • Easy test data → use realistic noise/users → tests deployment conditions.
  • Fast but wrong response → evaluate quality and latency together → speed alone is insufficient.

How to evaluate

Word error rate = substitutions + deletions + insertions, divided by reference words. For 10 reference words and 2 such errors, WER is 20% (illustrative).

Answer flow

  1. Required outcome.
  2. Model/task measure.
  3. System/user measure.
  4. Compare baseline and failure cases.

Exam traps

  • Evaluation data must not be reused as training examples.
  • A lower error score need not improve every user task.

C078

Multimodal cognition

Multimodal cognition combines different input types and knowledge to interpret a situation more completely than one modality alone.

Problem it solves: Use when images, speech, sensor measurements or case details provide complementary evidence.

How to use it

  1. State what each input contributes.
  2. Process each modality into useful information.
  3. Align observations belonging to the same event.
  4. Combine representations or decisions.
  5. Apply knowledge to the combined evidence.
  6. Return a decision with uncertainty and a defined action.
Example · data issues · evaluation · exam flow

Worked idea

Sample-paper mapping: the App supplies an eye-response sign; the Web also receives patient details and other signs. Together they support reasoning outputs, rather than treating an image label as the whole system.

What can go wrong → what to change → why

  • Inputs refer to different times/people → align records → prevents invalid combinations.
  • One input unreliable → represent quality or seek another reading → extra modalities are not automatically helpful.
  • Black-box fusion → label what passes between components → makes the design explainable.

How to evaluate

Compare with single-input baselines, test missing/noisy inputs and check full task correctness.

Answer flow

  1. Need for multiple evidence types.
  2. Per-input processing.
  3. Alignment and combination.
  4. Decision and evaluation.

Exam traps

  2. Separate assumptions from evidence.
  3. Check the inference or calculation.

C081

Soar architecture

Soar’s lecture example separates long-term action knowledge from the current state and constructed search states in working memory.

Problem it solves: Use when explaining how a cognitive architecture represents a problem and selects actions toward a goal.

How to use it

  1. Represent current state and goal in working memory.
  2. Keep reusable objects, relations and operators in long-term memory.
  3. Apply only legal operators to generate next states.
  4. Search the resulting state space.
  5. Select a path that reaches the goal and meets the stated cost preference.

Worked idea

Lecture jug sequence: (0,0) → fill 3L (0,3) → pour into 5L (3,0) → refill 3L (3,3) → pour into 5L (5,1). Goal: 1L remains in the 3L mug.

RAG and knowledge-graph cognition

RAG retrieves relevant source material before an LLM writes an answer. A knowledge graph represents explicit entities and relationships for linked knowledge use.

  3. Retrieve material relevant to the query.
  4. Provide that material with the question to generation.
  5. Check that the answer stays within the evidence.

Paper addition · HMM

HMM: weekly query patterns

A hidden Markov model (HMM) explains an ordered observation sequence using hidden states that can change over time. For this classification task, a defensible design trains one HMM for each work-pattern class.

Problem it solves: Recognize software-engineer pattern A versus sales-executive pattern B from a week of chatbot query records.

How to use it

  1. Prepare one ordered daily-count sequence per employee-week: ergonomics, visual-habit and eye-exercise counts.
  2. Propose hidden daily work/eye-care-need modes, such as sustained screen work versus varied activity; these are modelling assumptions.
  3. Learn initial-state probabilities, transitions between daily modes and emissions: how likely each query-count observation is under a mode.
  4. Fit separate HMMs using labelled A and B training weeks.
  5. Score a new weekly sequence under each HMM; choose the better-supported class, accounting for class priors if unequal.

Source check: Exam-required extension: no substantive HMM teaching pages were found in the 36 core lecture texts. This is a proposed coherent architecture, not an official key. The table is incomplete; no numerical HMM probabilities or measured performance are asserted.

Example · data issues · evaluation · exam flow

Worked idea

Illustrative observation: day 1 counts (3,6,1). It is observable query behaviour, not the hidden work mode. The employee’s job class stays fixed across the week while latent daily modes may change.

What can go wrong → what to change → why

  • Only a few table rows shown → obtain complete training weeks → cannot estimate reliable probabilities from ellipses.
  • Similar query counts across roles → test unseen employees → proxy behaviour may not separate work patterns.

How to evaluate

Hold out employees/weeks; compare A/B classification errors and whether sequence order adds useful evidence.

Answer flow

  1. State the class being predicted.
  2. Define hidden state versus observed daily counts.
  3. Explain transitions, emissions and one-model-per-class scoring.
  4. Validate on unseen employee-weeks.

Exam traps

  • Do not alternate software-engineer/sales-executive job labels as daily activity states without justification.
  • Query counts are observations; their temporal order matters.
