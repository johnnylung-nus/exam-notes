C029

Reasoning-system architecture

A reasoning-system architecture connects inputs, structured knowledge, an inference procedure, outputs and validation. Naming “AI” alone does not explain how a decision is made.

Problem it solves: Use when asked to design a complete system and show component responsibilities, interfaces or knowledge structures.

How to use it

  1. Extract user need, inputs and required outputs from the case.
  2. Choose a representation matched to available knowledge.
  3. Name the actual inference procedure.
  4. Draw component boxes with labelled data arrows.
  5. Add missing/conflict handling, explanations and validation.
Example · data issues · evaluation · exam flow

Worked idea

Sample A-EYE-Web study design: findings → validation → patient facts; disease frames and rules feed a forward-chaining engine; results include candidate diagnoses, urgency and action.

What can go wrong → what to change → why

  • Overcomplicated design → one coherent procedure first → separate outputs do not require separate models.
  • Unclear arrows → label information passed → architecture must show how components cooperate.

How to evaluate

Check requirement coverage, representative cases, data structures, explanations and failure handling. State assumptions instead of inventing case facts.

Answer flow

  1. Read required scope.
  2. Specify components and data.
  3. Explain processing.
  4. Validate outputs and limitations.

Exam traps

  • Knowledge base is storage/representation; inference engine is the procedure.
  • Use black boxes for subsystem relationship questions and internals when requested.

C030

Rules + ML integration

Rules plus ML separates prediction from policy. ML estimates an outcome; rules use that estimate and other facts to choose permitted actions.

Problem it solves: Use when learned patterns help prediction but business, safety or operational constraints must determine decisions.

How to use it

  1. Define the ML prediction target and input data.
  2. Train/evaluate the predictor.
  3. Pass prediction and relevant facts to the rule engine.
  4. Apply thresholds, exceptions and constraints.
  5. Return action with prediction evidence and fired-rule explanation.
Example · data issues · evaluation · exam flow

Worked idea

Lecture fraud example: transaction → fraud score → rules checking limits, country and account risk → approve, review or reject.

What can go wrong → what to change → why

  • Score treated as action → define policy mapping → probability alone does not encode allowed behaviour.
  • Stale rules/model → monitor both → either part can fail independently.

How to evaluate

Evaluate prediction quality separately from decision outcomes, constraint violations and review workload. Test threshold boundaries and conflicts.

Answer flow

  1. Separate prediction from decision.
  2. Draw labelled flow.
  3. State rule inputs and policy.
  4. Validate model and final action.

Exam traps

  • High confidence is not automatically high urgency.
  • Hybrid design needs a reason for each component, not a catalogue of algorithms.

C031

Knowledge graph + LLM integration

A KG–LLM workflow uses structured graph facts to support natural-language answers. The language model can interpret a question and explain retrieved relationships.

Problem it solves: Useful when users ask questions requiring connected entity knowledge, but need readable answers.

How to use it

  1. Identify entities and relations in the question.
  2. Construct a controlled graph query.
  3. Retrieve relevant facts/paths.
  4. Give retrieved evidence to the language model.
  5. Generate a concise answer with supporting facts and check it against evidence.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example asks which approved drugs target EGFR mutations. The graph lookup supplies drug–gene–disease relationships; the LLM explains them.

What can go wrong → what to change → why

  • Wrong entity/query → validate query and entity mapping → fluent language can hide retrieval errors.
  • Incomplete KG → state missing evidence → graph grounding cannot create missing verified facts.

How to evaluate

Evaluate query correctness, retrieved evidence coverage and whether every answer claim is supported. Check source freshness.

Answer flow

  1. State required relationships.
  2. Show query/retrieval step.
  3. Explain LLM role.
  4. Validate evidence and final answer.

Exam traps

  • A language model does not automatically make graph facts trustworthy.
  • Predicted/extracted links need provenance and validation.

C032

Retrieval-augmented generation

Retrieval-augmented generation retrieves relevant external material and supplies it to an LLM before it generates an answer. It can improve grounding and freshness.

Problem it solves: Choose when a language interface must answer from an approved or changing document collection.

How to use it

  1. Prepare approved documents with source identifiers.
  2. Split/index searchable content using suitable text or embeddings.
  3. Retrieve relevant passages for the user query.
  4. Provide passages and the question to the LLM.
  5. Return an evidence-grounded answer or clarify when retrieval is insufficient.
Example · data issues · evaluation · exam flow

Worked idea

Lecture HR example: retrieve travel/remote-work policies, then generate an answer about working overseas with the relevant sections.

What can go wrong → what to change → why

  • Wrong passage → improve retrieval/chunking → generation cannot compensate for absent evidence.
  • Unsupported additions → constrain answer to evidence and verify → RAG reduces but does not eliminate hallucination.

How to evaluate

Check retrieval relevance/coverage and answer faithfulness separately. Test unanswered questions and stale/conflicting policies.

Answer flow

  1. Identify knowledge source.
  2. Describe retrieval.
  3. Describe grounded generation.
  4. Add verification/fallback.

Exam traps

  • Semantic FAQ retrieval returning a stored answer is not automatically RAG.
  • Retrieval does not retrain the LLM.

C033

Agentic orchestration

Agentic orchestration coordinates planning, tools, memory and feedback over multiple steps. An agent chooses actions, observes their results and adjusts its plan.

Problem it solves: Useful when a task needs several operations or external tools, rather than one prediction or answer.

How to use it

  1. Define goal, constraints and available tools.
  2. Break the task into useful substeps.
  3. Select a tool with explicit inputs.
  4. Inspect returned observations and update task state.
  5. Validate completion or revise the plan; enforce a stopping limit.
Example · data issues · evaluation · exam flow

Worked idea

Lecture travel assistant: collect requirements, search options, use a calculator and combine results into a feasible client-visit plan.

What can go wrong → what to change → why

  • Tool error/loop → check results and limit retries → repeated actions are not progress.
  • Unsupported plan → validate dates, resources and constraints → plausible text is not an executable solution.

How to evaluate

Evaluate task completion, constraint satisfaction, tool errors, cost and traceable evidence. Compare with a simpler fixed workflow.

Answer flow

  1. Explain why multiple steps are needed.
  2. Draw plan–tool–observation loop.
  3. State memory/constraints.
  4. Show validation and stopping.

Exam traps

  • More agents are not automatically better.
  • Tool outputs are observations to check, not guaranteed truth.

C034

Market basket analysis

Market basket analysis finds items that occur together and expresses associations as IF-condition THEN-consequent rules. The basket definition determines what association means.

Problem it solves: Useful for cross-selling or discovering history-to-outcome patterns when data can be represented as transactions.

How to use it

  1. Define the transaction unit and count.
  2. Join/clean records and encode facts as items.
  3. Bin numerical/time values where appropriate.
  4. Mine frequent itemsets and generate rules.
  5. Filter by support, confidence and application relevance.
Example · data issues · evaluation · exam flow

Worked idea

Sample study answer: one basket per consultation contains prior diagnoses, prior treatments, linked elapsed-time categories and current diagnosis. Patient ID/date organise history; they are not ordinary mined items.

What can go wrong → what to change → why

  • Temporal leakage → use only pre-consultation history → future facts are unavailable at prediction.
  • Wrong consequent → keep current-diagnosis RHS for diagnostic rules → co-occurrence mining does not know the application target.

How to evaluate

Check threshold counts, useful consequent, held-out performance and expert relevance. Association is neither causation nor treatment justification.

Answer flow

  1. Unit → contents → encoding → count.
  2. Mine rules.
  3. Filter target/time roles.
  4. Validate useful associations.

Exam traps

  • Elapsed time since treatment differs from treatment duration.
  • Similar words do not prove identical clinical meanings.

C035

Association-rule support

Support is the proportion of all baskets containing every item in the whole rule: both the condition and the consequent. It measures how common that combination is.

Problem it solves: Use to reject extremely rare associations or calculate whether a rule meets the supplied minimum support.

How to use it

  1. Count all eligible baskets.
  2. Count baskets containing the complete condition and consequent.
  3. Divide complete-rule count by total basket count.
  4. Compare with the supplied support threshold.
  5. Keep basket unit/count consistent across calculations.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: 100 consultation baskets; 20 contain the condition and 12 contain condition plus outcome. Rule support =12/100=12%. Reverse direction has the same support.

What can go wrong → what to change → why

  • Rare but important rule → justify threshold/domain review → a high threshold may discard useful rare cases.
  • Duplicated transactions → deduplicate at the defined unit → inflated counts distort evidence.

How to evaluate

Recalculate counts and check denominator. Report percentage or count exactly as requested; minimum count 3 is different from 3%.

Answer flow

  1. Define basket unit.
  2. Identify whole itemset.
  3. Count and divide by all baskets.
  4. Apply threshold and explain coverage.

Exam traps

  • Support denominator is not just condition baskets.
  • High support alone does not make a rule predictive.

C036

Association-rule confidence and lift

Confidence asks how often the consequent occurs when the condition occurs. Lift compares that confidence with how common the consequent already is.

Problem it solves: Use to judge rule reliability and whether a high confidence merely reflects a popular outcome.

How to use it

  1. Count baskets with the condition.
  2. Count baskets with both sides.
  3. Confidence = both count / condition count.
  4. For lift, divide confidence by overall consequent frequency.
  5. Apply supplied thresholds and domain constraints.

Source check: Support and confidence are explicitly taught on Day2 p32; lift is an explanatory extension and was not located as a substantive topic in the inspected foundation pages.

Example · data issues · evaluation · exam flow

Worked idea

Illustrative: both=12, condition=20, total=100 gives 60% confidence. If the consequent occurs in 50% of baskets, lift=0.60/0.50=1.2: a positive association beyond baseline.

What can go wrong → what to change → why

  • Popular consequent → compare baseline/lift → high confidence can be uninformative.
  • Small condition count → require support and validate → confidence from a few examples is unstable.

How to evaluate

Check rule direction, counts and holdout behaviour. Lift above one suggests positive association, not causality or clinical validity.

Answer flow

  1. Calculate support/confidence.
  2. Check baseline prevalence.
  3. Apply thresholds.
  4. Explain relevance and limitations.

Exam traps

  • Reverse confidence usually differs.
  • There is no universal confidence cutoff.

C037

Content-based recommendation

Content-based recommendation matches item attributes to a user’s preferences or previously liked items. It does not require other users to have rated the same item.

Problem it solves: Useful when item descriptions/features are available, including new items with no interaction history.

How to use it

  1. Extract structured item features or text vectors.
  2. Build a user profile from declared preferences or liked items.
  3. Use the same feature representation for both.
  4. Compute similarity and rank unseen eligible items.
  5. Add controlled variety and evaluate relevance.
Example · data issues · evaluation · exam flow

Worked idea

Lecture movie pattern: represent genre/director/text, form a profile from liked movies, then recommend nearby item vectors. Several interest profiles may work better than one average for diverse tastes.

What can go wrong → what to change → why

  • Overspecialisation → bounded exploration/diversity → repeatedly similar items reduce discovery.
  • Poor metadata → improve extraction/semantic representation → missing useful attributes weakens matching.

How to evaluate

Measure relevant recommendations and diversity, not rating error if no rating is predicted. Check new-user profile availability.

Answer flow

  1. Identify features.
  2. Build profile.
  3. Match/rank.
  4. Discuss metadata, cold start and variety.

Exam traps

  • Item-based CF uses interaction patterns; content-based filtering uses item attributes.
  • New-item support still needs useful content.

C038

User-based collaborative filtering

User-based CF recommends what similar users like. Similarity comes from shared rating/interaction patterns; it is a neighbourhood-based form of CF.

Problem it solves: Use when enough users have overlapping histories to make their similarities meaningful.

How to use it

  1. Build user–item ratings with blanks retained as unknown.
  2. Compare the target user with others on valid shared items.
  3. Select similar users who rated each candidate item.
  4. Compute a similarity-weighted rating or preference score.
  5. Rank eligible unseen items and test held-out results.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: neighbours with similarity .8 and .2 rated an unseen film 5 and 3. Weighted prediction=(.8×5+.2×3)/1=4.6.

What can go wrong → what to change → why

  • Sparse overlap → collect history or use content/hybrid fallback → similarity based on few common items is unreliable.
  • Different rating habits → mean-centering/Pearson → generous and strict users can share tastes.

How to evaluate

Use rating MAE/RMSE when predicting scores; use top-list relevance for recommendations. Check coverage and low-history users.

Answer flow

  1. Explain neighbour mechanism.
  2. Check overlap.
  3. Predict/rank.
  4. Connect data problem to remedy.

Exam traps

  • Missing is not dislike.
  • The sample’s treatment-set feedback is not automatically separate ratings for every treatment.
Sample paper: 5001 Q3(c)

C039

Item-based collaborative filtering

Item-based CF compares items using how users rated them, then recommends items related to those the target user liked. It remains collaborative filtering.

Problem it solves: Useful when item similarities can be precomputed and remain more stable than user similarities.

How to use it

  1. Transpose the interaction perspective: each item is described by user ratings.
  2. Compute item similarities using suitable overlap/normalisation.
  3. Precompute a neighbour list for each item.
  4. Use the target user’s ratings of similar items to score candidates.
  5. Exclude seen/ineligible items and rank.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: a user rated two items 5 and 2; candidate similarities .9 and .1 produce score 4.7 by weighted averaging.

What can go wrong → what to change → why

  • Sparse item histories → content/hybrid fallback → item similarities also need evidence.
  • Changing catalogue → refresh similarities → old precomputed neighbours can become stale.

How to evaluate

Compare rating/top-list accuracy, coverage and serving cost. The usual item-based speed benefit depends on item/user counts and update frequency.

Answer flow

  1. Identify item representation.
  2. Explain offline similarity.
  3. Show user-specific scoring.
  4. Discuss stability and sparse-item limits.

Exam traps

  • Similarity here comes from users, not product descriptions.
  • Precomputation does not remove all cold-start problems.

C040

Similarity and rating prediction

Similarity defines what counts as a useful neighbour. Prediction then combines neighbours’ known ratings, often with similarity weights and rating-scale adjustment.

Problem it solves: Use when a scenario asks how ratings are predicted or why a similarity choice is misleading.

How to use it

  1. Choose comparison coordinates and missing-value policy.
  2. Use cosine for direction, Euclidean for distance, or Pearson for centred rating patterns.
  3. Require sufficient relevant overlap.
  4. Select neighbours with known candidate ratings.
  5. Compute the stated weighted prediction, restoring a mean if centred.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: two neighbours weighted .75 and .25 rate an item 4 and 2; prediction=3.5. The denominator is the sum of usable weights, not all users.

What can go wrong → what to change → why

  • Zero-filled unknowns → use a justified missing-data policy → absence is not a measured zero.
  • Tiny overlap/zero denominator → fallback or abstain → a numeric score may be unreliable.

How to evaluate

Compare held-out predictions and coverage under alternative similarity/normalisation policies.

Answer flow

  1. State representation.
  2. Justify similarity.
  3. Identify usable neighbours.
  4. Show arithmetic and limitations.

Exam traps

  • Cosine similarity and Euclidean distance have opposite ranking directions.
  • Binary all-one co-rated values can make standard similarities uninformative.

C041

Recommendation evaluation

Evaluation must match the goal: rating error checks score prediction; top-list metrics check recommendation usefulness. A low rating error does not ensure a useful ranked list.

Problem it solves: Use when comparing recommenders, choosing factor count or assessing readiness to deploy.

How to use it

  1. Define relevant items and what the user actually sees.
  2. Hold out known interactions/ratings without leaking them into training.
  3. Tune on validation data and reserve a final test.
  4. Calculate MAE/RMSE for rating predictions, precision/recall at K for relevant lists.
  5. Also assess coverage, diversity and operational cost.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: 3 relevant items among 10 recommended gives precision@10=.3. If 5 relevant items exist in the evaluation set, recall@10=.6.

What can go wrong → what to change → why

  • Unknown relevance → state evaluation coverage/candidate policy → unrated does not prove irrelevant.
  • Ranking ignored → use a rank-sensitive check when required → precision@K treats positions within K alike.

How to evaluate

Use identical splits and eligibility rules for fair comparisons. Record threshold and denominator; lecture workshop variants sometimes return fewer than K recommendations.

Answer flow

  1. Goal → split → metric.
  2. State relevance threshold.
  3. Compute and interpret.
  4. Discuss coverage and deployment.

Exam traps

  • Do not tune repeatedly on final test data.
  • Offline relevance does not prove causal business improvement.
Sample paper: 5001 Q3(c)

C042

Sparsity and cold start

Sparsity means most user–item pairs lack observations. Cold start means a new user/item has little or no history. They weaken different parts of recommendation.

Problem it solves: Use to assess whether neighbourhood CF or interaction-only MF has enough evidence to personalise.

How to use it

  1. Identify users, items and what one feedback entry actually rates.
  2. Estimate observed density only with justified counts.
  3. Check user/item history and shared overlap.
  4. Use content, onboarding or popularity fallback where appropriate.
  5. Collect feedback and validate transitions to personalised methods.
Example · data issues · evaluation · exam flow

Worked idea

Sample Q3(c): about 40% give feedback across 300 treatments; few shared ratings make patient similarity unreliable. The assumed .4% density is illustrative, not established individual-treatment data.

What can go wrong → what to change → why

  • Sparse overlap → content/hybrid or validated MF → share useful signals, while recognising uncertainty.
  • No history → ask starter preferences/use metadata fallback → MF cannot learn an empty user vector from nothing.

How to evaluate

Report recommendation coverage and quality by history length, including new users/items.

Answer flow

  1. Identify missingness.
  2. Explain failure mechanism.
  3. Propose targeted fallback.
  4. State assumptions and tests.

Exam traps

  • Blank is unknown, not a zero rating.
  • MF helps share patterns but does not magically solve cold start.
Sample paper: 5001 Q3(c)

C043

Matrix factorization

MF is a model-based CF method: it learns a short hidden-factor vector for each user and item from interaction ratings. Their dot product predicts a rating.

Problem it solves: Use to share patterns across many sparse ratings without calculating a neighbourhood for every prediction.

How to use it

  1. Prepare observed user, item, rating records and split them.
  2. Choose latent-factor count and initialise vectors.
  3. Fit known training ratings with a regularisation penalty.
  4. Tune factor count/penalty on validation data.
  5. Score unseen items by user–item dot product and rank eligible ones.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example user A=[1.2,.8], item W=[1.5,1.7]: predicted rating=1.2×1.5+.8×1.7=3.16. Hidden dimensions need not have named genre meanings.

What can go wrong → what to change → why

  • Treat blanks as zero → fit observed ratings appropriately → missing is not dislike.
  • Too many factors → regularise/reduce dimension → sparse data can be memorised.

How to evaluate

Compare validation rating error and recommendation relevance. Check cold-start coverage separately.

Answer flow

  1. Explain CF→model-based MF relationship.
  2. Show fit and dot-product prediction.
  3. Address sparse data/overfit.
  4. Evaluate.

Exam traps

  • CF is the broader family; MF is one method.
  • This recommendation problem remains separate from the SVD/PCA chapter.

C044

SGD / ALS training

SGD and ALS are two ways to learn MF user/item factors. SGD adjusts them from rating errors; ALS alternates which side is fixed while solving the other.

Problem it solves: Use when asked how factors are trained or why factorisation is an iterative optimisation rather than manually assigning genres.

How to use it

  1. Choose factor count, objective and regularisation.
  2. Initialise factors.
  3. SGD: predict a known rating, calculate error and make a small update to the involved vectors.
  4. ALS: fix user vectors and solve item vectors, then reverse.
  5. Repeat while checking validation performance; stop appropriately.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: predicted rating 3, actual 5 means the update should increase this user–item compatibility. ALS instead solves many conditional least-squares subproblems with one matrix held fixed.

What can go wrong → what to change → why

  • SGD unstable → tune learning rate → huge steps can overshoot.
  • Long training/overfit → monitor validation and regularise → lower training error alone is insufficient.

How to evaluate

Compare validation loss, runtime and stability across initialisations. Specify observed-data objective or implicit confidence weighting correctly.

Answer flow

  1. State objective.
  2. Explain update schedule.
  3. Describe stopping.
  4. Justify settings and evaluation.

Exam traps

  • ALS does not update both matrices independently at the same instant.
  • A normalisation instruction is not permission to turn blanks into measured ratings.

C045

Recommendation overfitting and regularization

Overfitting means learning training-specific noise instead of patterns that transfer. In MF, too many factors or large weights can fit sparse observations too closely.

Problem it solves: Use when training error falls but validation worsens, or a proposed recommender is too complex for available evidence.

How to use it

  1. Separate training, validation and test data.
  2. Compare training and validation error as complexity/training increases.
  3. Tune factor count on validation.
  4. Add regularisation to discourage excessively large factor weights.
  5. Stop before validation degrades and evaluate once on final test.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: factors K=3 give validation RMSE .8; K=5 gives 1.1 even though training improves. Prefer K=3 under that validation result, not the largest model.

What can go wrong → what to change → why

  • Memorisation → fewer factors/stronger penalty → reduce flexibility.
  • Underfitting → ease excessive penalty or increase capacity → a model can also be too simple.

How to evaluate

Use held-out metrics and inspect both error curves. Select settings by validation, not a universal factor-count rule.

Answer flow

  1. Identify evidence of overfit.
  2. Name specific control.
  3. Explain why it helps.
  4. Check validation trade-off.

Exam traps

  • Regularisation does not remove the need for a data split.
  • The lecture’s 50–100 factors is a starting heuristic, not an exam law.

C046

Implicit feedback and preferences

Implicit feedback records actions such as views, clicks and purchases. It suggests interest but usually does not directly measure dislike or a rating level.

Problem it solves: Use when users rarely provide explicit ratings but interaction logs are available.

How to use it

  1. Define the event and what it plausibly indicates.
  2. Choose binary preference or justified event strength.
  3. Aggregate within a suitable time/session window.
  4. Choose an implicit-aware learning/ranking method.
  5. Evaluate against future relevant behaviour and practical outcomes.
Example · data issues · evaluation · exam flow

Worked idea

Lecture examples include page views, repeat visits, time spent and purchases. A purchase may be a gift or mistake; many views may show interest without proving satisfaction.

What can go wrong → what to change → why

  • All unseen treated as dislike → retain uncertainty or use controlled negative sampling → users may never have seen the item.
  • Subjective event weights → validate alternative weightings → assigning 5 to a share is an assumption.

How to evaluate

Assess top-list performance and event-definition bias. Distinguish predicting strength of positive activity from like-versus-dislike classification.

Answer flow

  1. Identify feedback type.
  2. State preference/confidence interpretation.
  3. Choose method.
  4. Explain missingness and evaluate.

Exam traps

  • Explicit and implicit ratings are not interchangeable evidence.
  • Observed activity is not necessarily approval.

C047

Jaccard similarity

Jaccard similarity compares two sets: number of shared elements divided by number in their union. It suits binary interaction sets without counting shared absences as agreement.

Problem it solves: Use when each observed event means presence/interest and standard co-rated all-one vectors yield unhelpful identical similarities.

How to use it

  1. Create each user’s set of observed items.
  2. Find the intersection of the sets.
  3. Find their union.
  4. Divide intersection size by union size.
  5. Use the resulting similarity for neighbour/ranking logic, with overlap checks.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: A={1,2,3}, B={2,3,4,5}. Intersection has 2, union has 5, so Jaccard=.4.

What can go wrong → what to change → why

  • Tiny overlap → minimum evidence/fallback → a perfect score on one event may be fragile.
  • All positive ratings averaged → rank candidate similarities instead → ordinary weighted all-one ratings still predict one.

How to evaluate

Compare held-out recommendation relevance and coverage; state how empty sets are handled.

Answer flow

  1. Represent as sets.
  2. Count intersection/union.
  3. Calculate.
  4. Explain how the score supports recommendation.

Exam traps

  • Shared missing items are not common likes.
  • Jaccard does not by itself produce meaningful 1–5 ratings.

C048

Negative sampling

Negative sampling selects some unobserved user–item pairs as training negatives instead of treating the entire missing matrix as labelled dislike.

Problem it solves: Use for scalable implicit-feedback classification or ranking, while remembering that an unobserved item may actually be liked.

How to use it

  1. Identify observed positive interactions.
  2. Choose a sampling policy and negative-to-positive ratio.
  3. Sample unseen candidates, excluding known positives.
  4. Train the classifier/ranker on positives and sampled negatives.
  5. Evaluate with a clearly stated candidate set and sampling policy.
Example · data issues · evaluation · exam flow

Worked idea

Lecture policies: uniform sampling; popularity-weighted sampling; hard negatives similar to liked items. Hard candidates create more difficult discrimination.

What can go wrong → what to change → why

  • False negative → control/review sampling → lack of interaction may mean lack of exposure.
  • Biased easy negatives → use realistic candidates and compare policies → inflated evaluation may not reflect serving.

How to evaluate

Check ranking/relevance and computational savings. Keep train/evaluation sampling transparent for fair model comparisons.

Answer flow

  1. Explain why missing labels are uncertain.
  2. Specify sampling.
  3. Describe learning target.
  4. Evaluate under realistic candidates.

Exam traps

  • A sampled zero is a modelling assumption, not a confirmed dislike.
  • Hardest negatives are not automatically best.

C049

Confidence-weighted implicit MF

Confidence-weighted implicit MF separates preference from confidence. Any observed activity gives preference 1; no activity gives preference 0 with low confidence, rather than confirmed dislike.

Problem it solves: Use when counts or durations provide stronger evidence of interest but are not explicit rating values.

How to use it

  1. Convert interactions to binary preferences.
  2. Assign higher confidence to stronger/more repeated observations.
  3. Retain low confidence for unobserved entries.
  4. Fit user/item factors with confidence-weighted preference error plus regularisation.
  5. Tune confidence scale/factors and rank candidates.
Example · data issues · evaluation · exam flow

Worked idea

Lecture confidence rule is 1 plus a scale times interaction count. With scale 40, count 2 yields confidence 81; no interaction yields confidence 1, not equal evidential weight.

What can go wrong → what to change → why

  • Heavy users dominate → tune/transform counts → raw count need not track liking linearly.
  • Dense objective cost → use suitable implicit ALS implementation → even unobserved pairs enter with low weight.

How to evaluate

Evaluate held-out ranking and coverage; compare confidence settings on validation data.

Answer flow

  1. Separate binary target from evidence strength.
  2. Explain weighted loss in words.
  3. Describe training.
  4. Discuss unknowns and evaluation.

Exam traps

  • Preference zero is not certainty of dislike.
  • Confidence weight is not a calibrated probability.

C050

Bayesian personalized ranking

Bayesian personalised ranking learns relative preferences: for one user, an observed positive item should score above a sampled unobserved item. It targets ordering rather than exact ratings.

Problem it solves: Useful when implicit feedback supports a ranked list but no meaningful 1–5 target exists.

How to use it

  1. Select a user and an observed positive item.
  2. Choose an unobserved comparison item.
  3. Score both with the recommender.
  4. Update parameters to favour the positive item.
  5. Repeat with regularisation and validation, then rank eligible candidates.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: user watched A but not B. Train toward score(A)>score(B); this does not imply a measured rating of 5 for A or proven dislike of B.

What can go wrong → what to change → why

  • Unseen but attractive item sampled → acknowledge uncertain negatives → non-observation is imperfect evidence.
  • All item pairs materialised → sample training pairs → the possible pair count grows rapidly.

How to evaluate

Evaluate held-out ranking/relevant-item retrieval rather than relying on rating MAE. Inspect negative-sampling sensitivity.

Answer flow

  1. Identify implicit ranking goal.
  2. Construct user–positive–comparison examples.
  3. Explain ordering objective.
  4. Validate rankings.

Exam traps

  • Pairwise preference is not a direct observed dislike label.
  • No need to invent a long formula to explain the mechanism.

C051

Hybrid recommenders

Hybrid recommenders combine complementary information or methods. Choose a combination that addresses a specific weakness, such as cold start or changing interests.

Problem it solves: Use when neither content nor interaction history alone covers all users/items or objectives.

How to use it

  1. Identify each method’s strengths and failure cases.
  2. Choose a lecture pattern: weighted, switching, mixed, cascade, feature combination/augmentation or meta-level.
  3. Specify the information/scores passed.
  4. Tune combination parameters on validation data.
  5. Evaluate the full system and each component.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative switching: new user gets popularity/declared-profile recommendations; once sufficient history exists, use CF. Weighted fusion instead combines scores after compatible scaling.

What can go wrong → what to change → why

  • Unclear fusion → specify switching rule or score calculation → listing two algorithms is not an architecture.
  • More complexity/latency → compare simpler baseline → extra components may add cost without benefit.

How to evaluate

Assess quality, coverage, cold-start users, diversity and serving latency. Check that the hybrid improves its intended weakness.

Answer flow

  1. State weakness.
  2. Choose matching hybrid pattern.
  3. Draw inputs and fusion.
  4. Validate benefit and cost.

Exam traps

  • Mixed display and weighted score fusion differ.
  • A hybrid cannot manufacture reliable data from absent evidence.

C052

Deep collaborative filtering

Deep collaborative filtering learns nonlinear user–item interactions. In neural CF, user and item embeddings feed an MLP instead of relying only on a dot product.

Problem it solves: Consider when sufficient interaction data and features justify more capacity than simple MF.

How to use it

  1. Define user/item inputs and explicit or implicit target.
  2. Map IDs or features to embeddings.
  3. Combine embeddings with the chosen neural layers.
  4. Train with a loss matched to rating or binary/ranking target.
  5. Tune capacity/regularisation and compare against MF.
Example · data issues · evaluation · exam flow

Worked idea

Lecture NeuMF combines generalised MF and MLP branches. Autoencoder CF instead compresses a rating vector and reconstructs ratings, including estimates for unseen items.

What can go wrong → what to change → why

  • Sparse IDs/cold start → add side information or fallback → ID-only embeddings still need history.
  • Overfitting/cost → regularise and baseline-test → nonlinear capacity is not automatically useful.

How to evaluate

Check held-out recommendation quality, coverage, latency and model size. Separate candidate retrieval from expensive ranking if catalogue is large.

Answer flow

  1. Define target.
  2. Explain chosen architecture.
  3. Specify data/loss.
  4. Justify benefit over simple baseline.

Exam traps

  • Do not confuse user/item IDs with meaningful numerical magnitudes.
  • Deep models do not automatically solve missing feedback.

C053

Sequence-based recommendation

Sequence-based recommenders use the order of a user’s interactions to predict the next useful item or rank candidates for current intent.

Problem it solves: Useful when recent session behaviour matters, such as a shopper’s changing goal or news interests.

How to use it

  1. Group and time-order events into user/session sequences.
  2. Encode items and available context.
  3. Train next-item prediction or candidate ranking using only earlier events.
  4. Use RNN/GRU or attention/Transformer according to the lecture design.
  5. Serve candidates/rankings and update session context.
Example · data issues · evaluation · exam flow

Worked idea

Lecture examples: Prod2Vec learns items occurring in similar session contexts; GRU4Rec models session order; BST uses behaviour sequences for candidate ranking.

What can go wrong → what to change → why

  • Accidental recent click → attention to relevant history → latest event alone may distort intent.
  • Future leakage → chronological construction/split → prediction cannot use later clicks.

How to evaluate

Evaluate next-item/ranking success on later events plus latency. Check anonymous sessions and short histories.

Answer flow

  1. Identify sequence/target.
  2. Define event order and features.
  3. Explain model’s sequence use.
  4. Validate future predictions.

Exam traps

  • A session is not automatically a lifelong user profile.
  • A ranking model need not be the catalogue retrieval model.

C054

Graph-based recommendation

Graph-based recommendation models users, items and other entities as nodes, with interactions/relationships as edges. Recommendation can become missing-link prediction.

Problem it solves: Useful when social links, item categories or interaction topology add evidence beyond a flat rating matrix.

How to use it

  1. Define node and edge types.
  2. Construct a graph using training-time information only.
  3. Learn representations through random walks or neighbour aggregation.
  4. Score possible user–item links or retrieve nearby item embeddings.
  5. Filter seen/ineligible items and rank.
Example · data issues · evaluation · exam flow

Worked idea

Lecture examples include Node2Vec random walks and GraphSAGE neighbour sampling. Decathlon graph nodes include users, items and sports, with click/purchase/related links.

What can go wrong → what to change → why

  • Future/test edges included → remove them before training/features → topology can leak the answer.
  • Sparse/new nodes → use features/fallback → graph structure alone may provide little evidence.

How to evaluate

Evaluate held-out link/recommendation rankings, cold-node behaviour, scalability and source quality.

Answer flow

  1. Draw typed graph.
  2. Explain embedding/scoring.
  3. Prevent edge leakage.
  4. Justify extra relationship value.

Exam traps

  • A possible link is not an established fact.
  • Random walks and graph neural aggregation are different training mechanisms.

C055

Genetic algorithm representation and fitness

A genetic algorithm searches a population of encoded candidate solutions. Fitness expresses how good each decoded solution is for the actual objective and constraints.

Problem it solves: Useful for large optimisation spaces where exhaustive search is impractical and a good approximate feasible solution is acceptable.

How to use it

  1. Define what one full solution contains.
  2. Choose chromosome encoding: bits, real values, integers or a permutation.
  3. Define objective, constraints and fitness direction.
  4. Initialise a diverse population and evaluate it.
  5. Select, recombine, mutate and replace repeatedly until a stopping rule.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative route problem: chromosome is an ordered city list; fitness rewards shorter feasible tours. The representation/operators must avoid or repair duplicate/missing cities.

What can go wrong → what to change → why

  • Fitness ignores constraint → enforce validity/penalty/repair → a high score may otherwise be unusable.
  • Poor encoding → choose meaningful representation → search operates on encoded solutions, not business intent.

How to evaluate

Track best feasible objective, runtime and variability across runs; compare a simple baseline. No automatic global-optimum guarantee.

Answer flow

  1. Define solution and encoding.
  2. Specify fitness/constraints.
  3. Explain generation loop.
  4. Set stop and evaluate.

Exam traps

  • Fitness may require transforming a cost-minimisation objective.
  • A population member is one candidate solution, not one feature.

C056

GA selection operators

GA selection favours fitter candidates for reproduction while retaining some diversity. It decides who contributes genetic material, not how genes are changed.

Problem it solves: Use when tracing roulette-wheel probabilities or choosing selection pressure for an optimisation design.

How to use it

  1. Evaluate every candidate’s fitness.
  2. Choose a method: roulette, tournament or rank selection.
  3. Roulette: divide suitable nonnegative fitness by total and form cumulative intervals.
  4. Draw/select parents according to the method.
  5. Then apply crossover, mutation and replacement.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative roulette: fitness 2,3,5 yields probabilities .2,.3,.5. Random value .65 falls in the third candidate’s cumulative interval (.5,1].

What can go wrong → what to change → why

  • One candidate dominates → rank/tournament pressure tuning → diversity can collapse early.
  • Raw negative costs → transform or use a compatible selection method → roulette probabilities must be valid.

How to evaluate

Check probabilities sum to one and random values map to the correct interval. Compare diversity, convergence and final feasible quality.

Answer flow

  1. State fitness direction.
  2. Calculate selection weights.
  3. Show selected parents.
  4. Discuss pressure and diversity.

Exam traps

  • Fittest has highest chance, not guaranteed selection.
  • Tournament draws participants randomly then selects the better participant.

C057

GA crossover and mutation

Crossover recombines existing parent material; mutation randomly changes components to introduce/restore diversity. Both depend on the chromosome representation.

Problem it solves: Use when asked to trace offspring generation or explain premature convergence and parameter trade-offs.

How to use it

  1. Select parents first.
  2. Apply crossover if its probability test passes.
  3. Use single-point, multi-point or uniform crossover as specified.
  4. Apply mutation at the stated gene/chromosome level.
  5. Check validity, repair if required, evaluate and replace.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative binary parents 11|00 and 00|11 produce 1111 and 0000 after one-point crossover. A bit mutation might change 1111 to 1011.

What can go wrong → what to change → why

  • Permutation duplicates → permutation-safe crossover/repair → ordinary string splicing can invalidate routes.
  • Mutation too high → reduce rate → useful structure is lost; too low can lose diversity.

How to evaluate

Check offspring validity, diversity and best feasible fitness over multiple runs. Improvement in one generation is not guaranteed.

Answer flow

  1. Show parent encoding.
  2. Apply exact crossover/mutation.
  3. Check constraints.
  4. Explain parameter trade-off.

Exam traps

  • Per-bit mutation expectation = population×length×rate, not a guaranteed count.
  • Crossover and mutation perform different roles.

C058

Symbolic / connectionist / hybrid AI

Symbolic AI uses explicit representations/rules; connectionist AI learns distributed representations in neural networks. Hybrid systems combine complementary capabilities.

Problem it solves: Use when a question asks which AI approach fits structured expertise, noisy high-volume data or a system needing both.

How to use it

  1. Identify whether reliable rules, labelled data or both are available.
  2. Match structured constraints/explanations to symbolic methods.
  3. Match perception/pattern learning to data-driven methods.
  4. Specify an actual hybrid information flow if combining them.
  5. Validate each part and the overall decision.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: an image model extracts a sign; explicit domain rules combine that sign with supplied facts to determine a reviewed action. Do not claim the sample app contains a trained model unless established.

What can go wrong → what to change → why

  • Rule maintenance → expert updates/tests → hand-built knowledge can become stale.
  • Neural opacity/bias → validation, explanations and constraints → learnt patterns need system-level checks.

How to evaluate

Compare task success, explanation quality, knowledge/data requirements and maintenance. The simplest justified design may be sufficient.

Answer flow

  1. Identify task/evidence.
  2. Choose paradigm with reason.
  3. Show hybrid interface if needed.
  4. Explain limits and validation.

Exam traps

  • Not every reasoning system requires every AI technique.
  • Separate subsystem responsibilities do not prove multiple neural networks.
