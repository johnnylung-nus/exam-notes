C001

Search problem formulation

Search means exploring possible states and actions to reach a goal. The representation determines what solutions the algorithm can find.

Problem it solves: Use when the question asks for a route, arrangement or sequence satisfying requirements.

How to use it

  1. Define what one state contains.
  2. Specify the initial state and valid actions.
  3. State the goal test and hard constraints.
  4. Assign action costs and the objective.
  5. Choose a search method that matches costs, memory and heuristic availability.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative delivery task: state = current city plus visited cities; action = travel to an unvisited city; goal = visit all required cities and return; objective = minimum total travel cost.

What can go wrong → what to change → why

  • Missing state information → include visited cities/resources → legality depends on history.
  • Conflicting objectives → state priority or weights → cheapest and fastest need not coincide.

How to evaluate

Check that the final path reaches the goal, obeys constraints and has correctly summed cost. Compare search effort and solution quality.

Answer flow

  1. Identify state and goal.
  2. Define actions, constraints and costs.
  3. Justify algorithm.
  4. Trace and check result.

Exam traps

  • A node is a state, not necessarily just a location.
  • A feasible solution need not be optimal.

C002

Breadth-first search

Breadth-first search explores all states at one depth before going deeper. It uses a queue: add new children at the end.

Problem it solves: Useful for fewest-step solutions when each action has the same cost, or finding all nodes within a limited number of hops.

How to use it

  1. Put the start in the frontier queue.
  2. Remove the oldest queued node and check the goal.
  3. Append its valid unvisited children.
  4. Record parents to reconstruct the path.
  5. Repeat until success or the queue is empty.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative tree: A has B and C; B has D and E. With left-to-right children, expansion begins A, B, C, D, E. C is checked before deeper nodes.

What can go wrong → what to change → why

  • Cycles → keep visited states → prevent repeated expansion.
  • Large branching → frontier grows rapidly → consider cost/heuristic search when suitable.

How to evaluate

Verify the queue and expansion order. On equal-cost edges, the first reached goal has minimum steps; weighted edges require another criterion.

Answer flow

  1. Check equal step costs.
  2. Write frontier after each expansion.
  3. Apply stated child order.
  4. Return path, not just visiting order.

Exam traps

  • Fewest edges does not mean cheapest weighted path.
  • State tie/child order rather than inventing a unique trace.

C003

Depth-first search

Depth-first search follows one branch deeply before returning to alternatives. New children go at the front of the frontier, giving stack-like behaviour.

Problem it solves: Useful for exploring a branch, enumerating paths or situations where keeping a broad frontier is expensive.

How to use it

  1. Start with the initial node.
  2. Take the most recently added node.
  3. Check goal and generate children in the stated order.
  4. Explore deeper before siblings.
  5. Backtrack when a branch ends; track visited states or path cycles.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative tree: A→B→D is explored before A→C. If D fails, return to B and try its next child rather than restarting the whole problem.

What can go wrong → what to change → why

  • Infinite branch → depth limit or suitable cycle control → ensure other branches can be considered.
  • Poor first branch → excessive search → use information or another strategy.

How to evaluate

Check expansion/backtracking order and memory. DFS does not generally guarantee the shortest or cheapest solution.

Answer flow

  1. Identify branching and goal.
  2. Apply stack order consistently.
  3. Show backtracking.
  4. Discuss completeness and cost limitations for this space.

Exam traps

  • Do not describe DFS as level-by-level.
  • Deepest-first does not mean choosing the most promising heuristic.

C004

Uniform-cost search / Dijkstra

Uniform-cost search, called Dijkstra in the route example, expands the frontier path with the lowest accumulated cost from the start. It uses no goal-distance estimate.

Problem it solves: Choose when edge costs differ and the aim is the cheapest path with nonnegative edge costs.

How to use it

  1. Set start cost to zero.
  2. Keep frontier entries ordered by total cost so far.
  3. Remove the lowest-cost entry.
  4. Relax each outgoing edge: update a state if this path is cheaper.
  5. Stop when the goal is selected from the frontier.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: A→B costs 2, A→C costs 1, C→B costs 0.5. Discovering B directly does not settle it; the cheaper path through C costs 1.5.

What can go wrong → what to change → why

  • Treating edges equally → use accumulated costs → number of steps can mislead.
  • Repeated states → retain best cost and predecessor → avoid accepting an expensive duplicate.

How to evaluate

Sum the returned path cost and compare alternatives. With equal edge costs it behaves like BFS; without a heuristic it may explore many nodes.

Answer flow

  1. Identify weighted objective.
  2. Calculate cumulative costs.
  3. Update best paths.
  4. Select goal only when cheapest frontier entry.

Exam traps

  • Cost so far includes every edge from the start.
  • Negative edge costs invalidate ordinary Dijkstra assumptions.

C005

A* search

A* compares the estimated whole journey: cost already paid plus estimated cost remaining. It keeps competing frontier paths, not only the current node’s children.

Problem it solves: Use for minimum-cost routing when a useful admissible heuristic is available.

How to use it

  1. Set cost so far g(start)=0; h is estimated remaining cost.
  2. Calculate f=g+h for every frontier entry.
  3. Expand the globally lowest f; keep unexpanded alternatives.
  4. For each child, add the edge to the parent g and update cheaper paths.
  5. Stop when the goal is selected as the lowest-f frontier entry.
Example · data issues · evaluation · exam flow

Worked idea

Lecture Romania route: the 450-cost goal is generated first, but Pitesti still has f=417. Continuing yields the 418-cost route, which is then selected.

What can go wrong → what to change → why

  • Stopping on goal generation → continue frontier comparison → another route may be cheaper.
  • Inconsistent heuristic → reopen improved states or require consistency → closed-state shortcuts can lose optimality.

How to evaluate

Check cumulative g, correct h and all frontier f values. Optimality needs admissibility plus correct repeated-state handling.

Answer flow

  1. Define g, h and f in words.
  2. Maintain frontier across branches.
  3. Update cheaper duplicate paths.
  4. Explain stopping and optimality conditions.

Exam traps

  • g is not just the latest edge.
  • Lowest child is not necessarily lowest frontier node.

C006

Heuristics and admissibility

A heuristic estimates remaining cost, helping search focus on promising states. Admissible means it never overestimates the true cheapest remaining cost.

Problem it solves: Needed when choosing or checking an A* estimate; a plausible-looking estimate is not enough to claim optimality.

How to use it

  1. Identify the actual objective and its units.
  2. Explain how the estimate relates to that objective.
  3. Check that the goal estimate is zero.
  4. Justify a lower bound, rather than checking only convenient examples.
  5. Use consistency or reopen improved states in graph search.
Example · data issues · evaluation · exam flow

Worked idea

Lecture examples include straight-line distance for road routes and Manhattan distance for tile moves. Straight-line distance is a lower bound only when road cost is compatible with physical distance.

What can go wrong → what to change → why

  • Wrong units → align estimate with cost → kilometres cannot directly estimate fare.
  • Overestimation → revise lower bound → A* may otherwise choose a suboptimal goal.

How to evaluate

Check estimates against known remaining costs; compare nodes expanded. Zero is admissible but gives no directional guidance and reduces A* to uniform-cost search.

Answer flow

  1. State what cost is being estimated.
  2. Check lower-bound argument.
  3. Discuss informativeness.
  4. Connect conditions to algorithm guarantee.

Exam traps

  • A smaller estimate is not automatically more informative.
  • Admissible does not mean exact.

C007

Hill climbing

The lecture labels its heuristic-only route method “Hill Climbing (Greedy Best First Search)”. It chooses the promising child using remaining-distance estimates, ignoring the journey already paid.

Problem it solves: Use the lecturer’s stated variant when tracing an exam example. Local hill climbing and global-frontier greedy search are not interchangeable algorithms.

How to use it

  1. Identify whether the question retains alternatives or discards them.
  2. Score candidates with h only, following the lecture convention.
  3. Choose the stated best child or frontier node.
  4. Handle dead ends/backtracking exactly as specified.
  5. Report the actual completed route cost separately.

Source check: The deck groups hill climbing and greedy best-first under one label and allows backtracking; retain its specified trace, while distinguishing conventional local and global-frontier variants.

Example · data issues · evaluation · exam flow

Worked idea

Lecture Romania example follows Arad→Sibiu→Fagaras→Bucharest, costing 450. Choosing the smallest remaining-distance estimate did not find the 418-cost A* route.

What can go wrong → what to change → why

  • Local optimum/plateau → restart or annealing where appropriate → local improvement can stall.
  • Ignoring paid cost → use A* for cheapest paths → a near-looking node may require an expensive journey.

How to evaluate

Assess route cost, success and search effort. Heuristic-only ranking does not guarantee minimum total cost.

Answer flow

  1. Name the exact variant.
  2. State candidate-retention rule.
  3. Trace h choices.
  4. Explain why result need not be optimal.

Exam traps

  • Do not silently rename all greedy search hill climbing.
  • Lower h need not mean lower g+h.

C008

Simulated annealing

Simulated annealing is an optimisation search that sometimes accepts a worse move, helping escape a local minimum. The chance of accepting worse moves decreases as temperature cools.

Problem it solves: Useful when the search/error landscape has local traps and always-improve local search can get stuck.

How to use it

  1. Define candidate solutions, allowed neighbours and objective.
  2. Start from a solution and a temperature schedule.
  3. Propose a random neighbour.
  4. Accept improvements; sometimes accept a worse move according to temperature and deterioration.
  5. Cool gradually, repeat and retain the best solution found.

Source check: The supplied MR Day4 p74 names simulated annealing as an escape technique but does not teach its full procedure here; algorithm steps are a clearly identified study elaboration, not a quoted lecture derivation.

Example · data issues · evaluation · exam flow

Worked idea

Illustrative schedule: moving temporarily to a slightly worse timetable may allow a later move to a much better timetable that greedy local improvement cannot reach.

What can go wrong → what to change → why

  • Cooling too quickly → slow cooling or restart → search may freeze in a poor basin.
  • Always accepting worse moves → reduce temperature → otherwise search resembles random wandering.

How to evaluate

Compare best feasible objective across repeated runs and time budgets. A single successful run is not a general optimality guarantee.

Answer flow

  1. Identify the local-trap problem.
  2. Define neighbours and objective.
  3. Explain controlled worse-move acceptance.
  4. Justify stopping and compare repeated results.

Exam traps

  • Temperature is an algorithm control, not model prediction confidence.
  • This is an optional optimiser, not a guaranteed cure for every training issue.

C009

Deductive reasoning

Deduction applies a general rule to facts to obtain a conclusion. If the rule and premises are true and inference is valid, the conclusion follows logically.

Problem it solves: Choose for explicit business/domain rules where the question asks what follows from known facts.

How to use it

  1. Write the relevant rule clearly.
  2. Match its conditions against present facts.
  3. Check every required condition, including AND/OR and thresholds.
  4. Apply the conclusion and record the rule used.
  5. Continue if the new conclusion triggers another rule.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example: if raining then street wet; raining is known; infer street wet. This direction is deduction, whereas guessing rain from wetness is abduction.

What can go wrong → what to change → why

  • Unknown condition → ask or defer → missing is not automatically false.
  • Incorrect domain rule → expert validation and versioning → valid logic cannot rescue false premises.

How to evaluate

Test ordinary cases, boundaries, missing facts and contradictory rules. Explain which facts and rules support the result.

Answer flow

  1. State facts.
  2. Select applicable rule.
  3. Show inference direction.
  4. State conclusion and assumptions.

Exam traps

  • A true conclusion does not prove its presumed cause.
  • Logical certainty is conditional on reliable premises.

C010

Abductive reasoning

Abduction proposes an explanation for observed evidence. The explanation is plausible, not logically guaranteed, because other causes may produce the same evidence.

Problem it solves: Use for diagnosis, fault finding or interpreting observed effects under uncertainty.

How to use it

  1. List the observed effects.
  2. Identify candidate causes that could explain them.
  3. Check additional evidence and competing explanations.
  4. Rank or update candidates if justified probabilities are available.
  5. Report uncertainty and request discriminating information.
Example · data issues · evaluation · exam flow

Worked idea

Lecture rain example: the street is wet, so rain is a possible cause. A sprinkler could also explain wetness; observing wetness alone does not prove rain.

What can go wrong → what to change → why

  • Single-cause assumption → compare alternatives → several causes can share symptoms.
  • Invented probabilities → use justified prior/likelihood information → labels alone do not quantify uncertainty.

How to evaluate

Check whether the proposed explanation accounts for the observations and survives contrary evidence. In labelled cases, assess diagnostic/ranking performance.

Answer flow

  1. Name evidence.
  2. Generate plausible causes.
  3. Identify what distinguishes them.
  4. Conclude with stated uncertainty.

Exam traps

  • Do not present reverse implication as deduction.
  • Most plausible does not mean certainly true.

C011

Inductive reasoning

Induction learns a general pattern from particular observations. Unlike deduction, a pattern supported by examples can still fail on a new case.

Problem it solves: Use when historical labelled examples are available and the goal is to predict unseen outcomes.

How to use it

  1. Define one training example, input features and desired output.
  2. Collect representative observations.
  3. Fit a hypothesis/model to the training examples.
  4. Tune complexity on validation data.
  5. Evaluate on untouched cases and inspect errors.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example: seeing Japanese cars entering the staff carpark suggests a pattern, but does not prove every staff member drives a Japanese car.

What can go wrong → what to change → why

  • Biased observations → broaden sampling → observed cases may not represent the target population.
  • Memorisation → control complexity and validate → fitting the past is not the same as generalising.

How to evaluate

Judge performance on unseen representative data, with metrics reflecting the task and costs of mistakes.

Answer flow

  1. Identify examples and target.
  2. Explain learning from instances.
  3. Check sampling and leakage.
  4. Assess generalisation.

Exam traps

  • A perfect training fit is not proof of a universal rule.
  • Training labels must not become prediction-time inputs.
Sample paper: 5001 Q2(f)

C012

Forward chaining

Forward chaining starts with known facts and repeatedly applies satisfied IF–THEN rules to derive more facts. It is data-driven.

Problem it solves: Useful when incoming observations should trigger all relevant conclusions, such as diagnosis, warning and action rules.

How to use it

  1. Store current facts in working memory.
  2. Match rule conditions to these facts.
  3. Choose a rule if several can fire.
  4. Add its new conclusions.
  5. Repeat until no new facts arise or the required result is reached.
Example · data issues · evaluation · exam flow

Worked idea

Lecture medical illustration: temperature over 100°F gives fever; fever plus illness over a month gives suspected infection; that plus sore throat yields a strep-throat conclusion within the toy rules.

What can go wrong → what to change → why

  • Many irrelevant rules → index conditions or restrict scope → reduce unnecessary matching.
  • Rule loops → avoid refiring unchanged facts → prevent endless repetition.

How to evaluate

Trace derived facts and rule IDs. Test missing data, conflicts and termination; expert-supplied clinical rules require validation.

Answer flow

  1. List initial facts.
  2. Show rule firing order.
  3. Add intermediate facts.
  4. Return outputs and reasons.

Exam traps

  • The engine performs inference; the KB stores rules.
  • Separate diagnosis/triage outputs do not require separate trained models.
Sample paper: 5001 Q2(d)

C013

Backward chaining

Backward chaining starts with a goal and works backwards through rules that could establish it. Their conditions become subgoals.

Problem it solves: Useful for checking a specific hypothesis or asking only questions relevant to a target conclusion.

How to use it

  1. State the goal to prove.
  2. Find rules with that goal in their THEN part.
  3. Check each IF condition against known facts.
  4. Turn unknown conditions into subgoals or questions.
  5. Continue until the goal succeeds or candidate rule paths fail.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example asks whether the illness is strep throat, then checks sore throat and suspected bacterial infection, then fever and temperature.

What can go wrong → what to change → why

  • Circular subgoals → track active goals → avoid recursion loops.
  • Failure to prove → distinguish insufficient knowledge from falsity → unknown is not necessarily absent.

How to evaluate

Check that every required subgoal has evidence and that the final explanation contains the supporting rule chain.

Answer flow

  1. Identify goal.
  2. Select supporting rules.
  3. Expand conditions into subgoals.
  4. State proven, disproven or unresolved based on evidence.

Exam traps

  • Do not start by firing every rule from all data.
  • Goal-directed inference does not automatically mean probabilistic reasoning.

C014

Conflict resolution in rule systems

Conflict resolution chooses which rule fires when several rules match in the same cycle. The choice can affect processing order and possibly outputs.

Problem it solves: Needed in rule-engine designs with multiple applicable rules, contradictory actions or exception policies.

How to use it

  1. Build the set of currently matched rules.
  2. Apply a documented selection strategy.
  3. Possible lecture strategies: priority, most specific condition set or most recent supporting data.
  4. Fire the selected rule and update working memory.
  5. Match again and explain the decision.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: a general discount rule and a higher-priority exclusion both match. Apply the declared exception policy rather than whichever happens to be stored first.

What can go wrong → what to change → why

  • Hidden priorities → record explicit rule priority → make behaviour reproducible.
  • Conflicting conclusions → detect and escalate or apply defined precedence → arbitrary order can produce unsafe decisions.

How to evaluate

Create test cases where multiple rules match. Check deterministic selection, explanation and that important exceptions are not bypassed.

Answer flow

  1. Identify matching rules.
  2. Show the conflict.
  3. Name and apply selection policy.
  4. Explain resulting conclusion.

Exam traps

  • A conflict set need not imply all rules are logically inconsistent.
  • Choosing one rule does not prove the others false.
Sample paper: 5001 Q2(d)

C015

Case-based reasoning

Case-based reasoning solves a new problem by retrieving similar previous cases, adapting their solutions and retaining the reviewed outcome.

Problem it solves: Suitable when solved examples are available but writing complete explicit rules is difficult.

How to use it

  1. Represent the new case using relevant features.
  2. Retrieve similar stored cases.
  3. Inspect why the retrieved cases are relevant.
  4. Adapt their solutions to the important differences.
  5. Evaluate the proposed solution and retain success/failure for future use.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative support case: retrieve an earlier VPN failure with similar symptoms, but adapt its fix if the new device uses a different operating system.

What can go wrong → what to change → why

  • Superficial similarity → use task-relevant features and differences → a familiar-looking case may need another solution.
  • Bad historical solutions → quality review before retention → errors can otherwise propagate.

How to evaluate

Measure retrieval relevance and final solution success separately. Explain the matched case, differences and adaptation.

Answer flow

  1. Define case fields.
  2. Specify similarity/retrieval.
  3. Explain adaptation.
  4. Validate and retain reviewed result.

Exam traps

  • Nearest-case retrieval alone omits adaptation and review.
  • A case database is not automatically an explicit rule engine.

C016

Bayesian reasoning

Bayesian reasoning updates belief in a hypothesis after observing evidence. It combines the prior belief with how likely that evidence is under competing hypotheses.

Problem it solves: Use when uncertainty matters and the case provides or justifies probabilities, rather than forcing a certain conclusion.

How to use it

  1. Name the hypothesis and observed evidence.
  2. Identify prior probabilities.
  3. Identify evidence likelihoods for the competing hypotheses.
  4. Multiply each prior by its evidence likelihood.
  5. Normalise across possible hypotheses to obtain updated beliefs.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example: with equal male/female priors, 4% of men and 50% of women having long hair, male-and-long-hair mass is .02 versus .25; male given long hair is .02/.27 ≈7%.

What can go wrong → what to change → why

  • Ignoring base rate → include prior → evidence alone can mislead.
  • Unsupported conditional probabilities → collect/validate them → a graph or label does not supply numeric values.

How to evaluate

Check that probabilities are coherent and sum appropriately; compare predictions with observed outcomes where available.

Answer flow

  1. Identify hypothesis/evidence.
  2. Separate prior and likelihood.
  3. Calculate and normalise.
  4. Interpret uncertainty in the scenario.

Exam traps

  • Probability of evidence given cause is not probability of cause given evidence.
  • High diagnostic probability is not automatically high urgency.
Sample paper: 5002 Q2(d)

C017

First-order / predicate logic

Predicate logic describes objects, their properties and relationships using predicates, variables and quantifiers. It makes the scope of a rule explicit.

Problem it solves: Useful when an exam asks for formal knowledge representation or a distinction between every object and at least one object.

How to use it

  1. Define the domain of objects.
  2. Name predicates and what each argument means.
  3. Translate relations and conditions.
  4. Choose “for all” versus “there exists” carefully.
  5. Test the statement against a small counterexample.
Example · data issues · evaluation · exam flow

Worked idea

Lecture rain rule: for every day, if that day is rainy, its street is wet. This does not say every day is rainy or that all wet streets were caused by rain.

What can go wrong → what to change → why

  • Ambiguous scope → state quantifier and domain → everyday language can hide different meanings.
  • Reversing implication → check direction → cause-to-effect does not prove effect-to-cause.

How to evaluate

Check whether the representation says exactly what the scenario requires. Trace a valid inference using its facts and rules.

Answer flow

  1. Identify entities and relations.
  2. Define predicates.
  3. Write rule and quantifiers.
  4. Explain its meaning in plain words.

Exam traps

  • An implication is not automatically a two-way equivalence.
  • A variable needs a defined domain.

C018

Semantic networks

A semantic network represents entities/concepts as nodes and relationships as labelled edges. Inheritance and traversal help connect related knowledge.

Problem it solves: Useful for showing associations or concept hierarchies when a visual relationship model is more helpful than flat records.

How to use it

  1. Identify classes and instances.
  2. Choose meaningful relationship labels.
  3. Draw the directed links and hierarchy.
  4. Separate class membership, is-a inheritance and part-of composition.
  5. State what can be inferred by following the links.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: Canary is-a Bird; Bird is-a Animal. A canary therefore belongs to the animal category. Eye part-of Face expresses a different relationship.

What can go wrong → what to change → why

  • Unlabelled links → label direction and semantics → readers cannot infer what a connection means.
  • Exceptions to inherited defaults → represent overrides → a general property may not hold for every subclass.

How to evaluate

Check that each claimed inference follows the intended relation semantics. Informal networks need additional rules if stronger formal inference is required.

Answer flow

  1. Extract entities.
  2. Label relations.
  3. Show useful paths/inheritance.
  4. Check meaning and exceptions.

Exam traps

  • Is-a and part-of are different.
  • A diagram of associations alone does not provide calibrated probabilities.
Sample paper: 5001 Q1(c)

C019

Frames

Frames represent structured objects or typical situations using named slots, values and relationships. Parent frames can provide inherited shared properties and defaults.

Problem it solves: Choose when the scenario naturally describes objects with attributes, such as patient findings, equipment or diseases.

How to use it

  1. Identify object/frame types.
  2. Define slots, value types and qualitative states.
  3. Create shared parent slots and specific child slots.
  4. Link frames with correctly named relationships.
  5. Specify how an inference procedure uses the stored information.
Example · data issues · evaluation · exam flow

Worked idea

Sample discussion: BodyPart has name, position and time; Eye adds eye position; Monitor has brightness and height status. Patient facts must distinguish present, absent and unknown.

What can go wrong → what to change → why

  • Only drawing objects → add slots/relations and inference use → a database alone does not establish frame-based reasoning.
  • Defaults treated as facts → allow patient-specific override → typical knowledge is not always true.

How to evaluate

Check inheritance, qualitative values and whether the schema can represent the question’s actual inputs and conclusions.

Answer flow

  1. List frames.
  2. Specify slots and links.
  3. Show inheritance/overrides.
  4. Explain matching or rule processing.

Exam traps

  • A frame stores knowledge; it does not itself choose a diagnosis.
  • Disease knowledge and current patient findings are different records.

C020

Ontologies

An ontology formally specifies a domain’s concepts, relationships, hierarchies and constraints. It provides shared meaning and supports classification/consistency checks.

Problem it solves: Useful when several data sources must describe the same domain consistently or when valid relations and class membership matter.

How to use it

  1. Define important classes and instance types.
  2. Specify properties and permitted relations.
  3. Add class hierarchy and constraints.
  4. Map source terms to the shared definitions.
  5. Check consistency and state valid inferred memberships.
Example · data issues · evaluation · exam flow

Worked idea

Lecture university example: Professor is a subclass of Academic. If Alice is a Professor, Alice is an Academic even if that fact was not stored separately.

What can go wrong → what to change → why

  • Conflicting source meanings → map and reconcile concepts → identical labels can mean different things.
  • Excessive complexity → model required distinctions only → maintenance cost can exceed value.

How to evaluate

Check class consistency, illegal relation types and whether relevant queries can be expressed. Have domain experts review definitions.

Answer flow

  1. Identify shared concepts.
  2. Define hierarchy and constraints.
  3. Map entities/facts.
  4. Demonstrate one inference and validation.

Exam traps

  • Ontology defines the schema/meaning; a KG stores concrete facts.
  • More formality does not make incorrect source facts true.

C021

Knowledge graph structure and queries

A knowledge graph stores connected facts as entities and named relationships, often subject–predicate–object triples. Queries exploit those connections.

Problem it solves: Use when questions require relationships across entities, rather than only one row’s features.

How to use it

  1. Identify entities and stable identifiers.
  2. Define meaningful relation types and directions.
  3. Store source-backed triples and relevant attributes.
  4. Translate the question into graph conditions.
  5. Retrieve matching facts and retain their provenance.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example: Alice teaches AI101; Alice advises Bob; Bob enrolls in AI101. A query can find courses taught by Bob’s adviser.

What can go wrong → what to change → why

  • Duplicate names → entity matching → separate records may refer to one person.
  • Missing/incorrect links → validate and record provenance → graph queries are only as reliable as stored facts.

How to evaluate

Check query answers against known examples, graph coverage and relation direction. Distinguish stored facts from predicted links.

Answer flow

  1. Extract entity/relation schema.
  2. Show sample triples.
  3. Translate query.
  4. Return answer with supporting path.

Exam traps

  • A KG is not a decision tree.
  • An absent edge does not prove a relationship is false.

C022

KG traversal and multi-hop queries

Multi-hop queries follow several relationships. Conjunctive queries require all stated conditions, often joining or intersecting results.

Problem it solves: Useful for questions such as finding a team owner through its player, or finding entities satisfying several connected criteria.

How to use it

  1. Identify the anchor entity and desired answer type.
  2. Write the sequence of relation directions.
  3. Traverse the relevant links.
  4. For AND conditions, retain only entities meeting every branch.
  5. Return the answer and supporting paths.
Example · data issues · evaluation · exam flow

Worked idea

Lecture example: find a drug targeting a protein associated with Alzheimer’s and also involved in a Phase II trial. The trial condition must apply to the same candidate drug.

What can go wrong → what to change → why

  • Graph incompleteness → label incomplete coverage or propose verified link completion → traversal cannot follow missing edges.
  • Unbounded traversal → constrain relation types/depth → avoid exploring irrelevant paths.

How to evaluate

Check each hop, direction and join. Measure correctness and coverage separately; an empty result may mean insufficient data.

Answer flow

  1. Parse target and anchors.
  2. Draw required path/branches.
  3. Apply all conditions.
  4. Explain missing-data limitations.

Exam traps

  • AND is not a union of unrelated answers.
  • Predicted edges require validation before being treated as facts.

C023

TransE embeddings

TransE learns vectors so that moving from a head entity by a relation vector lands near the tail entity. Nearer means a more plausible triple.

Problem it solves: Use for compact KG representations and candidate missing-link prediction when a simple translation model suits the relations.

How to use it

  1. Collect known head–relation–tail triples.
  2. Learn entity and relation vectors.
  3. Train known triples to score better than corrupted alternatives.
  4. For a query, apply the relation to the head vector.
  5. Rank candidate tails by closeness and validate predicted links.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: for Alice–worksFor–CompanyA, Alice vector plus worksFor vector should be near CompanyA vector. This is a learned geometric score, not a confirmed new fact.

What can go wrong → what to change → why

  • One-to-many relations → consider relation-specific models → one translation struggles to represent many distinct tails.
  • False negatives in corrupted triples → sample/check carefully → missing links may actually be true.

How to evaluate

Hide known links and check candidate ranking; inspect relation types where performance is poor. Compare cost and quality with alternatives.

Answer flow

  1. Identify link-prediction task.
  2. Explain translation in words.
  3. Describe training and ranking.
  4. State expressiveness limits.

Exam traps

  • Vectors are learned features, not literal coordinates in the real world.
  • A high score does not establish causation.

C024

TransR embeddings

TransR keeps entities in an entity space and projects them into a separate space for each relation before applying translation. Different relations can focus on different aspects.

Problem it solves: Consider when one shared TransE space poorly handles diverse relation types or one-to-many/many-to-one relationships.

How to use it

  1. Start with entity vectors and relation-specific projection matrices.
  2. For a candidate triple, project head and tail into that relation’s space.
  3. Apply the relation translation there.
  4. Train true triples to score above negative alternatives.
  5. Rank candidates and check held-out links.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: a person’s work relationship and family relationship need not use exactly the same combination of features; separate projections permit that distinction.

What can go wrong → what to change → why

  • More parameters → regularisation and validation → sparse relations can overfit.
  • Projection overhead → compare with simpler baseline → improved representation must justify latency/memory.

How to evaluate

Evaluate ranking per relation, held-out performance and computational cost rather than assuming a richer model always improves.

Answer flow

  1. Describe TransE limitation.
  2. Explain relation-specific projection.
  3. State training/query steps.
  4. Discuss accuracy–complexity trade-off.

Exam traps

  • TransR does not give each entity a completely unrelated factual identity.
  • Relation-space scores are not automatically calibrated probabilities.

C025

Bilinear / DistMult embeddings

Bilinear KG models score interactions between a head, a relation and a tail. RESCAL uses a full relation matrix; DistMult restricts it to a diagonal for efficiency.

Problem it solves: Choose by the relation pattern: efficient symmetric scoring may be suitable for some links but fails to distinguish directed roles.

How to use it

  1. Identify whether direction/asymmetry matters.
  2. Learn entity vectors and a relation interaction representation.
  3. Score candidate triples.
  4. Train against known and sampled alternatives.
  5. Select a model with enough expressiveness for the required links.

Source check: Slide61 states relation-matrix memory grows quadratically with entity count; more precisely full relation matrices scale with embedding dimension squared per relation. Notes retain the cost warning with corrected dependence.

Example · data issues · evaluation · exam flow

Worked idea

Illustrative: DistMult gives the same score for Alice–fatherOf–Bob and Bob–fatherOf–Alice. That symmetry makes it unsuitable for modelling the direction by this score alone.

What can go wrong → what to change → why

  • Asymmetric relation → consider ComplEx or a suitable asymmetric model → DistMult swaps head/tail without changing score.
  • Full relation matrices → assess memory/overfitting → RESCAL has greater parameter cost.

How to evaluate

Test directional reversals, held-out link ranks and memory. RESCAL relation-matrix storage depends quadratically on embedding dimension, not simply entity count.

Answer flow

  1. Identify relation pattern.
  2. Explain score interaction.
  3. Compare full and diagonal matrices.
  4. Justify choice and tests.

Exam traps

  • DistMult’s computational efficiency does not remove its symmetry limitation.
  • KG factorisation is a different task from user–item recommendation MF.

C026

Neural knowledge graph embeddings

Neural KG models learn richer interactions between entities and relations. Graph neural approaches also aggregate information from neighbours. The architecture determines what new entities it can handle.

Problem it solves: Useful when simple translation/bilinear scores miss relevant graph structure or external features.

How to use it

  1. Define link prediction or node/graph classification target.
  2. Choose inputs: IDs, relation types, node features or text.
  3. Use the appropriate architecture, such as ConvE or relation-aware aggregation.
  4. Train on permitted graph information.
  5. Validate on the required setting, including genuinely unseen nodes if relevant.

Source check: Slide69 broadly promises unseen-entity handling for neural models; this depends on architecture and available features, so it is not asserted for all models.

Example · data issues · evaluation · exam flow

Worked idea

Lecture ConvE flow: reshape entity/relation embeddings, convolve, flatten/project and match candidate embeddings. GraphSAGE instead samples and aggregates neighbour features.

What can go wrong → what to change → why

  • Overfitting → dropout, regularisation and validation → added capacity can memorise links.
  • Unseen IDs → use an inductive feature/aggregation design where appropriate → ordinary ID embeddings do not automatically generalise.

How to evaluate

Check held-out prediction, leakage through graph edges, relation-specific errors and runtime.

Answer flow

  1. State target and graph inputs.
  2. Explain one chosen architecture.
  3. Specify training split.
  4. Assess accuracy, unseen-node support and cost.

Exam traps

  • Not every neural embedding model handles unseen entities without retraining.
  • A predicted link remains a hypothesis.

C027

Inductive learning and generalization

Generalisation means learned patterns also work on unseen cases. Matching every training observation can simply mean memorisation.

Problem it solves: Use when evaluating a proposed learned model, comparing complexity or explaining why training accuracy alone is insufficient.

How to use it

  1. Define the real future cases and desired target.
  2. Split data before fitting preprocessing or selecting models.
  3. Fit only training examples.
  4. Tune complexity with validation or cross-validation.
  5. Use a final untouched test set and inspect relevant errors.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative: a deep tree predicts every historical consultation correctly but fails on new patients. A smaller validated tree can be the better exam recommendation.

What can go wrong → what to change → why

  • Patient/time leakage → group patients or respect time where required → repeated/future information inflates results.
  • Unrepresentative data → assess relevant subgroups and shifts → random splits do not fix missing populations.

How to evaluate

Compare training and validation performance, then final test results. Choose metrics by the cost of mistakes, not accuracy alone.

Answer flow

  1. Define unseen setting.
  2. Check split/leakage.
  3. Compare fit and generalisation.
  4. Justify complexity and metric.

Exam traps

  • Validation selects settings; test estimates final performance.
  • Good average results can hide failures in important groups.
Sample paper: 5001 Q2(f)

C028

Decision-tree reasoning

A decision tree learns feature tests from labelled data. Prediction follows one branch per test to a leaf containing a class or numeric output.

Problem it solves: Useful when prediction needs interpretable conditions; different from a KG, which represents entity relationships.

How to use it

  1. Specify input features and training labels.
  2. Clean/encode features without leaking the label.
  3. Learn splits separating useful outcomes.
  4. Limit depth/prune or tune minimum leaf size.
  5. For a new case, follow tests and explain its path.
Example · data issues · evaluation · exam flow

Worked idea

Illustrative diagnosis model: current symptoms/signs are inputs and the recorded doctor diagnosis is the training label. A tree path explains which conditions produced its output.

What can go wrong → what to change → why

  • Very deep tree → pruning/validation → small leaves may memorise noise.
  • Missing/unavailable input → define handling or ask for information → prediction cannot rely on future outcomes.

How to evaluate

Use held-out classification/regression checks appropriate to the target; inspect errors and tree complexity. For an ensemble, combine tree outputs explicitly.

Answer flow

  1. Define example, inputs and label.
  2. Explain learning splits.
  3. Trace inference.
  4. Describe validation and overfitting control.

Exam traps

  • A tree is an algorithm/model, not a database cylinder.
  • Each node split is not a separate trained tree.
