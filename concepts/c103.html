C103

End-to-end（端到端） sense-making（情境理解） design

End-to-end sense making connects raw sensor（感測器） data to recognized entities（實體；被描述的對象）, relationships, context, knowledge and an action.

Recognise（辨識；從資料找出物件或模式） this in a question: Multiple sensors, camera + sound, conflicting measurements, alignment（對齊） · Robot sorting, actions（動作） change environment, reward（獎勵）, safe learning

How does sensing end in a useful, testable decision?

  • An end-to-end architecture must explain how raw readings become recognized entities, relations（關係；對象間的連結）, context and a useful action. Naming a neural network（神經網路） does not fill missing functions.
  • A feedback loop uses new sensor observations after an action to update the current state; it is not necessarily online model training.
  • The knowledge component stores reusable relationships or constraints（約束條件）, while the current state stores the presently observed scene and system condition.
  • Evaluation（評估） should trace errors through the chain: incorrect sensing can look like a reasoning（推理） failure, while correct recognition can still feed an unsuitable action policy（策略）.
Implementation steps and their purpose
  1. Define the user goal and required decision.
  2. Specify sensors, signals（訊號） and data preparation.
  3. Choose features（特徵；描述樣本的屬性）/representation（表徵；資料的表示方式） and recognition task.
  4. Combine entity relationships with context/domain knowledge.
  5. Show planning and the action/output.
  6. Return observations/feedback where the task is a continuing loop.

Data, implementation and validation

Data, components and application

  • Model output unrelated to user need → connect each stage to the required action → exposes missing functions.
  • Sensors disagree → align and assess quality → avoids unsupported combined conclusions.
  • Good classifier but unusable system → evaluate timing and error consequences → complete-system usefulness matters.

How to evaluate it

Check sensing, recognition and decision errors separately, then task success, latency, robustness and action consequences.

Build the answer in this order

  1. Scenario goal.
  2. Inputs → processing → knowledge.
  3. Decision → action/feedback.
  4. Evaluate complete loop.

Common wrong answers and the exact correction
  • An architecture needs responsibilities and labelled arrows, not just input → AI → output.
  • Learning/training need not happen in every runtime loop.

An answer you could write

  • The sensors capture camera/motion data, recognition estimates lane position and drift, and decision logic selects a warning.
  • The audible warning is the action; later observations update the state.
  • I evaluate each stage and end-to-end warning usefulness, delay and false/missed alerts.

Where this is tested in the sample papers

ISY5002 Q2(b) — Deep-RL sorting architecture, reward and safe learning

What the question requires

  1. Define observations/state, actions and task success.
  2. Choose reward terms for correct sorting, safety and time.
  3. Draw hardware, perception（感知；由輸入理解環境）, decision and control loops.
  4. Explain simulation-first training and controlled transfer.

Proposed answer points

  • RGB-D（Red, Green, Blue–Depth；彩色加深度影像） + robot sensors → identification/tracking → state → deep-RL policy → safety/motion checks → arm/gripper（夾爪；機器人抓取物件的部件） action → new observations and reward. Include target objects, obstacles, other robots and people in the environment.
  • Reward correct placement; penalize collisions and unnecessary time. Enforce joint/gripper constraints in control rather than hoping a learned reward guarantees safety.
  • Train in a physics-based（基於物理；模擬運動、接觸等物理規律） simulator, then validate in controlled low-risk real tests with safety constraints active.

Avoid: A reward penalty is not a hard safety guarantee. Classification（分類；預測類別） of the object（客體；三元組終點） and control of the robot are separate responsibilities.
