LLM（Large Language Model；大型語言模型） tools and agents

An LLM can translate a natural-language request into a tool call. An agent（代理） adds planning, memory and repeated action–observation steps.

Recognise（辨識；從資料找出物件或模式） this in a question: Call tools, execute a workflow, choose actions（動作）, multi-step planning

What must the system deliver?

Use when answering needs live data or actions, rather than text generation（生成式；學習資料生成或分布） alone.

Scenario cueSuitable choiceWhy it fits
Only fixed reminder operations neededSimple intent（意圖）/slot（資訊欄位） service pipeline（處理流程）Fewer moving parts and clear action outcomes.
Several dependent operations requiredAgent with explicit（明確；直接提供的資訊） observations（觀測值） and memoryLater choices can depend on real earlier results.

How does a language request become a validated tool call?

  • The LLM proposes a structured tool invocation; an external tool performs the operation. These are distinct events and should have distinct outputs in the design.
  • A tool interface needs a function name and typed arguments. Missing slots must be resolved before the request is executed.
  • An agent may repeat plan → tool → observation when multiple steps are needed; a one-step API（Application Programming Interface；應用程式介面） call does not require an elaborate agent framework.
  • Memory keeps useful state and results, while the tool response supplies authoritative current facts（事實；推理中已知的資訊）. Generated prose must not replace the observation.
Implementation steps and their purpose
  1. Identify the required external operation.
  2. Extract its arguments from the request.
  3. Choose and call the appropriate tool/API.
  4. Read the actual result and report it.
  5. For multiple steps, plan subgoals and repeat after observing each outcome.

Data, implementation and validation

Data, components and application

  • Made-up result → require actual tool output → distinguishes action from guessing.
  • Wrong arguments → validate required fields → avoids querying the wrong object（客體；三元組終點）/date.
  • High latency or private data → consider smaller/local components where appropriate → matches scenario constraints（約束條件）.

How to evaluate it

Check argument correctness, tool success, end-to-end（端到端） task completion, latency, cost and faithful reporting.

Build the answer in this order

  1. Task requires which tool?
  2. Request → arguments.
  3. Tool result → next action/answer.
  4. Test failure and recovery.

Common wrong answers and the exact correction
  • A tool-using chatbot is not automatically fully autonomous（自主；可自行作決定）.
  • An LLM response does not prove an operation happened.

An answer you could write

  • The language component extracts a supported function name and validated arguments before calling the external tool.
  • The tool performs the actual operation; generated API-shaped text is not proof that it succeeded.
  • Use the returned result to answer or choose another step, and report a failure rather than inventing success.
