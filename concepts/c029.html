C029

Reasoning-system architecture（推理系統架構）

A reasoning-system architecture connects inputs, structured knowledge, an inference（推論） procedure, outputs and validation. Naming “AI” alone does not explain how a decision is made.

Recognise this in a question: Design reasoning（推理） solution, components, internal data structures, static lookup replacement

What information flows through a reasoning system?

  • Architecture explains responsibilities and information movement. A box labelled inference engine must name a procedure, such as forward chaining（前向推理） or case adaptation, while its KB must show what knowledge is stored. Input→AI→answer cannot answer a question explicitly asking for processes and data structures.
  • The requested granularity matters. Sample Q2(c) asks about the relationship between App and Web, so show the App’s RAPD output feeding the Web alongside doctor-entered findings. Q2(d) asks internal design, so now patient facts, knowledge structures, rule matching and result explanations belong in the diagram.
  • A coherent design should handle insufficient and contradictory evidence. Use present/absent/unknown for findings, request relevant missing information and avoid forcing one diagnosis when only a differential is supported. Diagnosis, urgency and recommended action are separate outputs but can be derived by one engine with different rule types.
Implementation steps and their purpose
  1. Extract user need, inputs and required outputs from the case.
  2. Choose a representation matched to available knowledge.
  3. Name the actual inference procedure.
  4. Draw component boxes with labelled data arrows.
  5. Add missing/conflict handling, explanations and validation.

Data, implementation and validation

Data, components and application

  • Overcomplicated design → one coherent procedure first → separate outputs do not require separate models.
  • Unclear arrows → label information passed → architecture must show how components cooperate.

How to evaluate it

Check requirement coverage（涵蓋率）, representative cases, data structures, explanations and failure handling. State assumptions instead of inventing case facts.

Build the answer in this order

  1. Read required scope.
  2. Specify components and data.
  3. Explain processing.
  4. Validate outputs and limitations.

Common wrong answers and the exact correction
  • Knowledge base is storage/representation; inference engine is the procedure.
  • Use black boxes for subsystem relationship questions and internals when requested.

An answer you could write

  • “Doctor findings and RAPD enter validated patient facts; a forward-chaining engine uses disease frames and typed rules to produce supported diagnoses, urgency and action.”
  • “Unknown findings trigger relevant follow-up; conflicting rules are resolved by declared priority or flagged for review.”

Where this is tested in the sample papers

ISY5001 Q2(a) — Stakeholder pain points

What the question requires

  1. Name the stakeholder.
  2. State a difficulty supported by the case.
  3. Connect it to the system’s intended benefit.

Proposed answer points

  • Primary doctors may lack specialist eye knowledge when choosing diagnosis/referral urgency.
  • Patients may face extra referral steps or delayed specialist assessment.

Avoid: Avoid invented numerical shortages or generic “AI is faster” claims.

ISY5001 Q2(b) — Functions, inputs and outputs

What the question requires

  1. Separate App and Web responsibilities.
  2. Name each input and processing function.
  3. Name distinct outputs and give a case example.

Proposed answer points

  • App: images of the eyes under illumination → measure/compare pupil response → RAPD indication.
  • Web: patient profile, symptoms and signs (including RAPD) → diagnostic/triage reasoning → diagnosis or differential list, urgency and action guidance.

Avoid: A diagnosis, referral urgency and action are different outputs. This is a case-study architecture, not clinical advice.

ISY5001 Q2(c) — Hybrid（混合式） subsystem relationship and data flow

What the question requires

  1. Treat the two subsystems as black boxes.
  2. Draw images → App → RAPD result → Web.
  3. Add doctor-entered profile, symptoms and signs to Web.
  4. Label the Web’s diagnostic, urgency and action outputs.

Proposed answer points

  • The App-to-Web relationship is sequential/serial in the proposed data-flow description.
  • A box diagram with labelled arrows is sufficient for the relationship; detailed knowledge internals belong in part (d).

Avoid: Use the lecturer’s exact hybrid taxonomy if prescribed. Do not add an unmentioned trained classifier or compulsory intermediate human gate.

ISY5001 Q2(d) — Knowledge-based internal architecture and data structures

What the question requires

  1. Validate inputs; distinguish present, absent and unknown.
  2. Store patient facts in working memory.
  3. Represent specialist knowledge as disease frames and diagnostic/triage/action rules.
  4. Match/fire rules; display conclusions and explanations.

Proposed answer points

  • Patient facts → inference engine ← knowledge base → diagnosis candidates + urgency + action.
  • Show structures: patient fact fields; disease frame IDs; rules with conditions, conclusions, priority and explanation. One engine can apply several rule types.
  • If evidence is missing/conflicting, request information or flag for doctor review. Clinical contents require specialist validation.

Avoid: A box labelled “AI” is insufficient. A KB stores knowledge; an inference engine names the procedure using it. Softmax（機率正規化函數） scores do not automatically encode urgency.

ISY5001 Q2(e) — Critique a proposed static lookup replacement

What the question requires

  1. Identify the proposed table’s actual scope.
  2. Compare it with the complete required functions.
  3. Explain a case-specific gap and consequence.

Proposed answer points

  • The proposal maps symptoms to diagnoses but does not establish equivalent urgency/action guidance. A primary doctor may still lack the information needed to act.
  • A table can be extended to multiple outputs and combinations; adequacy and maintenance are the issues to justify.

Avoid: Do not claim every lookup table can return only one diagnosis or cannot represent combinations. If criticizing unweighted tick counts, explicitly state that assumption.
