C024

TransR embeddings（嵌入；用向量表示內容）

TransR keeps entities（實體；被描述的對象） in an entity space and projects them into a separate space for each relation（關係；對象間的連結） before applying translation. Different relations can focus on different aspects.

Recognise（辨識；從資料找出物件或模式） this in a question: Predict a missing relation, entity embedding, relation-specific（關係專屬；依關係使用不同設定） projection（投影；轉到選定方向的座標）

Why project entities into a relation-specific space?

  • TransR gives each relation its own projection of the entity vectors. It can therefore emphasise work-related features for worksFor and a different combination for a family relation. Head and tail are projected using the chosen relation’s matrix before translation is scored.
  • The projection is the key change from TransE; simply adding more dimensions without relation-specific handling does not explain TransR. Entities retain a shared base representation（表徵；資料的表示方式）, but their relation-specific views can differ. The relation vector acts inside that projected space, not directly in the original space.
  • This flexibility costs parameters and computation. A sparsely observed relation may not provide enough evidence（證據；已觀察到的資訊） to learn a reliable projection, so a model with greater apparent expressiveness can perform worse on new links. Model choice must compare the representational need against data per relation, regularisation and serving budget.
Implementation steps and their purpose
  1. Start with entity vectors and relation-specific projection matrices.
  2. For a candidate triple（三元組；主體、關係、客體）, project head and tail into that relation’s space.
  3. Apply the relation translation there.
  4. Train true triples to score above negative alternatives.
  5. Rank（秩；矩陣獨立資訊的維度數） candidates and check held-out（留出資料；未參與該階段訓練） links.

Common wrong answers and the exact correction
  • TransR does not give each entity a completely unrelated factual identity.
  • Relation-space scores are not automatically calibrated（校準；令量測或機率對應實際意義） probabilities.

TransR limitations: the four lecture points

The trade-off: a separate projection for each relation gives flexibility, but it must be learned, stored and applied.

Lecture pointWhy it happensExam implication
Increased Model Complexity（模型更複雜）Besides entity/relation vectors, TransR learns a projection matrix for each relation. There are more parameters and modelling choices than in TransE.Justify why relation-specific spaces are needed; extra complexity is a cost, not automatically an improvement.
Computational Overhead（額外運算成本）Both head and tail must be projected before the translation score is calculated. Training and scoring therefore involve additional matrix operations.Consider training time, prediction latency and memory as well as ranking quality.
Limited Interpretability & Scalability（難解釋／擴展受限）Interpretability: learned vector coordinates and matrix entries do not usually have simple human-readable meanings. Scalability: storing relation matrices and evaluating many triples/candidates becomes costly as the graph and relation set grow.A good score alone may not explain a relation in ordinary words. Test whether the model fits the available graph size, memory and query-time budget.
Risk of Overfitting（過度擬合風險）A relation with few observed triples may not provide enough evidence to estimate its projection reliably. Extra parameters can fit training links without generalizing to unseen links.Check held-out performance, especially per relation; consider regularization, smaller dimensions or a simpler model if justified.

Short exam answer: “TransR models relation-specific views more flexibly than TransE, but each relation’s projection matrix adds parameters, storage and computation. Learned projections are difficult to interpret, large graphs increase processing cost, and sparse relations can overfit. I would compare held-out ranking quality and resource cost with a simpler baseline.”
