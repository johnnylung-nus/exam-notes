Abductive reasoning（溯因；由現象尋找合理解釋）

Abduction proposes an explanation for observed evidence（證據；已觀察到的資訊）. The explanation is plausible, not logically guaranteed, because other causes may produce the same evidence.

Recognise（辨識；從資料找出物件或模式） this in a question: Observed symptoms（症狀；患者感受到的不適）, possible cause, similar previous case

Illustrative explanatory reasoning（推理）

Worked study example: A machine is unexpectedly hot. Causes below are invented to show reasoning, not factual diagnostic rules. Further observations（觀測值） should distinguish causes.

What this tells us: A plausible first explanation is not enough. Compare alternatives and request evidence that separates them. In a clinical exam, use only case-supported findings and specialist-validated knowledge; do not invent precise probabilities.

How is a plausible cause different from a proved fact?

  • Abduction moves from an observation to possible explanations. Because several causes may produce the same effect, its output should be candidates supported by evidence, not a guaranteed fact. The useful tutoring question is “what other explanation could produce this?” rather than merely naming the most familiar cause.
  • Additional observations matter when they discriminate between candidates. Repeating evidence shared by every candidate does not help much. In a system design, follow-up questions should target differences that can change the ranking（排序） or rule support（支持度；同時出現的交易比例）, rather than collect every conceivable feature（特徵；描述樣本的屬性）.
  • A diagnostic output and an action output need not be identical. The sample paper distinguishes possible diagnoses（診斷；判斷可能的疾病或故障原因） from urgency/referral decisions. A direct warning-sign rule can justify（給出理由；用情境與證據支持選擇） urgency even while the diagnosis remains uncertain; forcing every action through one confident diagnosis creates an unnecessary dependency.
Implementation steps and their purpose
  1. List the observed effects.
  2. Identify candidate causes that could explain them.
  3. Check additional evidence and competing explanations.
  4. Rank（秩；矩陣獨立資訊的維度數） or update candidates if justified probabilities are available.
  5. Report uncertainty and request discriminating information.

Prepare the data and validate the representation（表徵；資料的表示方式）

Data, components and application

  • Single-cause assumption（假設；答案依賴但題目未明說的條件） → compare alternatives → several causes can share symptoms.
  • Invented probabilities → use justified prior（先驗機率；看證據之前）/likelihood（概似度） information → labels（標籤；作比較的正確答案） alone do not quantify uncertainty.

How to evaluate it

Check whether the proposed explanation accounts for the observations and survives contrary evidence. In labelled cases, assess diagnostic/ranking performance.

Build the answer in this order

  1. Name evidence.
  2. Generate plausible causes.
  3. Identify what distinguishes them.
  4. Conclude with stated uncertainty.

Common wrong answers and the exact correction
  • Do not present reverse implication（蘊涵；若前件成立則後件成立） as deduction.
  • Most plausible does not mean（均值；平均數） certainly true.

An answer you could write

  • Heat is compatible with blocked airflow, failed fan or heavy workload, so I retain alternatives rather than declare one proven cause.
  • I check fan operation and workload because these distinguish candidates; a repeated hot-surface observation alone does not identify the cause.
