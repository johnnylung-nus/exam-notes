MR-20 Ontologies（本體）

The lecture defines an ontology as a formal specification of concepts/classes, relationships/properties, constraints and hierarchies. Know what these elements mean and how to write the lecture’s representation.

Write the university ontology

Classes: Person, Student, Professor, Course
Student ⊆ Person
Professor ⊆ Person
Professor ─teaches→ Course
Student ─enrolls_in→ Course
Professor ─advises→ Student
ElementMeaning
ClassA kind of entity, such as Professor or Course.
HierarchyA more specific class belongs within a broader class; Professor is a kind of Person.
Property/relationA named connection such as teaches or advises.
Constraint/axiomA formally stated condition or relationship the model uses. Do not invent one merely because it sounds plausible.
IndividualA particular entity, such as Alice; an individual is not a class.

What the lecturer’s Alice example actually gives

Professor ⊆ Academic
Alice is a Professor
Therefore: Alice is an Academic

The same slide’s university hierarchy shows Professor under Person, so Alice is also a Person. No extra Academic ⊆ Person statement is needed to justify those two results.

Read each hierarchy link in its stated direction. Alice being Academic does not, by itself, prove Alice is Professor; every Academic need not be a Professor.

Canary ontology notation from the comparison slide

Bird ⊑ Animal
Canary ⊑ Bird ⊓ ∃canSing.True
SymbolRead it as
⊑is a subclass of / is included in
⊓AND: both descriptions apply
∃there exists at least one relation of the specified kind
canSing.TrueThe singing relation used in this lecture notation
  • In plain words: Bird is a kind of Animal.
  • Canary is a Bird with the stated singing relation.
  • Therefore a Canary is also an Animal.
  • Do not reverse this to say all Animals are Canaries.

The original comparison slide also expresses the bird example as a semantic network and a frame. Here the Canary example stays on the Ontologies page; Semantic Networks uses the original Mary/John diagram.

If asked to draw or write an ontology

  1. Identify the relevant classes.
  2. Show the supplied class hierarchy.
  3. Name the properties/relations and the kinds of entities they connect.
  4. Write any given constraints/axioms; define unfamiliar symbols.
  5. Add an individual fact if useful, then show one conclusion justified by the stated hierarchy.

Ontology versus knowledge graph: the lecture says ontology defines what is legal and provides the semantic structure; a knowledge graph stores actual entities and facts. See the knowledge-graph page for triples.

Do not automatically reject a record just because an arrow looks unusual. A consistency conclusion needs the actual declared constraints and reasoning rules; a diagram alone is insufficient.

Used Cases:

The use-case names come from the lecture. The short scenarios below explain how to recognize them in an exam; they are teaching examples, not quoted exam questions.

Lecture use caseWhat it meansExample / clue in a question
Semantic Web（語義網）Give web data shared, machine-readable meanings and relationships.Different datasets publish course/person information; agreed classes and properties let the system interpret and connect them.
Biomedical informatics（生物醫學資訊學）Organize and connect biomedical concepts and records with defined meanings.Different sources use disease names/codes; map them to agreed concepts before combining information. Similar wording alone does not prove equivalence.
Enterprise knowledge management（企業知識管理）Keep organizational knowledge consistent across departments/systems.HR and project records need the same meanings for Employee, Department and worksIn; define the shared classes and relationships.

Choose by the required job: explain what knowledge is stored and how this representation helps with the scenario. A use-case name alone is not a sufficient reason.
