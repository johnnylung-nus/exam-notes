C019

Frames（框架；附欄位的知識記錄）

Frames represent structured objects or typical situations using named slots（資訊欄位）, values and relationships. Parent frames can provide inherited shared properties and defaults.

Recognise this in a question: Knowledge representation（知識表示） schema（知識結構）, slots, defaults, inheritance（繼承）, entities（實體；被描述的對象） and attributes（屬性；對象的描述欄位）

How do slots, defaults and inheritance describe an entity?

  • A frame is a structured description with named slots, not just a box containing a label（標籤；作比較的正確答案）. Slots specify what can be known about the object（客體；三元組終點） and which values are permitted. Qualitative slots such as too-close/optimal（最優）/too-far can capture the interpretation required by the scenario, rather than storing only uncontextualised numbers.
  • Inheritance shares common slot definitions through parent frames. A child adds specialised slots or overrides a default; it should not duplicate every field or confuse a has-part link with a subtype. A disease frame stores domain knowledge while a patient frame stores this particular case’s observations（觀測值）.
  • Reasoning（推理） still needs a procedure. A frame can organise associated symptoms, rule references and result fields, but “match patient to disease frame” must explain what counts as a match. Simple match counts are support（支持度；同時出現的交易比例） scores, not calibrated probabilities, and a typical disease property is not automatically true for every patient.
Implementation steps and their purpose
  1. Identify object/frame types.
  2. Define slots, value types and qualitative states.
  3. Create shared parent slots and specific child slots.
  4. Link frames with correctly named relationships.
  5. Specify how an inference（推論；由依據得出結論） procedure uses the stored information.

Prepare the data and validate the representation（表徵；資料的表示方式）

Data, components and application

  • Only drawing objects → add slots/relations（關係；對象間的連結） and inference use → a database alone does not establish frame-based reasoning.
  • Defaults treated as facts（事實；推理中已知的資訊） → allow patient-specific override → typical knowledge is not always true.

How to evaluate it

Check inheritance, qualitative values and whether the schema can represent the question’s actual inputs and conclusions.

Build the answer in this order

  1. List frames.
  2. Specify slots and links.
  3. Show inheritance/overrides.
  4. Explain matching or rule processing.

Common wrong answers and the exact correction
  • A frame stores knowledge; it does not itself choose a diagnosis.
  • Disease knowledge and current patient findings are different records.

An answer you could write

  • BodyPart stores shared name, position and observation time; Eye inherits those slots and adds eye position, while Monitor is separate equipment.
  • PatientFacts stores current present/absent/unknown findings; disease frames store reusable knowledge and rule links used by the inference engine（推理引擎；套用知識得結論）.

Where this is tested in the sample papers

ISY5001 Q1(c) — Frame schema, slots, relationships and inheritance

What the question requires

  1. Identify the case objects: body parts, equipment and environment.
  2. Give each frame named slots, including qualitative states.
  3. Use a parent frame for shared properties.
  4. Label is-a and part-of relationships differently.

Proposed answer points

  • BodyPart(name, position, recorded_time) can be a parent for Eye and Face. Equipment can be a parent for Monitor.
  • Face may add distance/status; Monitor adds brightness/contrast; Environment adds ambient light. Link measurements to reference ranges.

Avoid: An eye is a body part, and is part of a face. These are different relationships. Do not replace a frame design with an unstructured object list.

ISY5001 Q2(d) — Knowledge-based internal architecture（架構） and data structures

What the question requires

  1. Validate inputs; distinguish present, absent and unknown.
  2. Store patient facts in working memory（工作記憶；當前處理的資訊）.
  3. Represent specialist knowledge as disease frames and diagnostic/triage/action rules.
  4. Match/fire rules; display conclusions and explanations.

Proposed answer points

  • Patient facts → inference engine ← knowledge base（知識庫；供推理查用的知識） → diagnosis candidates + urgency + action.
  • Show structures: patient fact fields; disease frame IDs; rules with conditions, conclusions, priority and explanation. One engine can apply several rule types.
  • If evidence is missing/conflicting, request information or flag for doctor review. Clinical contents require specialist validation.

Avoid: A box labelled “AI（人工智慧）” is insufficient. A KB stores knowledge; an inference engine names the procedure using it. Softmax（機率正規化；轉成總和為1的權重） scores do not automatically encode urgency.

ISY5001 Q2(e) — Critique a proposed static lookup replacement

What the question requires

  1. Identify the proposed table’s actual scope.
  2. Compare it with the complete required functions.
  3. Explain a case-specific gap and consequence.

Proposed answer points

  • The proposal maps symptoms to diagnoses but does not establish equivalent urgency/action guidance. A primary doctor may still lack the information needed to act.
  • A table can be extended to multiple outputs and combinations; adequacy and maintenance are the issues to justify.

Avoid: Do not claim every lookup table can return only one diagnosis or cannot represent combinations. If criticizing unweighted tick counts, explicitly state that assumption.
