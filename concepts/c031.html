C031

Knowledge graph（知識圖譜） + LLM（Large Language Model；大型語言模型） integration

A KG（Knowledge Graph）–LLM workflow uses structured graph facts（事實；推理中已知的資訊） to support（支持度；同時出現的交易比例） natural-language answers. The language model can interpret a question and explain retrieved（檢索；找出相關資料） relationships.

Recognise（辨識；從資料找出物件或模式） this in a question: Answer from documents, grounded（依據來源；使輸出有可核對支持） response, current facts, connected evidence（證據；已觀察到的資訊）

What must the system deliver?

Useful when users ask questions requiring connected entity knowledge, but need readable answers.

Answer requires entity relationships plus readable explanationKG lookup then LLM synthesisStructured conditions remain checkable

How can a language model use graph facts correctly?

  • KG–LLM integration assigns structured lookup and language generation different jobs. The graph query identifies connected entities under explicit（明確；直接提供的資訊） conditions; the LLM interprets the user’s wording and explains retrieved results. It should not fill a missing approved-drug fact from a plausible association in its language memory.
  • Entity linking（實體連結；把名稱對應至正確實體） and query construction are failure points before generation. A synonym, gene variant or relation direction can change the intended query. A controlled query template or validation of generated queries helps ensure the system asks the graph the same question the user asked.
  • Provenance（來源脈絡；資料從哪裡來） must survive the interface. Retrieved facts should include source and freshness where available; extracted or predicted links need an evidence status. Otherwise a fluent explanation can make a tentative graph-completion suggestion look like a verified database assertion. An empty graph answer should trigger a qualified response rather than fabricated completeness（完備性）.
Implementation steps and their purpose
  1. Identify entities and relations in the question.
  2. Construct a controlled graph query.
  3. Retrieve relevant（相關性；是否切合問題） facts/paths.
  4. Give retrieved evidence to the language model.
  5. Generate a concise answer with supporting facts and check it against evidence.

Illustrative structured query versus fluent assumption（假設；答案依賴但題目未明說的條件）

Worked study example: Question: “Which approved drugs target gene G?” Candidate records are invented to explain conjunction（合取；各條件都要成立） and evidence handling.

Data, implementation and validation

Data, components and application

  • Wrong entity/query → validate query and entity mapping → fluent language can hide retrieval errors.
  • Incomplete KG → state missing evidence → graph grounding cannot create missing verified facts.

How to evaluate it

Evaluate query correctness, retrieved evidence coverage（涵蓋率；能服務的使用者或項目範圍） and whether every answer claim is supported. Check source freshness.

Build the answer in this order

  1. State required relationships.
  2. Show query/retrieval step.
  3. Explain LLM role.
  4. Validate evidence and final answer.

Common wrong answers and the exact correction
  • A language model does not automatically make graph facts trustworthy.
  • Predicted/extracted links need provenance and validation.

An answer you could write

  • “I resolve gene G, query drugs with both a verified targets edge and the required approval status, then generate a sourced explanation from those records.”
  • “Predicted links and trial-only candidates remain labelled and are not presented as verified approved matches.”
